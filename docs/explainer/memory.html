Memory and caches

Fetching a number from main memory takes about a hundred times longer than adding two numbers. Caches hide that gap, and they work in lines of 64 bytes that only one core at a time may write. This page explains caches, cache lines, what happens when two cores write the same line (contention), and why the study pads its counters.

RAM is far away

Main memory (RAM) is large, gigabytes, but it sits outside the core. Asking it for a number and getting the answer takes about a hundred steps of the core's clock. A core could do a hundred additions in that time.

Think of a cook. The counter is small and right in front of the cook; the pantry is big and down the hall. If every pinch of salt meant a walk to the pantry, nothing would get cooked.

Caches: small, near, fast

So each core has a few small, fast memories next to it, called caches. When the core needs a number, it looks in the nearest cache first (L1, small and almost instant), then in a bigger one (L2), then in one that all the cores share (L3, bigger and slower), and only then in RAM. It keeps what it brings back in the caches, because it is likely to need it again soon.

L1 is the cook's counter: a dozen things within reach. L2 is the shelf behind. L3 is the walk-in fridge the whole kitchen shares. RAM is the pantry down the hall.

Data moves in lines of 64 bytes

Caches do not move one byte at a time. They move fixed blocks of 64 bytes, called cache lines. Ask for one byte and the whole line comes, because fetching 64 bytes costs about the same as fetching 1, and the neighbours are probably wanted next.

Nobody walks to the pantry for one egg: you bring the carton. The carton is the cache line.

One consequence matters for the study: two different numbers that sit in the same 64 bytes travel together. Eight counters of 8 bytes each fit in one line. False sharing and padding shows why that is a problem and how the study avoids it.

Two cores, one line

Each core has its own caches, so the same line can be in several caches at once. That is fine while every core only reads it. To write a line, a core must be the only one that holds it: every other copy is thrown away. The writer fetches the line first, and the next core that wants to write fetches it back.

Think of one shared notebook. Anyone may read it. To write in it you must hold it, and only one person can hold it. If eight people each want to add a line, the notebook goes round the table and each person waits for it. That waiting is contention.

The transfer takes about as long as a fetch from RAM, roughly 100 steps of the clock. An addition that could take 1 step takes 100, because another core wrote the line last. This is why a histogram with shared counters can get slower with more threads, which RQ2 measures.

An atomic add (What an atomic add is) reads the counter, adds one and writes it back as one indivisible step, so it always needs the counter's line for writing. If another core wrote that line last, the line travels first.

In depth: coherence, RFO, L1 to L3

Every core has its own L1 and L2; the cores share a larger L3. A coherence protocol keeps the copies consistent: shared state for readers, exclusive or modified for the one writer, invalidations for the rest. A locked read-modify-write on x86 needs the line in a writable state; if it is modified elsewhere, the request is a read for ownership (RFO) that pulls the line from the other core's cache.

Coherence in JS terms. Picture one SharedArrayBuffer slot that only one worker may hold at a time to write. Atomics.add waits until it holds the slot. If eight workers all add to the same slot, they queue for it.

Contention

Contention is several cores wanting the same line for writing at the same time. The histogram sets how much of it there is through its input: an image with k distinct grey levels sends every add to one of k counters (k: the contention dial). Why

Why is this not a flaw of the histogram to fix? It is what the study measures. Sharing one counter between threads is the simplest synchronization there is, and its cost is cache-line traffic. RQ2 asks whether that cost is the same in the browser as natively. The histogram that avoids the sharing, the local histogram, is measured too, and it is the version a real program should use.

False sharing and padding

There is a second way to contend for a line, without wanting the same counter. A counter is 8 bytes and a line is 64, so eight counters fit in one line. Two threads that add to two different counters in the same line still take turns holding the line. This is false sharing: contention with no shared variable.

It is like two people editing different words on the same line of a shared document, when only one person may hold a line at a time. They never touch each other's words, and they still wait for each other.

The study removes it by giving every counter its own block: each counter is followed by padding, so that the next one starts 128 bytes later. Switch the layout to see the difference:

Why

Why pad? Would the natural layout not be fairer? Without padding, the shared histogram would measure two things mixed together: the cost of sharing a counter, and the accidental cost of neighbours sharing a line. The study wants the first alone. The second is measured on its own, as the packed histogram of the extras campaign, so nothing is hidden.

Why

Why 128 bytes and not 64? Intel CPUs often fetch lines in pairs (the adjacent-line prefetcher), so two counters 64 bytes apart can still interfere; 128 keeps them in different pairs. A pilot on an earlier build tried both spacings natively and found them within about 1% of each other at 8 threads, and 128 was kept as the safer choice (ADR 0049). That pilot justifies the design; it is not a result. The price is 256 x 128 bytes = 32 KiB of counters instead of 2 KiB.

The packed histogram keeps the same code with 8-byte counters, eight per line. Private and packed atomics has its times next to the padded ones.

In short, false sharing costs every environment time, and Chrome most: its advantage under spread contention exists only with padded counters.

Counting line moves

The CPU keeps counters of its own, and one of them counts exactly the event described here: a core asking for a line and finding it in another core's cache with fresh writes in it (a HITM, for "hit modified"). Dividing that count by the number of adds gives how many times per add the line moved. The study reads these counters on its real runs: Line transfers, counted has the table.

In summary. RAM is far and caches are near. Data moves in 64-byte lines, so neighbours travel together. Many cores may read a line but only one may write it, so threads that add to the same counter take turns and the line travels, which costs about a hundred times the add itself. In the study, k sets how many counters the adds spread over, and padding gives each counter a line of its own, so only true sharing is measured.
