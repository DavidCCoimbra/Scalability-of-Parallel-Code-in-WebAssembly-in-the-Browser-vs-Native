Memory and caches

A core can add two numbers in a fraction of a billionth of a second. Fetching one of those numbers from the computer's main memory takes a hundred times longer. Everything about speed on a modern chip comes from hiding that gap, and the histogram in this study lives or dies on it.

In short: main memory is far away, so each core keeps a small copy of what it is using close by, in boxes of 64 bytes; when two cores want to write the same box, it has to travel between them, and that trip is what "contention" costs.

RAM is far away

The chip's main memory (RAM) is big, gigabytes, but it sits outside the core, at the end of a long wire. Asking it for a number and getting the answer back takes roughly a hundred steps of the core's clock. For a core that could have done a hundred additions in that time, that is an eternity.

An analogy. The cook's counter is small and right in front of them. The pantry is big and down the hall. If every pinch of salt meant a walk to the pantry, nothing would ever get cooked.

Caches: small, near, fast

So each core has a few small, very fast memories of its own next to it, called caches. When the core needs a number, it looks in the nearest cache first (L1, tiny and almost instant), then a bigger one (L2), then one shared by all the cores (L3, bigger and slower), and only then goes to RAM. Whatever it brings back, it keeps in the caches, in case it is needed again soon. Most of the time it is.

An analogy. The L1 cache is the cook's counter: a dozen things, within reach. L2 is the shelf behind them. L3 is the walk-in fridge the whole kitchen shares. RAM is the pantry down the hall. A good cook brings what they need to the counter once and keeps it there.

Data moves in lines of 64 bytes

Caches do not move one byte at a time. They move fixed boxes of 64 bytes, called cache lines. Ask for one byte and the whole line it sits in comes along, because fetching 64 bytes costs about the same as fetching 1, and the neighbours are probably wanted next.

An analogy. Nobody walks to the pantry for one egg. You bring the carton. The carton is the cache line.

This has a consequence that matters for the study: two different numbers that happen to live in the same 64 bytes travel together, whether you want them to or not. Eight small counters, 8 bytes each, fit in one line. Contention and padding shows why that is a problem and how the project avoids it.

Two cores, one line

Each core has its own caches, so the same line can be in several caches at once. That is fine while everyone only reads it. The moment one core wants to write it, the rule is: only one core may hold a line for writing, and every other copy is thrown away. The writer has to fetch the line to itself first, and the next core that wants to write has to fetch it back.

An analogy. One shared notebook. Anyone may read it. To write in it you must hold it, and only one person can hold it. If eight people each want to add a line, the notebook goes round the table, and each person waits for it. That waiting is contention.

The trip takes about as long as a fetch from RAM, roughly 100 steps of the clock. An addition that could have taken 1 step now takes 100, because the line was last written by someone else. This single fact explains why the study's shared-counter histogram gets slower with more threads (RQ2), and why the project counts exactly how many of these trips each add costs (Why Chrome).

What to remember

In summary. RAM is far, caches are near. Data moves in 64-byte lines, so neighbours travel together. Many cores may read a line, only one may write it, and when the writer changes, the line travels, which costs about a hundred times more than the write itself.

Contention and padding

Eight threads adding to the same counter can be slower than one thread doing all the adds alone. That sounds wrong until you know one fact about CPUs: cores do not share single numbers, they share blocks of 64 bytes, and only one core at a time may hold a block in order to write it. This page is about what that fact does to the histogram, and how the study keeps it under control.

In short: an atomic add needs its block exclusively, so contention is the block moving from core to core; the study sets how many blocks the adds spread over (k) and gives every counter its own block (padding).

One line, one writer

The whole story rests on two facts from Memory and caches:

  • Main memory is far from the cores, so each core keeps copies of what it is working on in a small, fast memory of its own, its cache. Data moves between memory and caches in fixed blocks of 64 bytes, called cache lines, never one byte at a time.
  • Many cores may hold a copy of the same line for reading. But to write into a line, a core must be the only one holding it: every other copy is thrown away first, and the next core that wants it has to fetch it again from the one that wrote it.

An analogy. One sheet of paper on a table, and eight people who each want to write one tick on it. Anyone may look at the sheet, but to write, you have to pick it up, and only one person can hold it. So the eight take turns, and most of each person's time is spent waiting for the sheet to come round.

An atomic add (what that is) reads the counter, adds one and writes it back as one indivisible step, so it always needs the counter's line for writing. If another core wrote that line last, the line must first travel over. On an 8-core chip that trip is of the order of a hundred clock ticks, a hundred times what the add itself costs.

In depth: coherence, RFO, L1 to L3

Every core has its own L1 and L2; the cores share a larger L3. A coherence protocol keeps the copies consistent: shared state for readers, exclusive or modified for the one writer, invalidations for the rest. A locked read-modify-write on x86 needs the line in a writable state; if it is modified elsewhere, the request is a read for ownership (RFO) that pulls the line from the other core's cache.

Coherence in JS terms. Picture one SharedArrayBuffer slot that only one worker may hold at a time to write. Atomics.add waits until it holds the slot. If eight workers all add to the same slot, they queue for it.

At k = 1 every add moves the one hot line, and 8 threads take more than twice as long as one, in all three runtimes. At k = 256 two cores rarely want the same line at the same moment, but with 8 threads most adds still find their line last written by another core, so natively and in Firefox the speedup stays near 1: no gain from 8 threads, but no loss either. Chrome is the exception, and that is the subject of Why Chrome.

Why

Why is this not a flaw of the histogram, to be fixed? It is the thing being measured. Sharing one counter across threads is the simplest possible synchronization, and its cost is pure cache-line traffic. RQ2 asks whether that cost is the same in the browser as natively. A histogram that avoided the sharing (the private control) is also measured, and that is the version a real program should use.

False sharing and padding

There is a second way to fight over a line without wanting the same counter. A counter is 8 bytes and a line is 64, so eight counters fit in one line. Two threads adding to two different counters that happen to share a line still take turns holding the line. This is false sharing: contention with no shared variable at all.

An analogy. Two people editing different words of the same line of a shared document, where the rule is that only one person may hold a line at a time. They never touch each other's words, and they still wait for each other.

The study removes it by giving every counter its own block: each counter is followed by enough padding that the next one starts 128 bytes later. Switch the layout to see the difference:

Why

Why pad at all? Would it not be fairer to measure the natural layout? Without padding, the shared histogram would measure two things mixed together: the true cost of sharing a counter, and the accidental cost of neighbours sharing a line. The study wants the first one alone. The second is measured separately, as the packed extra below, so nothing is hidden.

Why

Why 128 bytes and not 64? Intel CPUs often fetch lines in pairs (the adjacent-line prefetcher), so two counters 64 bytes apart can still interfere. 128 keeps them in different pairs. A pilot on an earlier build tried both spacings natively and found them within about 1 % of each other at 8 threads, inside the noise between two campaigns; 128 was kept as the safer choice (ADR 0049). That pilot justifies the design only; it is not a result. The price is 256 x 128 bytes = 32 KiB of counters instead of 2 KiB.

Counting line moves

Everything above would be a story if it could not be checked. It can: the CPU keeps counters of its own, and one of them counts exactly the event described here, a core asking for a line and finding it in another core's cache with fresh writes in it (a HITM, for "hit modified"). Reading those counters during 30 runs per cell, and dividing by the number of adds, gives how many times per add the line moved.

Natively and in Firefox the line moves about once per add at k = 256 and about once per four adds at k = 1 (when a core keeps the line for a while, its next few adds find it already there). Chrome's numbers look different, and that difference is the whole of Why Chrome: code and counters, where the table lives.

In summary. Cores share 64-byte lines, and only one may write a line at a time, so threads adding to the same counter take turns and the line travels. k sets how many counters the adds spread over; padding makes sure each counter has a line of its own, so only true sharing is measured. The CPU can count the line moves, and the study did.
