Change the measured path safely

Most changes to this repository are ordinary. A few touch the code that is timed, and that code is the experiment: it changes only with a record. This page gives the rules that protect the measurements, the reason for each, and the procedure for a change to the measured path.

The rules

Each rule exists because of one way the study could go wrong.

RuleWhat goes wrong without it
Never edit a file in data/raw/A run is what the machine wrote at that moment. A number fixed by hand cannot be told from a real one later, and every table it feeds becomes suspect. A wrong run is excluded by a rule written before the analysis (the data check), or run again and the old one moved to excluded/ with an ADR that says why.
Regenerate every table; never edit oneYou can delete data/tables/ and remake it with make all-results. If a number in the paper and a number in a table disagree, one make shows which one moved (Reproduce the tables and figures).
Never mix runs of two builds in one comparisonThe compiler lays code out differently after almost any change, and the layout alone can move a time by a few percent. Two builds compared with each other measure the change, not the environment. Every reported campaign ran on the build tagged measured/v3, and every run records the digest of its binary (Builds and tags, The build history).
Change the measured code only with an ADR and a codegen diffThe timed region, the workload kernels and the checksum are the experiment. A refactor there leaves the machine code the same (codegen-neutral) or it makes a new build. See the procedure below.
mypy --strict, and types for domain conceptsThe harness and the analysis are Python that runs unattended for 14 hours. A typo in a key name found at run 3000 of 5310 costs an afternoon; the type checker finds it before the campaign starts. Enums and dataclasses (Workload, PlannedRun, Interval) instead of strings and tuples mean a wrong value cannot be built.
One struct per file, one concept per module, a README with a Mermaid flowchart per folderA file that holds one thing can be opened from a question ("where is the padding?") and read whole. The README answers "which file holds what" before you open any (Repository tour).
Named constants; comments only for a whyYou can search for CACHE_LINE_BYTES; you cannot search for 128. A comment that repeats the code goes stale the first time the code changes; a comment that says why does not.
No em dash, and every document in EnglishThe author's rule, applied to every file so that the repository reads as one text.

Change the measured code

The measured path is the timed region (bench/src/measurement/), the workload kernels and the checksum. You may change it: refactors, new parameters, rewritten loops and closures. Follow these steps.

  1. Write the ADR first. Say what changes, why, and what it could do to the comparison.
  2. Run the codegen diff. It builds the base and your tree at the same path, in every variant, and reports which functions' machine code differ. Put the list of hot functions that changed in the ADR.
  3. If no hot function changed, the change is a readability refactor and the build stays the same (ADR 0062).
  4. If one did, it is a new build. Tag it, and run again every campaign that is compared with another. The second build did so (ADR 0069), and so did measured/v3: 27,150 runs (ADR 0084, The session of a build).
bash scripts/codegen_diff.sh measured/v3

Warning

Adding code can change code you did not touch. The first draft of the sequential filter called a helper of the parallel filter; with two callers the compiler stopped inlining that helper, and the machine code of the parallel filter changed although its source had not (ADR 0086). Run the codegen diff after every change in bench/src, not only after changes to a kernel.

Why

Why so careful about a few instructions? The study's differences are a few percent, and the layout of the code in memory alone moves times by that much. Mytkowicz and others showed in 2009 that changing the link order or an environment variable can swing a benchmark more than the optimization being tested. A one-line change in the loop is a change to the experiment, and the only sound way to keep comparing is to measure everything again on the new build.
