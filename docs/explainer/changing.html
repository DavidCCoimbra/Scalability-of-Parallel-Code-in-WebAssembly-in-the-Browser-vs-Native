Add a workload or change the measured path

You will want to change something: a workload, a campaign, a statistic, a comment. Most changes are ordinary. A few touch the one thing that must not move without a record: the code that is timed. This page gives the rules, the reason behind each one, and a recipe for the three common additions.

In short: raw data is never edited, tables are always regenerated, the measured code changes only with an ADR and a codegen diff, and everything else follows the style the type checker and the tests enforce.

The rules and why

Each rule below exists because of a way the study could have gone wrong. The box says what that way is.

Why

Never edit a file in data/raw/. A run is what the machine wrote at that moment. If a wrong-looking number is "fixed" by hand, nothing can tell it from a real one later, and the whole table it feeds is suspect. A wrong run is excluded by a rule written before the analysis (The data check), or re-run and the old one moved to excluded/ with an ADR saying why.

Why

Every table is regenerated, never hand-edited. data/tables/ can be deleted and remade with make all-results. If a number in the paper and a number in a table ever disagree, one make shows which one moved (From raw runs to the paper).

Why

Never mix runs of two builds in one comparison. The compiler lays out code differently after almost any change, and the layout alone can move a time by a few percent (Our own asymmetries). Two builds compared against each other would measure the change, not the runtime. Every reported campaign ran on the build tagged measured/v3, and every run records the binary's hash (Builds and tags).

Why

The measured code changes only with an ADR and a codegen diff. The timed region, the workload kernels and the checksum are the experiment. A refactor there must leave the machine code the same (codegen-neutral) or it makes a new build. See Touching the measured code.

Why

mypy --strict, and types for domain things. The harness and the analysis are Python that runs unattended for 14 hours. A typo in a key name found at run 3000 of 5310 costs an afternoon; the type checker finds it before the campaign starts. Enums and dataclasses (Workload, PlannedRun, Interval) instead of strings and tuples mean a wrong value cannot even be built.

Why

One struct per file, one concept per module, a README with a Mermaid flowchart per folder. The reader of this project is someone who has never seen it (you, today). A file that holds one thing can be opened from a question ("where is the padding?") and read whole. The README answers "which file holds what" before you open any (How the code is organised).

Why

Named constants, comments only for a why. CACHE_LINE_BYTES can be searched for; 128 cannot. A comment that repeats the code goes stale the first time the code changes; a comment that says why (and which ADR) does not.

Why

No em dash anywhere, and every document in English. The author's rule, applied to every file so that the repository reads as one text.

Add a workload

A workload is a struct that implements one small trait: prepare outside the clock, run inside it, checksum over the result.

  1. Write it in bench/src/workloads/, one file. Keep allocation in prepare or the constructor: the WASM allocator takes a global lock, and a lock inside the timed region would be a synchronization cost that is not the one under study.
  2. Name it in WorkloadKind (bench/src/experiment/workload_kind.rs): the enum variant, its string name, its capabilities (can it repeat identically for passes, does it take a grain or a pitch) and its line in build_with.
  3. Mirror the name in the harness: the Workload enum of harness/campaign/workload.py and its capabilities, so a spec can name it and the harness can refuse what it cannot do.
  4. Give it a checksum that means something. The checksum is hashed from the final result only. Two environments or two thread counts that produce different checksums are wrong, and analysis.datacheck blocks the analysis.
  5. Add it to the CI cases (harness/browser_check/cases.py): CI runs every workload small in headless Chrome and Firefox and compares the checksums with native. A workload that is not there is not checked in a browser.
  6. Add a quick spec (harness/campaigns/quick-*.json, a make quick-* target) so anyone can watch it run on a laptop in a minute. Then a real spec, if it is to be measured.
  7. Run make test (Rust tests, Python tests, lint) and make quick-rq1 style check for your workload.

Add a campaign

  1. Copy the closest spec in harness/campaigns/ (every key explained). Give it a new name (the results folder) and a new orderSeed (any integer; it is recorded, so the order can be rebuilt).
  2. Keep the protocol unless the question needs otherwise: 30 repetitions, the P-core mask, the warm-up per workload, "strict": true on the PC. Changing a protocol value is a design decision: write the ADR first (When a decision needs an ADR).
  3. Add a row to harness/campaigns/README.md with its ADR, and if it is a sequence of specs, a target in make/campaign.mk like cutoff-campaigns.
  4. Try it small first: a quick- copy with 3 repetitions and 4096², run on the Mac.
  5. Measure on the PC: make env-setup, then make campaign SPEC=..., make status from another terminal. Nothing else may run on the PC meanwhile.
  6. Add the results target in make/results.mk: the data check first, then the tables into data/tables/<name>/; add it to all-results.

Why

Why a file and not command-line flags? Because the file is committed. Months later the spec says exactly what ran, the harness stores it inside campaign.json next to the runs, and a restart checks that nothing in it changed (Sessions and resume). A flag typed in a terminal is gone when the terminal closes.

Add an analysis

  1. A command is a top-level module in analysis/ run as python3 -m analysis.<name> data/raw/<campaign> --output ...; the statistics it uses live in the subpackages (stats/, scaling/, inference/). Reuse them: the bootstrap, Holm and the run summaries are there, with their seed and settings fixed by the analysis plan.
  2. Read the raw folder through analysis.campaign and analysis.runs, never the CSVs by hand: they apply the same exclusions as every other table.
  3. Write a CSV table and, for a statistic with settings, a .json sidecar with them and the commit (Why the tables carry a sidecar).
  4. A unit test in analysis/tests/ on a tiny made-up campaign; a row in analysis/README.md; the command in a make *-results target.
  5. If the pages of this documentation should show it: make explainer picks up every CSV in data/tables/*-v3/ automatically (The numbers of this documentation).

Why

Why was the analysis plan written before the campaign? With 162 configurations and many statistics to choose from, something would come out "significant" by luck, and it is human to prefer the test that does. The plan (docs/adr/0037-analysis-plan.md, ADR 0037) fixed the tests, the 10 primary contrasts and the exclusions first. A new analysis is welcome, but it is exploratory until a plan says otherwise (Ten decisions, a stricter bar).

Touching the measured code

The timed region (bench/src/measurement/), the workload kernels and the checksum are the experiment itself. Changing them is allowed, with a record:

  1. Write the ADR first: what changes, why, and what it could do to the comparison.
  2. Run the codegen diff: bash scripts/codegen_diff.sh [BASE_REF] builds the base and your tree at the same path, every variant, and reports which functions' machine code differ. Put the list of hot functions that changed in the ADR.
  3. Neutral? If no hot function changed, it is a readability refactor and the build stays the same (ADR 0062).
  4. Not neutral? It is a new build: tag it (measured/v3), and every campaign to be compared with another must be re-run on it. The v2 build re-ran every campaign for this reason (ADR 0069), and so did measured/v3: 27,150 runs (ADR 0084, The session of a build).

Why

Why so careful about a few instructions? Because the study's differences are a few percent, and the layout of the code in memory alone moves times by that much. Mytkowicz and others showed in 2009 that changing the link order or an environment variable can swing a benchmark more than the optimization being tested. A one-line change in the loop is a change to the experiment, and the only honest way to keep comparing is to re-measure everything on the new build.

In summary. Raw data is read-only, tables are disposable, the timed code is the experiment. Add a workload through the trait and the two name lists; add a campaign through a spec file; add an analysis through a command that reuses the plan's statistics. When in doubt, write the ADR.
