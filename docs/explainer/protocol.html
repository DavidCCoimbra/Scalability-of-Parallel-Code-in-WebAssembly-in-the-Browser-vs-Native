Runs, warm-up and order

Timing a program once tells you very little: the next time it will take a different time (Measuring time: why one run is not enough). This page is the set of rules that decide how many times to measure, which measurements to keep, and in what order to take them, so that the numbers mean what we say they mean.

In one sentence: repeat whole program starts, not just loops inside one program; throw away the first iterations of each; take 30 starts per configuration; and shuffle all the starts of all three environments together, so that a slowly changing machine cannot favour one of them.

The run is the unit

Inside one run, the workload is timed 10 times in a row. Those 10 times mostly agree. It is tempting to treat them as 10 measurements. They are not, and understanding why is the key to this whole page.

Iterations, inside one run

Same process, same compiled code, same memory layout, warm caches. Everything a program start decides, these 10 share. If the start happened to be a slow one, all 10 are slow together. They are 10 looks at one situation.

Runs, between starts

A fresh process or a fresh browser re-draws everything a start decides: which machine code the browser's compiler produced this time, where the buffers landed in memory, which cores the threads got. Each run is a new situation. Only runs are independent (ADR 0005).

Picture it. To know how long your commute takes, you would not time it once and then look at your watch 10 times during that one trip. You would make the trip on 30 different days. The 10 looks at the watch are iterations; the 30 days are runs.
Why does it matter which one we count? Because the number of measurements decides how sure we claim to be. With 30 runs of 10 iterations, counting iterations would say "300 measurements, very sure"; counting runs says "30 measurements, fairly sure". The 300 would be a lie, because the 10 inside a run are not 10 pieces of new information. That mistake has a name, pseudo-replication, and it is the most common error in benchmark papers (Georges et al. 2007; Kalibera and Jones 2013). The study avoids it by reducing each run to one number first, the median of its 10 iterations (the middle one when sorted), and doing every statistic over those 30 numbers.

Warm-up inside the run

The first iterations of a run are slow. In a browser, the engine is still turning the WebAssembly into fast machine code, in stages, while the program already runs (tier-up; see Engines and JIT). Natively, the first pass touches memory that was never used before, and the caches are cold. These iterations are timed, so you can see them in the CSV, but they are not used: they are the warm-up, W iterations before the 10 measured ones.

Why not just skip one iteration? Because how long the start-up effect lasts depends on the workload and on the environment. Firefox kept recompiling one histogram function for dozens of iterations. If W were too small, the measured iterations of that cell would still be slow, and Firefox would look worse than it is. If W were huge, campaigns would take days for nothing. So W was chosen per workload, from pilot runs with no warm-up and 100 iterations: find the iteration where each run settles, take the largest over every environment and thread count, multiply by 1.5 for safety, and never go below 5 (ADR 0043). The same W is then used in native, Chrome and Firefox, so the environments compared within a workload get the same procedure. That choice came from pilot data, which is fine for a design decision; pilot data never appears as a result.

Two more things happen before the clock starts. The pool of worker threads is built. And in the browser, the page first waits 3 seconds, the start delay.

Why wait 3 seconds? A browser keeps doing things of its own for a while after it opens: loading extensions, checking files, warming its own caches. In a pilot, Firefox was still doing that during the first short iterations and made them up to 32 % slower. Three seconds lets the browser finish being a browser before the page starts being a benchmark (ADR 0048).
Why is the first browser run of each session thrown away? The first launch of a browser after the machine was prepared is much slower than every later one (likely because its files are read from disk for the first time). If it counted, one run of one configuration would be an outlier for a reason that is not the runtime. So that launch is run and discarded, in every session, and the first counted run is like all the others (discarded first launch, ADR 0034, ADR 0040).

30 runs, 10 iterations

Each configuration (one environment, one workload, one N) is measured by 30 runs, each with 10 measured iterations (ADR 0047). The main campaign is 3 environments, 9 workload settings and 6 thread counts (N in {1, 2, 4, 6, 7, 8}), times 30: 4860 runs, plus 450 runs of plain sequential code at one thread (Is the one-thread baseline fair?): 5310 in all.

Why 30, and not 5 or 100? More runs make the estimate more precise, but each one costs machine time, and the gain shrinks: going from 5 to 30 narrows the uncertainty a lot; going from 30 to 100 narrows it only a little more. Thirty is the course's rule, and a pilot checked that 30 gives the precision the questions need: the intervals below are within a few percent of the estimate. More iterations per run would not have helped at all, because what varies is between runs, not inside them.

Random interleaved order

The 5310 runs took 14 hours. Over that time, a machine drifts: it warms up, a background job wakes up, memory fragments. Now imagine all the native runs were taken first and all the Firefox runs last. Any slow change of the machine would land on Firefox and not on native, and would look like a difference between the two environments. It would be invisible, and it would be wrong.

Why shuffle, and why with a seed? The campaign builds the full list of runs (every environment, workload, N and repetition) and shuffles it once, so native, Chrome and Firefox runs are mixed throughout. Drift still happens, but it now falls on all three alike: it becomes noise, which the intervals account for, instead of a bias, which nothing would catch. The shuffle uses a recorded seed (2026112201 for the main campaign), so the same order can be rebuilt later: a stopped campaign resumes at exactly the position it stopped, and anyone can reproduce the sequence (ADR 0034).

After the campaign, the data check looks for drift that slipped through anyway: in each configuration, do the run values trend with the run's position in the order? One of the 177 configurations showed a trend, about what chance alone would produce. It is kept, and it is not one of the cells the ten primary comparisons use.

If you already know this: the plan, the seed and the drift check

The drift check is Spearman's rho between a run's order position and its value, flagged at |rho| above 0.5 with at least 10 runs. With 30 runs and no drift that happens by chance about 0.7 % of the time, so about 1.2 of the 177 configurations are expected (ADR 0051).

Fork-join calibration

Starting a parallel region has a cost of its own: the worker threads must be told there is work, and the thread that asked must wait until all of them are done. That is the fork-join cost (Fork-join and its cost). To know how big it is, every run times a few parallel regions with nothing inside them, before its warm-up: what remains is the pure price of starting and joining (ADR 0030).

Why measure it at all, if the workload's time already includes it? Because without a separate number we could not tell a slow workload from a slow start. If the browsers scale worse on small images, is the parallel code slower, or is the fixed cost of each region bigger? The calibration answers that: it is the fixed cost. Nothing is subtracted from the measured times; the calibration describes, it does not correct.

Two kinds of sample, 20 of each in every run:

  • warm: back to back, so the workers are still awake and looking for work;
  • cold: each after a pause at least as long as the workload's checksum, so the workers have gone to sleep, as they have before every measured iteration. Cold minus warm is the cost of waking them.

If you already know this: the step at N = 8, the clock ticks and the code

All three environments step up at N = 8, likely because the coordinating thread then shares the 8 cores with N workers. Below N = 8 the browser values are one or two ticks of their coarse clocks (performance.now() steps by 5 µs in Chrome and 20 µs in Firefox), so a 0 there means "under one tick", not free.

What to remember. One number per run, 30 runs per configuration, the first iterations of each run thrown away, and all the runs of all three environments shuffled together. Each rule exists because without it the numbers would look just as precise and be wrong.
