The run protocol

A run is one fresh process that warms up, times the workload ten times and writes the times to a file. This page follows a run from the harness to the two files it leaves on disk, then gives the rules of the protocol: the run as the unit of analysis, the warm-up, the start delay, 30 runs in one shuffled order, and the fork-join calibration.

The run is the unit

Inside one run the workload is timed 10 times in a row, and those 10 times mostly agree. They look like 10 measurements. They are not, and the rest of this page follows from that.

Iterations, inside one run

Same process, same compiled code, same memory layout, warm caches. The 10 iterations share everything that a program start decides. If the start was a slow one, all 10 are slow together: they are 10 looks at one situation.

Runs, between starts

A fresh process or a fresh browser decides again everything that a start decides: the machine code the engine produces this time, where the buffers land in memory, which cores the threads get. Each run is a new situation. Only runs are independent (ADR 0005).

Why

Why does it matter which one is counted? The number of measurements decides how sure the study claims to be. With 30 runs of 10 iterations, counting iterations says "300 measurements"; counting runs says "30". The 300 would be false, because the 10 inside a run are not 10 pieces of new information. The mistake is called pseudo-replication (Georges et al. 2007; Kalibera and Jones 2013). The study reduces each run to one number first, the median of its 10 iterations, and computes every statistic over those 30 numbers.

For the atomic histogram at k = 1 they spread over about a quarter of their value, in clusters: how the 8 threads of one start take turns on the one contended counter differs from start to start. No number of iterations inside one run shows that spread; only new starts do.

From the harness to two files

A run is one start of one program. For native, the compiled program starts, measures and exits. For a browser, Chrome or Firefox starts with a new, empty profile, loads one page that measures, and is closed. Nothing survives from one run to the next: no process, no cache, no window.

Why

Why is nothing automated inside the browser? Puppeteer, Playwright or the DevTools protocol can drive a browser from a script, which would make the harness simpler. They do it from inside the browser process: more threads, more messages and more timers in what is measured. So the harness only launches the browser with a URL and waits for the result file to appear (ADR 0006).

A native run

For a native run the harness starts the compiled program, bench/target/release/native, with the configuration as command-line flags (workload, image size, threads). The program prints its results as CSV to standard output. The harness captures that text and writes it to disk, next to a record of the context of the run.

The program does four things in order, and the browser page does the same four, because it is the same Rust code. It builds the pool of N worker threads. It generates the input image from a fixed seed. It times a few empty parallel regions (the calibration). Then it runs the warm-up and the measured iterations, timing each one.

Why

Why is only the parallel work timed? Each iteration also prepares its buffers and checks its result, outside the timed region. Inside it, the time would include work that has no relation to scaling, which native and the browsers do at different speeds for reasons that are not threads. The timed region starts right before the parallel region and ends right after it.

Checksum. Every iteration ends by hashing its whole output to one number. The first iteration's number is the reference: a later one that differs means that the program computed something else, and the run fails. The numbers must also match across environments and thread counts, which harness.collect checks before any analysis.

A browser run

A browser run starts Chrome or Firefox with a temporary, empty profile, without a window (headless), with its updates, telemetry and background features off, and with a URL that carries the configuration: the same values the native program gets as flags (ADR 0022, ADR 0029).

Why

Why a fresh profile every time? A profile is the browser's state: caches, compiled code it saved, settings, history. If run 2 reused the profile of run 1, it could start with code already compiled or files already cached, and be faster for a reason that is not the environment. A fresh profile makes every browser run start from nothing, as every native run does.

Why

Why headless? A window means drawing, compositing and a desktop that talks to the browser: work on the measured cores that is not the workload. A pilot measured the difference between headless and a visible window at under 0.3%, so headless costs nothing and removes a source of noise (ADR 0046).

What the harness does

  1. Creates a fresh profile (Firefox also gets a user.js that turns off updates, telemetry and safe browsing).
  2. Starts the browser in the scope and CPU mask of the run, with index.html?run=<id>&threads=8&....
  3. Waits for <id>.csv to appear, or for a timeout.
  4. Stops the whole scope, so that no browser process survives into the next run, and deletes the profile.
  5. Adds the context of the machine (mask, governor, foreign CPU time) to <id>.json.

What the page does

  1. Refuses to run unless it is cross-origin isolated (The results server).
  2. Waits the start delay (3 s), so that the browser finishes its own start-up first.
  3. Starts a coordinating Web Worker, which loads the WASM module and starts N pool workers.
  4. The worker calls the same Rust run function and gets the CSV back as a string.
  5. The page posts {csv, meta} to the local server.

Why

Why does a worker run it, and not the page itself? While the pool works, the thread that started the parallel region waits for the others, and in a browser that wait blocks the thread (Atomics.wait). The main thread of a page may not block, because it also draws the page and handles input. So the page gives the work to a Web Worker, which may block, and waits for its message (Threads and Web Workers).

In depth: the page, the worker and the browser flags

Chrome is Chrome for Testing 155.0.8059.84 and Firefox is 158.0, both pinned and checked before every session (ADR 0021, ADR 0071). The start delay came from a pilot in which Firefox was still starting up during short iterations (ADR 0048).

The results server

A web page cannot write a file to your disk. So the harness runs a small web server on the machine, harness/server.py, on the E-cores, reachable only from the machine itself (127.0.0.1). It does two things:

  • It serves the page. The browser loads bench/www/index.html from it, with two headers that make the page cross-origin isolated.
  • It receives the result. When the page finishes, it posts the CSV and some context to the server (POST /results?run=<id>), and the server writes <id>.csv and <id>.json, the same two files a native run gets.

Why

Why do the headers matter? Threads in a browser share memory through a SharedArrayBuffer. That feature was once used in a security attack, so browsers now refuse it unless the page declares, through those two headers, that it loads no content from other sites. Without the headers there is no shared memory and no threads. The page checks that it is isolated before it starts, and fails with an error if it is not.

In depth: the headers and the write order

The server writes the JSON first and the CSV last, so a CSV that exists always means a complete run. It never overwrites a run (it answers 409): a repeated id is a bug in the harness to notice, not to hide (ADR 0019). The headers are COOP and COEP.

It lets the analysis exclude a run that was not taken under the right conditions. The run record lists every field.

Warm-up inside the run

The first iterations of a run are slow. In a browser, the engine is still compiling the WebAssembly to fast machine code, in tiers, while the program already runs (tier-up, Engines and JIT). Natively, the first pass touches memory for the first time and the caches are cold. These iterations are timed, so you can see them in the CSV, but they are not used: they are the warm-up, W iterations before the 10 measured ones.

Why

Why not skip one iteration and be done? How long the start-up effect lasts depends on the workload and on the environment: Firefox kept recompiling one histogram function for dozens of iterations. With W too small, the measured iterations of that configuration would still be slow, and Firefox would look worse than it is. With W very large, campaigns would take days. So W is chosen per workload, from pilot runs with no warm-up and 100 iterations: find the iteration at which each run settles, take the largest over every environment and thread count, multiply by 1.5, and never go below 5 (ADR 0043). The same W is used in native, Chrome and Firefox. Pilot data decided it, which is its proper use; pilot data is never a result.

Two more things happen before the timed region. The pool of worker threads is built. And in a browser, the page first waits 3 seconds, the start delay (The start delay tells how it was found).

Why

Why is the first browser run of each session discarded? The first launch of a browser after the machine is prepared is much slower than every later one, likely because its files are read from disk for the first time. If it counted, one run of one configuration would be an outlier for a reason that is not the environment. So every session runs that launch and discards it (discarded first launch, ADR 0034, ADR 0040).

The start delay

The numbers in this section come from pilots and from the earlier build, measured/v2. They justify the fix; they are not results of the study.

A browser keeps working for seconds after the page has loaded: it compiles code, loads components, starts services. The warm-up pilot ran with no delay, so its short measurements ended less than a second after the page loaded. The delay pilot (ADR 0048) then showed Firefox's local histogram at N = 8 up to 32% slower and erratic without a delay: Firefox's own start-up work competed with the 8 workers for the 8 cores.

Why

Why this would have gone unnoticed. Firefox would have looked worse at scaling than it is, and the loss would have been attributed to WASM threads. The cause was not threads: the browser was still starting during the measurement.

  • Fix: every browser run waits 3 s before it creates the coordinating worker (the start delay), and records it with the run.
  • Left: native has no delay, a known asymmetry that does not change a speedup inside one environment; 3 s against 6 s differs by about 1% (Threats to validity).

30 runs, 10 iterations

Each configuration (one environment, one workload, one N) has 30 runs, each with 10 measured iterations (ADR 0047). The main campaign is 3 environments, 9 workload settings and 6 thread counts (N in {1, 2, 4, 6, 7, 8}), times 30: 4860 runs. With 450 runs of sequential code at one thread (Is the one-thread baseline fair?) it has 5310.

Why

Why 30, and not 5 or 100? More runs make the estimate more precise, but each costs machine time and the gain shrinks: from 5 to 30 the interval narrows a lot, from 30 to 100 only a little more. Thirty is the rule of the course, and a pilot checked that 30 gives the precision the questions need. More iterations per run would not help, because the variation is between runs, not inside them.

This is the precision that 30 runs give for the 10 primary comparisons. The half-width is how far the ends of the interval are from the estimate, as a percentage. These are the stricter 99.5% intervals of Ten decisions, a stricter bar.

Random interleaved order

The 5310 runs took 14 hours. Over that time a machine drifts: it warms up, a background job wakes, memory fragments. Suppose every native run came first and every Firefox run last. A slow change of the machine would fall on Firefox and not on native, and would look like a difference between the two environments.

Why

Why shuffle, and why with a seed? The campaign builds the full list of runs (every environment, workload, N and repetition) and shuffles it once, so native, Chrome and Firefox runs are mixed from start to end. Drift still happens, but it falls on all three alike: it becomes noise, which the intervals account for, and not a bias, which nothing would catch. The shuffle uses a recorded seed (2026112201 for the main campaign), so the same order can be rebuilt: a stopped campaign resumes at the position where it stopped, and anyone can reproduce the sequence (ADR 0034).

After the campaign, the data check looks for drift that remains: in each configuration, do the run values trend with the position of the run in the order? One of the 177 configurations shows a trend, about what chance alone produces. It is kept, and it is not one of the configurations of the ten primary comparisons.

In depth: the plan, the seed and the drift check

The drift check is Spearman's rho between the order position of a run and its value, flagged at |rho| above 0.5 with at least 10 runs. With 30 runs and no drift that happens by chance about 0.7% of the time, so about 1.2 of the 177 configurations are expected (ADR 0051).

Fork-join calibration

A parallel region has a cost of its own: the worker threads must be told that there is work, and the thread that asked must wait until all of them finish. That is the fork-join cost (Fork-join and its cost). To measure it, every run times a few parallel regions with nothing inside, before its warm-up (ADR 0030).

Why

Why measure it, if the time of the workload already includes it? Without a separate number, nothing tells a slow workload from a slow start. If the browsers scale worse on small images, is the parallel code slower, or is the fixed cost of each region larger? The calibration answers that. Nothing is subtracted from the measured times: the calibration describes, it does not correct.

Each run takes 20 samples of each of two kinds:

  • warm: back to back, so the workers are still awake and looking for work;
  • cold: each after a pause at least as long as the checksum of the workload, so the workers are asleep, as they are before every measured iteration. Cold minus warm is the cost of waking them.

At N = 8 the browsers pay about 110 µs (Chrome) and 60 µs (Firefox) against 7.9 µs natively. Against a filter iteration of several milliseconds that is negligible; against a small parallel region it dominates, which Cutoff: the smallest image worth threading measures.

In depth: the step at N = 8, the clock ticks and the code

All three environments step up at N = 8, likely because the coordinating thread then shares the 8 cores with N workers. Below N = 8 the browser values are one or two ticks of their coarse clocks (performance.now() steps by 5 µs in Chrome and 20 µs in Firefox), so a 0 there means "under one tick", not zero cost.

In depth: the empty broadcast, and how the calibration table is computed

The table is computed by scripts/explainer_data.py from the calibration rows of data/raw/campaign-v3: all 30 runs of every configuration, 270 per environment and N. broadcast runs an empty closure on every thread; par_iter is an empty parallel iterator.

In summary. A run is one fresh start of one program, and it gives one number. The same Rust code times the workload in all three environments; the harness differs only in how it starts the program (flags or a URL) and how the result reaches the disk (printed, or posted to a local server). Each configuration has 30 runs, each run discards its warm-up iterations, browser runs wait 3 s first, and the runs of the three environments are shuffled into one order.
