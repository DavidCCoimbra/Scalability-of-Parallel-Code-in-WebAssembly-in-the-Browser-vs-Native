Research questions and design

The study checks, with one source and under the same conditions, whether parallel code gains from threads in a browser as it does natively, and whether that changes when the threads share data. This page gives the two research questions, the design that isolates them, the vocabulary every file name and table column is made of, and what earlier studies measured.

Why this matters

More heavy work runs inside the browser every year: photo and video editing, document viewers, small machine-learning models. WebAssembly (WASM) lets the browser run compiled code almost as fast as a native program on one core. With shared memory, the same code can also use every core with threads.

If you move a parallel library to the browser, you need to know two things:

  • Do 8 threads still give close to 8 times the speed, or does the browser add costs that grow with the threads?
  • Does code whose threads coordinate (shared counters, locks, atomic operations) behave differently in the browser than natively?

Earlier studies measured WASM against native on one thread, or measured threads without a native baseline and without coordination as a factor (What others measured).

RQ1 and RQ2

RQ1. How do the speedup and efficiency of the same parallel code evolve with the number of threads, natively and as WASM in the browser?

RQ2. To what extent does synchronization between threads affect the gap between WASM and native found in RQ1?

Two terms carry the questions:

Speedup. How many times faster the program is with N threads than with one, in the same environment. If one thread takes 80 ms and eight threads take 10 ms, the speedup is 8. Divided by N it gives the efficiency: 8 / 8 = 1, the ideal. Ratios, speedup and intervals has more.

Synchronization. Anything that makes threads coordinate instead of working alone. Here it is one thing: many threads adding to the same shared counters, each add made atomic

so that no count is lost.

Each question has its own workload and its own measure:

  • RQ1 uses the Gaussian filter, whose threads never coordinate. Its speedup curve is computed inside each environment (native against native, Chrome against Chrome). If the browser only makes every thread equally slower, the curves have the same shape.
  • RQ2 uses the histogram twice: with shared atomic counters, and with counters that are never shared (the control). How much slower the shared version is in a browser is compared with how much slower it is natively.

Why

Why compare the two histograms, and not only time the atomic one? The browser makes everything a little slower, atomics or not. If the study timed only the atomic histogram, a slow browser would look like a browser with slow synchronization. Dividing by the local histogram first removes the general slowness, and what remains is the cost of sharing. The next section does it with numbers.

Why

Why fix the questions and tests before the data? With 162 configurations, something always looks "significant" if you look long enough. An analysis plan fixed the metric, the tests and the 10 comparisons that answer the questions before the campaign ran, so the data cannot choose its own questions (pre-registration, ADR 0037).

RQ2 with made-up numbers

The numbers below are invented to show the arithmetic; the measured ones are in RQ2: synchronization. Say the local histogram takes 1 s natively and the atomic one takes 2 s. Sharing costs 2 times natively.

Native

no sharing: 1 s

shared atomics: 2 s

sharing costs 2×

Browser A

no sharing: 2 s

shared atomics: 4 s

sharing costs 2×

Browser B

no sharing: 2 s

shared atomics: 8 s

sharing costs 4×

Both browsers are twice as slow as native at everything, which is a matter for RQ1, not RQ2. In browser A sharing costs 2 times, as it does natively: its RQ2 value is 2 / 2 = 1, no extra penalty. In browser B sharing costs 4 times: 4 / 2 = 2, synchronization costs it twice what it costs natively. A value below 1 means that sharing costs less in that browser than natively, which is what Chrome shows at k = 256.

In depth: the metric as the analysis plan writes it

Per environment, r = log(Tatomic) − log(Tlocal) at the same N and k. The RQ2 effect is exp(Δr) with Δr = r(browser) − r(native): the atomic/local time ratio in the browser over the same ratio natively. The logs make the ratios symmetric (2× and 0.5× are the same distance from 1) and let the bootstrap resample the four groups of 30 runs independently. The 10 primary contrasts are the four k at N = 8 for each browser (RQ2) and the filter's speedup ratio at N = 8 for each browser (RQ1), with Holm's correction over the ten (The RQ2 metric, Holm).

Vocabulary: environment, workload, N, k

The study has about fifteen terms of its own. They name the cells of the experiment, the measurements and the builds; the general ones (thread, cache, median) are in the Concepts pages.

Four choices name a cell of the experiment. Every run belongs to exactly one cell:

Environment

Where the code runs: native (a normal Linux program), chrome or firefox (the same code as WebAssembly inside that browser). The three names are the values of the env column in the data. Environments and builds.

Workload

What is timed: filter, hist-atomic (the histogram with shared atomic counters) or hist-local (per-task local counters, the control). The exploratory campaigns add hist-atomic-private, hist-atomic-packed and two sorts, and the main campaign adds the sequential references filter-seq and hist-seq. Workloads.

N

How many worker threads the run uses: 1, 2, 4, 6, 7 or 8 in the main campaign, never more than the 8 P-cores. The deciding comparisons are at N = 8; 6 and 7 show whether a curve bends before the last core is used (ADR 0044).

k

How many distinct grey levels the histogram's input has: 1, 4, 16 or 256. It sets how much the threads contend for the shared counters. The filter has no k; its input is noise. k: the contention dial.

Vocabulary: run, iteration, configuration, campaign

Run

One fresh start of the program, or of the browser, that times the workload and writes one CSV file. The run is the unit of analysis: 30 runs give 30 values, not 300. The run is the unit.

Iteration

One timed pass over the whole image inside a run. A run does warm-up iterations that are not counted, then 10 measured ones. The run's value is the median of the 10.

Configuration

One cell (environment, workload, k, N) with its 30 runs. The main campaign has 162 configurations (and 15 more for the sequential references); "the filter in Chrome at N = 8" is one of them.

Campaign

Every run of a whole experiment, run in one seeded random order and kept in one folder, data/raw/<name>/. The main one, campaign-v3, has 5310 runs. Run a campaign.

Primary and exploratory

The 10 comparisons that answer RQ1 and RQ2 are primary: they were fixed before the data and get a stricter bar. Every other campaign (the engine arms, the counters, weak scaling, SIMD, E-cores, cutoff, grain) is exploratory: reported with ordinary intervals, and labelled as such.

Pilot

A small early campaign used to pick a setting (how many warm-up iterations, the image size, the start delay), on an earlier build. Pilot numbers justify a decision; they are never reported as results.

Vocabulary: build, tag, variant

Build

The exact compiled program: one native binary and one WASM module from one version of the source. Two builds can differ in one machine instruction, which can change a timing, so runs of different builds are never mixed in one comparison.

Tag

A name for the exact version of the code a campaign ran: measured/v3 is the one every reported number comes from. Every run records the digests of the build, so you can trace a run to its code. Builds and tags.

Variant

A build made with other compiler flags for an exploratory question: scalar (no SIMD) and avx2 (wider native SIMD). The default build is baseline.

Vocabulary: the numbers

From the 30 values of a configuration the study reports:

  • TN: the time with N threads, the geometric mean of the 30 run values (An average that respects ratios says why).
  • Speedup SN = T1 / TN: how many times faster N threads are than one, each environment against itself. 8 is the ideal with 8 threads; below 1 means 8 threads are slower than one.
  • Efficiency = SN / N: the share of the ideal. 1 is the ideal; 0.5 means the threads are half idle on average.
  • Interval: the range the value would likely fall in if the 30 runs were taken again, computed with the bootstrap (How sure the result is).
  • Time ratio browser / native: the same question in seconds, because a speedup alone can hide a slow start (Speedup and efficiency).

What others measured

The table gives each source, what it measured and how this study differs. In short: others measured WASM on one thread, or threads without a native baseline, or atomics outside a browser. None put the same code, three environments, a thread sweep and synchronization as a factor in one controlled experiment.

In summary. RQ1 asks whether the same code gains from threads in the browser as it does natively; RQ2 asks whether sharing counters between threads changes that. Code, input, machine and order are held the same, and the analysis plan fixed the ten deciding comparisons before the campaign. A run is one program start and one value; environment, workload, k and N name its cell; 30 runs make a configuration; a campaign is all of them in one shuffled order on one tagged build.
