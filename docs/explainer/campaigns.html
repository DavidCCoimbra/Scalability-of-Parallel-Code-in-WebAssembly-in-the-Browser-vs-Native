Run a campaign

A campaign is one set of measurements decided in advance: which runtimes, which workloads, which thread counts, how many runs. It is written down as a JSON file, the spec, before anything runs, and the harness runs exactly that and nothing else.

In short: a spec fixes every parameter and a random seed, the harness turns it into a shuffled list of runs, and stopping and restarting never changes that list: it only continues it.

What a campaign is

A run is one program start that measures one configuration (one runtime, one workload, one thread count) ten times and writes a CSV. A campaign is a list of runs decided before any of them starts: every configuration the question needs, thirty times each, in a shuffled order. The list is written as a small JSON file, the spec, and the harness runs exactly that list.

An analogy. A clinical trial writes down, before the first patient, who gets what and in which order, then follows the sheet. Deciding as you go is how you end up measuring your own expectations. The spec is the sheet.

Why

Why shuffle, and why record the seed? A machine drifts over thirteen hours: it warms, a background job wakes, a cache fills. If every native run came first and every Firefox run last, the drift would look like a difference between native and Firefox. Shuffled, the drift falls on all three alike and becomes noise instead of a bias (A fair comparison). The seed is recorded so the same shuffle can be rebuilt and a stopped campaign continues the same list (Sessions and resume).

Why

Why thirty runs, and why a fresh process each time? One run can be unlucky; thirty give a spread you can see and an interval you can report. A fresh process each time makes the thirty independent: nothing one run warmed up or cached helps the next (The run is the unit, 30 runs, 10 iterations).

Sessions, status and resume

A campaign of thousands of runs takes hours (the main one about 13), so it must survive a stop: a crash, a reboot, a Ctrl-C. The harness never keeps state in memory that it cannot rebuild from the results folder.

  1. Plan. The spec and its seed give the same shuffled list of runs every time. Native, Chrome and Firefox are interleaved, so a slow drift of the machine falls on all three alike.
  2. Session. The first start writes campaign.json: the spec, the build identity (commit, the SHA-256 of the native binary and of the WASM module, the browser versions) and the plan. A later start is a new session: it checks that the spec and the build are the same and refuses otherwise, so one campaign never mixes builds.
  3. Skip what is done. For each planned run, in order, the harness looks for its files. A run with a result is skipped; a run with an .error.json counts as failed and is run again only with --retry-failed (the old files move to failed/).
  4. Log. Every run appends one line to campaign.jsonl: its id, configuration, status, duration and problems.

make status SPEC=... reads only campaign.json and campaign.jsonl, never the machine, so it is safe in a second terminal during a measurement. Its ETA is the mean duration of the logged runs times the runs left.

The data check

Why

Why check the data before looking at it? Because a person who has seen the result will find reasons to drop the runs that disagree with it. The check runs the same rules on every campaign, written before the first one (ADR 0051), and reports; it never decides what the answer is. A campaign it blocks is re-run or excluded with an ADR, not patched.

When a campaign ends, and before any statistic is looked at, python3 -m analysis.datacheck writes a short quality report (ADR 0051). It removes nothing: the analysis plan fixed in advance which runs are excluded (D7), and the check only says whether the data can be analysed.

Every campaign of the study

Every result in the paper and in this documentation comes from a campaign on the build tagged measured/v3 (commit ac65af6a; every campaign records the digests of the binaries it ran). The campaigns of the earlier build, measured/v2, are at the tag data/v2, valid for their own build, but builds are never mixed in one comparison (ADR 0062, 0095). Pilots only sized the design; their runs and specs are in data/earlier/pilot/.
