Run a campaign

A campaign is one set of measurements fixed in advance: environments, workloads, thread counts and repetitions, written as a JSON spec. This guide shows you how to run one, watch it, resume it after a stop, and read the data check that decides whether it can be analysed. Stopping and restarting never changes the list of runs; it continues it.

What a campaign is

A run is one program start that measures one configuration (one environment, one workload, one thread count) ten times and writes a CSV. A campaign is a list of runs fixed before any of them starts: every configuration the question needs, thirty times each, in a shuffled order. You write the list as a small JSON file, the spec, and the harness runs exactly that list.

Why

Why shuffle, and why record the seed? A machine drifts over fourteen hours: it warms, a background job wakes, a cache fills. If every native run came first and every Firefox run last, the drift would look like a difference between native and Firefox. Shuffled, the drift falls on all three alike and becomes noise, not a bias (A fair comparison). The seed is recorded so that the same shuffle can be rebuilt and a stopped campaign continues the same list (Sessions, status and resume).

Why

Why thirty runs, and why a fresh process each time? One run can be unlucky; thirty give a spread you can see and an interval you can report. A fresh process each time makes the thirty independent: nothing that one run warmed or cached helps the next (The run is the unit, 30 runs, 10 iterations).

From this spec the harness plans 3 environments × 9 workloads × 6 thread counts × 30 repetitions = 4860 runs, and the 5 sequential references at one thread (3 × 5 × 30 = 450): 5310 runs, plus the discarded first launches. A run id names one of them: campaign-v3-2666-chrome-filter-noise-n8-r27 is position 2666 of the order, Chrome, the filter on noise, N = 8, repetition 27.

Sessions, status and resume

A campaign of thousands of runs takes hours (the main one about 14), so it must survive a stop: a crash, a reboot, a Ctrl-C. The harness keeps no state in memory that it cannot rebuild from the results folder.

  1. Plan. The spec and its seed give the same shuffled list of runs every time, with native, Chrome and Firefox interleaved.
  2. Session. The first start writes campaign.json: the spec, the identity of the build (commit, the SHA-256 of the native binary and of the WASM module, the browser versions) and the plan. A later start is a new session: it checks that the spec and the build are the same and refuses if they are not, so a campaign never mixes builds.
  3. Skip what is done. For each planned run, in order, the harness looks for its files. It skips a run with a result. A run with an .error.json counts as failed, and runs again only with --retry-failed (the old files move to failed/).
  4. Log. Every run appends one line to campaign.jsonl: its id, configuration, status, duration and problems.

make status SPEC=... reads only campaign.json and campaign.jsonl, never the machine, so you can run it in a second terminal during a measurement. Its ETA is the mean duration of the logged runs times the runs left.

One journal line, for a discarded first launch:

The data check

Why

Why check the data before looking at it? A person who has seen the result finds reasons to drop the runs that disagree with it. The check applies the same rules to every campaign, written before the first one (ADR 0051), and reports; it never decides what the answer is. A campaign that it blocks is run again or excluded with an ADR, not patched.

When a campaign ends, and before you look at any statistic, python3 -m analysis.datacheck writes a short quality report. It removes nothing: the analysis plan fixed in advance which runs are excluded (D7), and the check only says whether the data can be analysed.

Every campaign of the study

Every result in the paper and in this documentation comes from a campaign on the build tagged measured/v3 (commit ac65af6a; every campaign records the digests of the binaries it ran). The campaigns of the earlier build, measured/v2, are at the tag data/v2. They are valid for their own build, and builds are never mixed in one comparison (ADR 0062, 0095). Pilots only sized the design; their runs and specs are in data/earlier/pilot/.
