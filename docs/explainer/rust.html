Rust for JavaScript developers

The measured code is written in Rust. If you write JavaScript, most of it will look familiar: functions, loops, objects with fields, arrays, callbacks. Three ideas are new, and they are the reason the study could run the same code on 8 threads without a single lock. This page gives those three ideas first, with tiny examples, and then every Rust construct the repository uses, each next to the nearest JavaScript or TypeScript you already know.

In short: Rust is a language where every value has one owner, where many parts of the program may read a value at once but only one may change it, and where the compiler refuses to build a program in which two threads could write the same memory, which is exactly the guarantee a parallel benchmark needs.

Three ideas

Everything else on this page is detail. These three are what you need to read bench/src/ and to see why the filter and the local histogram can run on 8 threads with no lock at all.

An analogy. A library book. One person has it checked out (the owner). Many people may read a photocopy at the same time, but nobody may write in the book while photocopies are out, and only one person at a time may hold the pen. Rust's compiler is the librarian: it refuses to let you leave with a plan that breaks those rules.

1. Every value has one owner

A value belongs to one variable. Give it to another and the first can no longer use it. No two places ever think they own the same thing, so nothing is freed twice or changed behind your back.

let a = Histogram::default();
let b = a;       // a moves into b
// a.merge(..)   // error: moved

2. Many readers or one writer, never both

You may lend a value out to be read (&) to as many places as you like, or lend it out to be changed (&mut) to exactly one place, but never both at the same time.

let r1 = &image;     // read
let r2 = &image;     // read, fine
let w = &mut image;  // error: r1, r2 live

3. The compiler refuses racy code

Those two rules are checked when the program is built, not when it runs. Hand each thread its own &mut row and no thread can touch another's row; try to share one &mut and the build fails. A data race cannot reach the benchmark.

rows.par_chunks_mut(1)   // own rows
  .for_each(|r| blur(r)); compiles
spawn(|| total += 1);     refused

Why

Why does the study care? RQ2 compares a histogram that shares counters with one that does not. If the "does not share" version secretly shared something, or the filter had a hidden race that sometimes produced a wrong pixel, every ratio in the paper would be measuring a bug. Rust makes the no-sharing claim a property the compiler proved, and the checksum of every iteration confirms it at run time (Inputs and checksums).

The rest of this page is a reference. Read it with bench/src/ open; every excerpt is read from the real file when the data file is generated, and the link in its header opens the file. The "Nearest TS" panels use TypeScript; where a TypeScript word is new, it is explained in one line.

Types, ownership, borrowing

struct and impl: data, and the functions that work on it

A struct is an object type: named fields, no methods. The methods come separately, in an impl block. Fields without pub are private to the file, like #field in a JS class. Vec<u8> is a growable array of bytes, here used like a Uint8Array. &self in a method is a read-only this.

Why: every domain concept is a named type, never a loose tuple (the project's style rule). A pixel buffer with a width and a pitch cannot be confused with any other array of bytes.

enum and match: a closed set of cases

An enum lists the only values a thing can be, and each case can carry its own data. In TypeScript the same idea is a union type (a value that is one of several shapes, told apart by a tag). match is a switch over the cases that refuses to compile if you forget one.

Why: environment, workload and input are closed sets with fixed names in the CSV. A typo in a name is a build error, not a mislabelled row in the data.

Option, Result and the question mark

Option<T> is "a T, or nothing": T | undefined. Result<T, E> is "a T, or an error E", but the error is an ordinary return value you can see in the type, not an exception that may or may not be thrown. The ? after a call means "if this failed, return the failure from my function now", which is what letting an exception bubble up does, written out. When run returns an error, the WASM bridge turns it into a thrown JS exception that the page's worker catches.

Why: a bad configuration must become a recorded error file, never a silent wrong measurement (ADR 0027).

Ownership and borrowing in the code: &, &mut and moves

RustMeaningClosest JS idea
&Tborrow, read-only; many may exist at oncea Readonly<T> reference (TypeScript's "you may look but not change")
&mut Tborrow, read-write; only one may exist, and no &T at the same timethe only reference to it
T by valueownership moves in; the caller can no longer use it"I take this, don't touch it again"

These are ideas 1 and 2 above, as they appear in the code. merge(mut self, other) takes both histograms by value, so it owns them, adds one into the other and returns the result with no copy. Because only one &mut to each output row can exist, two threads can never write the same row: the parallel filter is proved free of data races before it runs.

Why: it is what lets Rayon run the closures on 8 threads without locks in the filter and the local histogram.

Slices: a window onto someone else's bytes

&[u8] is a view (a start and a length) into bytes owned by someone else, like Uint8Array.subarray; nothing is copied. a..b is the range from a up to but not including b. Every index into a slice is bounds-checked, but when the compiler can see that all the slices have the same length it drops the checks and turns the loop into SIMD instructions.

Why: the filter reads three input rows and writes one output row without copying, and its inner loop must use SIMD on both sides (ADR 0017).

Closures, iterator chains and sized integers

|hash, &byte| ... is an arrow function, (hash, byte) => .... The iterator method fold(init, f) is reduce(f, init). Unlike JS, Rust integers have a size: u8 (a pixel, 0 to 255), u16 (the filter's sums), u64 (the counters), usize (an index). Going past the top is a bug by default; wrapping_mul says "wrap around on purpose", like BigInt.asUintN(64, ...).

Why: the FNV-1a checksum proves every environment computed the same output, and the SplitMix64 input generator must give the same pixels bit for bit everywhere.

Traits and generics

trait: what every workload must be able to do

A trait is an interface (a list of methods a type promises to have), which may also carry default bodies: prepare does nothing unless a workload overrides it. impl Workload for AtomicHistogram is implements, written outside the struct.

Why: the timed loop runs any workload without knowing which, so "only run is timed" is guaranteed in one place (ADR 0015).

In depth: trait objects, generics, derive, cfg and compile-time asserts

Trait objects: Box<dyn Trait>

Box<dyn Workload> is "some object on the heap that implements Workload", which is what every TS object reference already is; Rust needs the Box because the concrete types have different sizes. + Send means the value may move to another thread; JS has no equivalent, because JS objects never cross threads.

Generics and where

A generic is a function written once for any type that meets a condition. where W: Workload is W extends Workload. ?Sized lets W be a dyn Workload. Unlike TS, Rust compiles one copy per concrete type, so the generic costs nothing at run time.

Why: the same loop runs with the native clock and with performance.now() in the browser; only the clock is injected (ADR 0015).

derive, cfg and const

#[derive(...)] generates standard methods; Copy makes the value copy on assignment, like a JS number. #[cfg(...)] removes code at compile time, like a bundler's dead-code elimination on process.env.X, but the removed code is never type-checked or shipped; it selects the native or browser clock. A const _: () = assert!(...) makes the build fail if the check is false: here, that the kernel weights sum to 16 and that the largest weighted sum fits in a u16, so the 16-bit SIMD arithmetic cannot overflow.

Why: an integer kernel gives exactly the same output on every target (ADR 0012), and one source builds for two targets.

Rayon in the code

Rayon is the library that runs a loop on many threads. You write the loop as you would for one thread, change chunks_mut to par_chunks_mut, and Rayon hands the pieces to a pool of threads and waits for all of them (Rayon and work stealing).

par_chunks_mut and for_each: the filter

par_chunks_mut cuts the output into chunks of rows and hands them to the pool; for_each returns after every chunk is done, which is the join. Unlike Web Workers, there is no postMessage and no copy: all threads see the same memory, and the &mut rule guarantees each row is written by exactly one thread. grain.tasks lets the grain sweep fix the task size; the main campaign uses Rayon's adaptive split.

fold and reduce: the local histogram

fold(Histogram::default, f): each Rayon task starts with its own fresh, zeroed histogram (Histogram::default is passed as a factory) and counts its chunks into it; nobody else touches it, so no atomics. reduce then merges the partial histograms pairwise. The private copy is per task, not per thread (privatization, ADR 0013).

Why: this is the lock-free control of RQ2.

The thread pool and broadcast

A pool is a fixed set of threads that wait for work, like Web Workers created once and reused. It is built before the timed iterations, so its start-up is never measured. broadcast with an empty closure leaves only the cost of handing out work and waiting, which every run measures (Fork-join and its cost).

Why: N is the independent variable of RQ1, so the pool must have exactly N threads in every environment; pool::check refuses a run otherwise.

Atomics in the code

AtomicU64 and fetch_add

fetch_add reads, adds and writes as one indivisible step, an atomic operation. It takes &self, not &mut self: atomics are the one kind of value that may change through a shared reference, which is why all threads can share the table. The Ordering argument makes no difference on these targets; see Memory order.

In depth: static atomics, repr(align) and inline

Static atomics

A global. Rust forbids a plain mutable global, because any thread could race on it, so the global is an atomic; in WASM every worker of the pool shares this memory.

#[repr(align(128))] and #[inline]

repr(align(128)) starts every counter on a 128-byte boundary and pads it to 128 bytes, one counter per cache line and per prefetch pair (False sharing and padding). #[inline(always)] on increment keeps the locked add inside the per-pixel loop; #[inline(never)] on blur_interior keeps it a separate function with a stable name, so scripts/check_simd.py can find it in both disassemblies.

From Rust to WASM

wasm_bindgen: exports and imports

wasm-bindgen is the bridge between Rust and JavaScript. #[wasm_bindgen] on a function makes it an export of the generated pkg/bench.js, with strings and errors converted for you. The extern "C" block is the opposite direction, like a TS declare function: it lets Rust call performance.now.

Why: the browser page calls the same run path as the native runner, only through this bridge (ADR 0018).

In depth: the build flags and in-file tests

The build flags

Threads need the atomics target features, memory shared between workers and created by JS (--shared-memory --import-memory), and per-worker thread-local storage. The prebuilt standard library for wasm32 has no atomics, so it is rebuilt with these flags (-Z build-std, nightly only, pinned in ADR 0009). Native builds use the default x86-64 baseline. bench/build-wasm.sh then runs the pinned wasm-bindgen to write bench/www/pkg.

Tests in the same file

#[cfg(test)] compiles the module only for cargo test, like in-source tests in Vitest. Most files in bench/src/ end with one; make test-rust runs them, and bench/tests/golden_checksums.rs pins the output checksums, so a refactor that changes a result fails CI (ADR 0062).

In depth: Two things you might expect and will not find

Arc (shared ownership across threads): Rayon's closures only borrow data for the length of the parallel call, so nothing needs reference counting. rayon::join: not called directly; the parallel iterators use it internally to split work in halves.

In summary. One owner per value; many readers or one writer; and the compiler, not a test, is what guarantees no two threads write the same memory. Everything in bench/src/ that looks strange is one of those three rules written down.
