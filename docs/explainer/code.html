Repository tour

The repository holds three programs, in two languages, and each one has exactly one job. One does the work and times itself. One starts that work under controlled conditions and keeps what it produced. One reads what was kept and turns it into tables and figures. Knowing which of the three you are looking at tells you most of what a file is for.

In short: the code that is measured and the code that measures are separate programs that only talk through files, so the measurement can never slow down what it measures.

An analogy. A cooking contest. The cook (bench/) makes the dish and stops the clock. The referee (harness/) sets up the kitchen the same way for every cook, says "go", and writes the time on a card. The judge (analysis/) reads all the cards at the end and decides. The referee never stands in the kitchen while the cook works, and the judge never touches a pan.

bench/

Rust, compiled to native and WASM

The two workloads, the loop that times them, the checksum. The only code that runs while the clock is running. One source builds the native program and the browser's WASM module.

harness/

Python

Starts each run as a fresh process or a fresh browser, confined to the fast cores, and stores the CSV it produced next to a record of the conditions it ran in. Never measures anything itself.

analysis/

Python

Reads the stored runs, reduces each run to one number, computes speedups, intervals and the ten decisions, and draws the figures. Writes data/tables/ and paper/figures/.

Why

Why three programs and not one? If the timing code and the orchestration lived in one process, the orchestrator's own work (writing files, polling, logging) could run on the same cores at the same moment as a timed iteration and add to its time, and nobody could tell by how much. Keeping them in separate processes, on separate cores, with files as the only link, means a slow harness cannot make a workload look slow. How they are connected, process by process, is on How the pieces talk.

Crate. Rust's word for one buildable package of code with its own Cargo.toml. bench/ is one crate.

bench/

One Rust crate builds two things from the same source: the native program (src/bin/native) and the WASM library the browser page loads (src/wasm.rs, www/). Both end up calling the same function, run::run_in_pool, so the code inside the clock is identical in every environment. One run, start to end follows that call line by line.

Every workload is a small object that promises three things, the Workload trait: prepare runs before the clock starts, run is the only timed call, and checksum hashes the result afterwards. The timing loop only knows about these three, so it cannot time anything else by accident.

Why

Why so small an interface? Because "what exactly is inside the clock" is the question a reviewer asks first. With three methods there is one answer, in one file (measurement/measure.rs), for the filter, both histograms and every extra. A workload with a fourth, untimed step would have to say so in its prepare.

harness/

The harness never measures anything. It does three things: start each run in a controlled way (a fresh process, a CPU mask that keeps it on the fast cores, a run scope that groups its processes), store what the run produced together with a record of the conditions, and join the stored runs into one table for analysis/.

Why one function for both? RQ1 compares browser against native. If native runs were confined one way and browser runs another, part of any difference could be the confinement, not the runtime. One function, one argument list, no second code path to drift.

analysis/

Each file at the top of analysis/ is a command you run as python3 -m analysis.<name>; the folders under it are the library those commands share. The statistics were fixed in an analysis plan before the main campaign ran (ADR 0037), so the code has few knobs: it does what the plan says.

Two choices shape every number it produces: each run becomes one value, the median of its measured iterations; then the runs of a configuration become one centre, their geometric mean. Reading the numbers says why, in plain words.

Why

Why fix the statistics before seeing the data? With 30 runs and a dozen possible summaries, there is nearly always one that makes a wished-for difference look real. Writing the rules down first, and keeping them in a file CI checks, removes that choice. A reviewer can read the plan and the code and see they match.

Style rules and why

These are the rules in CLAUDE.md ("Code style") that every file follows. Each one exists because of a specific way the study could have gone wrong; make lint and CI enforce the ones a machine can check.

Comments only when they add information

A comment says why, warns of a pitfall, or points to the paper, algorithm or ADR a value comes from. Never a comment that repeats the code.

Why

What goes wrong otherwise. A comment that restates the line drifts the first time the line changes, and then it lies. A comment that says "128, because the prefetcher pairs lines (ADR 0008)" tells the next reader the one thing the code cannot.

Named constants, no magic numbers

CHUNK_BYTES, CACHE_LINE_BYTES, BOOTSTRAP_RESAMPLES, each defined once with its source.

Why

What goes wrong otherwise. The number 65536 appears in the atomic histogram and in the local one. Change one and not the other, and the two histograms no longer split the image the same way: the RQ2 control stops being a control, and no test says so.

A README with a diagram per module

What the module does, which file holds what, and a Mermaid flowchart of the flow.

Why

What goes wrong otherwise. The harness has nine folders. Without a map a newcomer changes the launcher when the bug is in the server, or adds a second place that writes result files. The README is the map, and it is next to the code so it is updated with it.

Python: one concept per module, fully typed, mypy strict

One class or idea per file; every function typed; mypy --strict passes; the standard library where possible (matplotlib is the one exception, run through uv).

Why

What goes wrong otherwise. The analysis turns 150,000 CSV rows into 10 decisions. A function that silently gets a string where it expected a number, or a list where it expected a run, produces a wrong table that still looks like a table. Strict types make that a build error. The standard library rule means the numbers can be recomputed anywhere, with no version of anything to match.

Rust: one struct or impl per file, strong types, clippy clean

Domain concepts are their own types (ThreadCount, WorkloadKind), never loose tuples; rustfmt and clippy with -D warnings.

Why

What goes wrong otherwise. Passing (8, 1) where (1, 8) was meant is one swapped argument and a whole campaign at the wrong N. A ThreadCount cannot be handed to a parameter that wants a K. One struct per file also means the excerpts on these pages can point at one small, stable file.

The measured code is guarded

The timed region, the kernels and the checksum change only with an ADR that says why, and a codegen diff (scripts/codegen_diff.sh) that shows whether the machine code changed. A change that is not codegen-neutral makes a new tagged build, and runs from different builds are never mixed in one comparison (ADR 0062).

Why

What goes wrong otherwise. A harmless-looking tidy-up of a loop can let the compiler unroll it differently, and the time per pixel moves by a few percent. If half the runs of a campaign came from before the tidy-up and half from after, the comparison would be between two programs, not two runtimes. Touching the measured code walks through the procedure.

In summary. Three programs: the cook, the referee, the judge. The cook (bench/) is the only one inside the clock, and changing it is a procedure, not an edit. Everything else is Python that can be changed freely as long as the types and the tests pass.

How the pieces talk

The project is three programs in three languages that never run inside each other. A Rust program does the measuring. A Python program starts it, hundreds of times, in a controlled way. A second set of Python programs reads what was written and turns it into tables. They talk through files, one web request and one command line. This page is the map of those hand-offs.

In short: make starts the Python orchestrator, which starts one fresh process per run (the native binary, or a browser), the run writes a CSV of times (to its standard output, or by posting it to a tiny local web server), the orchestrator writes the context next to it, and the analysis reads only those files.

Why

Why so many separate programs, and not one? Because the thing being measured must not be the thing doing the measuring. If the orchestrator lived inside the benchmark, its own work (planning, writing files, waiting) would be inside the timed region, and worse, it would be inside it differently natively and in a browser. So the Rust code times only itself, and everything around it is another process on other cores (Shield and quiet mode). The price is that the pieces have to agree on formats, and that is what this page lists.

An analogy. A lab with a stopwatch inside the experiment, a technician who sets up each trial and writes the label, and an analyst who only ever sees the labelled sheets. The technician never touches the stopwatch; the analyst never enters the lab.

Query string. The part of a web address after the ?: pairs of name=value joined by &. The page reads it to know what to measure, the same way the native program reads its command line. One parser in the Rust code reads both (same source, same flags).

Why

Why does the browser post the result instead of saving a file? A web page cannot write to disk. So a tiny web server (harness/server.py) serves the page and accepts the result back; it is also what sends the two headers that let the page use shared memory (What WASM threads need). It listens only on 127.0.0.1, the machine itself, never the network.

Who starts whom

  1. You type make campaign SPEC=.... make builds the right variant, turns quiet mode on, and starts the orchestrator under systemd-inhibit so the PC cannot sleep.
  2. The orchestrator (harness.campaign) reads the spec, shuffles the runs with the spec's seed, checks the machine (strict campaigns), writes campaign.json, and starts the results server once for the whole campaign.
  3. Per run, it starts one fresh process in its own systemd scope: the native binary, or Chrome or Firefox with a fresh profile. It waits for the CSV (standard output, or the server), then writes the JSON.
  4. The run starts its thread pool, warms up, times its rounds, writes the CSV, and exits. A browser run is a page and a coordinating worker; the pool is more workers started by the page (A browser run).
  5. After the last run, the orchestrator stops the server, prints the counts, and make turns quiet mode off.
  6. Later, by hand, make results runs the analysis commands over the folder.

Nothing is kept in memory between runs that cannot be rebuilt from the folder, which is why a campaign can be stopped and continued (Sessions, status and resume).

On the Mac and on the PC

On the Mac

Every box runs, but with no CPU mask, no scope, no machine check ("strict": false specs, make quick-*). The pieces talk exactly the same way, so a change to a format shows up here first. The times are not results.

On the PC

The same boxes, plus the ones that hold the machine still: the shield keeps everything but the run off the 8 measured cores, each run gets its own scope so its CPU time and any escaped browser process are counted, and a strict campaign refuses to start if any of that is missing (Checked on every run).

In summary. Three programs, four hand-offs: a spec path, a command line or URL, a CSV, a JSON. The Rust code never knows about campaigns; the analysis never knows about browsers. Change a format in one place and look for the two readers of it.

Where to find things

Two lookup tables, for when you know what you are looking for but not which file holds it. The first answers "where in the code is this done?" with the file to open and the page that explains it. The second starts from something that went wrong ("the campaign refuses to start", "a checksum conflict") and says which check caught it and where to look.

In short: every part of the study has one home in the code, and every failure is caught by a named check; these tables map both.

An analogy. The index at the back of a textbook, and the troubleshooting page at the back of a manual. Neither explains anything; both tell you which page does.

Type a word in the box to filter both tables. Rows whose name uses a technical term carry a one-line gloss under it; the glossary and the linked page have the rest.

Where is it done?

Something broke: where to look

Most failures stop a run or a campaign with a message, on purpose: a run that would give a wrong number fails instead, and is counted. Tests run with make test (Rust, Python) and make lint; CI runs both on every PR. For the step-by-step, from make status to re-running one id by hand, see Debugging a run.

Why

Why does so much fail on purpose? A benchmark's worst outcome is not a crash but a wrong number that looks right. A run at the wrong N, on the wrong cores, or with a wrong checksum would sit in the table like any other and move a result. So every check that can tell refuses the run, writes an error file, and the data check counts it; nothing is dropped quietly.

In summary. If you are asking "where is X", the first table has the file and the page. If you are asking "why did it stop", the second table names the check, and the check is on your side.
