Introduction

This is the documentation of an empirical study: the same parallel Rust program is run as a native Linux program and as WebAssembly with threads in Chrome and in Firefox, and timed with 1 to 8 threads. This page says what the study asks, what it found, and where to read next.

What the study asks

A web page can run compiled code on several cores. The study checks whether that code gains from extra threads the way the native program does, with everything else held the same: one source, one compiler, the same flags, one machine.

  • RQ1. How do speedup and efficiency evolve with the number of threads for the same code, natively and as WebAssembly in the browser?
  • RQ2. To what extent does synchronization between threads change the gap found in RQ1?

Two workloads answer them. A 3x3 image filter splits the image into rows and never makes two threads wait for each other. An image histogram is built twice: once with counters that every thread shares (atomic counters), once with private counters merged at the end. The difference between the two histograms is the cost of sharing. The input sets how many counters the pixels are spread over, from 1 to 256, which the study calls k.

Every configuration is run 30 times, each run in a fresh process, in one shuffled order. Research questions and design has the full design.

What it found

RQ1: browser threads scale like native threads

With enough work per parallel region, the filter gains from 8 threads in the browsers as it does natively. The browser is slower by a constant factor per thread, and that factor does not grow with the thread count.

Firefox scales slightly better than native. That is not because it runs threads better: its loop is slower, and eight slower loops ask less of the memory they share. RQ1: scaling has the curves and What explains the results the evidence.

RQ2: synchronization changes the gap, and the engine decides how

The number below is the cost of sharing in the browser divided by the cost of sharing natively, with 8 threads. 1 means the browser pays what native pays; 2 means twice as much.

Chrome pays more than twice the native cost when every thread hits one counter, and less than half when the counters are spread out. Firefox never pays more than native. The cause is one choice of instructions: Chrome's optimizing compiler adds to a shared counter with a read and a compare-and-swap that retries, where native code and Firefox use one locked add. A native program rewritten to add Chrome's way gets Chrome's times in both directions. RQ2: synchronization has the contrasts and the test.

Measured twice

The study was measured on two builds of the program. The rules for the second measurement were written before it started, and all ten primary decisions came out the same. The session of a build tells that story, and Threats to validity lists what the results cannot establish.
