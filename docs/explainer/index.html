Start here

A web page can now run the same kind of heavy code a desktop program runs, and it can use several of the computer's cores to do it. This study asks a simple question about that: when the same program runs inside Chrome, inside Firefox, and directly on the computer, does adding more cores help each of them the same way?

In one sentence: same source, same compiler, same settings, same machine, three places to run: every difference we measure comes from where the code runs, not from the code.

The study in a story

Imagine one recipe and three kitchens. The recipe is a small program written in Rust, a language that can be turned both into a normal desktop program and into WebAssembly, the form a browser can run. The three kitchens are the computer itself ("native"), Chrome and Firefox. We give each kitchen the same two dishes to make, first with one cook, then with two, four, up to eight, and we time every attempt.

The first dish is an image blur. Cut the picture into strips, one strip per cook, and nobody has to talk to anybody. If eight cooks are not close to eight times faster here, it is the kitchen's fault.

The second dish is an image histogram: count how many pixels there are of each shade of grey. Done the obvious way, every cook adds to the same shared tally sheet, and cooks keep bumping into each other. Done the careful way, each cook keeps a private tally and they add them up at the end. The difference between the two ways is the cost of cooks waiting for each other, what programmers call synchronization. We can make the bumping worse or better by giving the picture fewer or more shades of grey.

Every attempt is repeated thirty times from a cold start, in a shuffled order, on one computer prepared so that nothing else disturbs it. From the times we ask two things:

  • RQ1. Does the browser gain as much from extra cores as the native program does?
  • RQ2. Does waiting for each other cost more in the browser than natively?

What we found, in words

RQ1. Yes, when each cook has enough to do. On the blur, Chrome and Firefox gain from eight cores almost exactly as much as the native program does (Firefox even a little more, not because its cooks work together better but because each of them is slower, so together they crowd the pantry less). The browser is a fixed amount slower at everything, like a kitchen with a slightly longer walk to the stove, but that amount does not grow as cooks are added. What does cost the browser more is handing out the work and collecting it, which only matters when each piece of work is tiny.

RQ2. It depends on the browser. In Firefox, waiting for each other costs the same as natively, or less. In Chrome it costs more when everyone crowds one tally, and, surprisingly, less when the tallies are spread out. The reason turned out to be in the machine instructions Chrome's engine chose for "add one to the shared tally": a "try, check, try again" loop where the others use a single step. We counted the retries happening, and then tested it: a normal program rewritten to add Chrome's way gets Chrome's times, slower on one tally and faster on many.

We also hit, and fixed, three traps of measuring inside a browser: Chrome quietly used cores it was told not to; Firefox's slow start made short runs look slow; and a browser we had pinned to one version updated itself in the middle of the work. And we measured the whole study twice, on two copies of the program, with the rules for the second time written down before it started: every answer came back the same (The session of a build).
