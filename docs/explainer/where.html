Where is it done?

Two lookup tables, for when you know what you are looking for but not which file holds it. The first answers "where in the code is this done?" with the file to open and the page that explains it. The second starts from something that went wrong ("the campaign refuses to start", "a checksum conflict") and says which check caught it and where to look.

In one sentence: every part of the study has one home in the code, and every failure is caught by a named check; these tables map both.
Picture it. The index at the back of a textbook, and the troubleshooting page at the back of a manual. Neither explains anything; both tell you which page does.

Type a word in the box to filter both tables. Rows whose name uses a technical term carry a one-line gloss under it; the glossary and the linked page have the rest.

Something broke: where to look

Most failures stop a run or a campaign with a message, on purpose: a run that would give a wrong number fails instead, and is counted. Tests run with make test (Rust, Python) and make lint; CI runs both on every PR. For the step-by-step, from make status to re-running one id by hand, see Debugging a run.

Why does so much fail on purpose? A benchmark's worst outcome is not a crash but a wrong number that looks right. A run at the wrong N, on the wrong cores, or with a wrong checksum would sit in the table like any other and move a result. So every check that can tell refuses the run, writes an error file, and the data check counts it; nothing is dropped quietly.
What to remember. If you are asking "where is X", the first table has the file and the page. If you are asking "why did it stop", the second table names the check, and the check is on your side.
