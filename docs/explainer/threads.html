Thread pools and fork-join

One worker takes an hour; eight workers should take about eight minutes. The catch is that handing out the pieces and collecting them back takes time too, and that time is the same whether the job is big or tiny. This page is about that handing out and collecting: what a thread is here, how the browser gets them, and how much the start and the finish of a parallel job cost in each runtime.

In short: a WASM thread is a Web Worker running the same module on the same shared memory, and the fixed price of starting and joining a parallel region is what separates the runtimes when the work is small.

Threads and Web Workers

A thread is one line of work inside a program; several threads of the same program share the same memory, so they can all read the same image and write their own rows of the output without copying anything. Natively, the program asks the operating system for threads and gets them.

A web page cannot ask for threads. What it has is the Web Worker: a second script that runs at the same time as the page, but in its own memory, talking to the page by sending messages (which copies the data). That is fine for small messages and useless for sharing a 67-million-byte image.

An analogy. Native threads are eight cooks in one kitchen, all reaching into the same fridge. Plain Web Workers are eight cooks in eight kitchens who can only pass each other notes under the door. A WASM thread is a cook in a separate kitchen who nevertheless shares one fridge with the others, because the building was built with a special permit for that.

The permit is a SharedArrayBuffer: one block of memory that several workers can see at once. The WebAssembly module's memory is one of those, so N workers running the same module on it behave like N threads of one program. The three kinds side by side:

Rayon and work stealing

Rayon is the Rust library that runs loops in parallel. You write almost the same loop as before, and Rayon splits the work across its threads. In the blur, the loop runs over the rows of the output; Rayon hands groups of rows to the threads, and the loop only finishes when every row is done. That final wait is the join, like await Promise.all(...) over a set of workers.

In depth: the filter's parallel region

Rayon does not cut the job into exactly N equal pieces and hope they finish together. It keeps splitting the work in halves, every thread keeps a pile of pieces, and a thread whose pile runs out steals half of another thread's pile (work stealing).

Why

Why steal instead of dividing evenly? Because the threads do not run at the same speed: one core of this PC is slower than the others, the browser's own threads borrow time from some cores, and some rows may be cheaper than others. With fixed shares, everyone would wait for the slowest. With stealing, the fast threads finish their pile and take over part of the slow one's, and the load balances itself. It is also why the study never ties a thread to a particular core: the browser could not, and Rayon does not need it.

Fork-join. The shape of every parallel call here: fork (wake N threads and give them work), compute, join (wait for the last one). The caller continues only after the join.

Fork-join and its cost

Waking eight threads, giving them work and waiting for the last one is not free, and the price does not shrink when the job is small. A parallel region that does almost nothing still pays it in full.

The study measures this cost in every run, with a parallel region that does nothing, and reports it per environment and thread count. The run protocol says how it is measured, RQ1: scaling has the values, and Exploratory campaigns shows it next to the work of a region, for a large and a small image.

Grain size

Inside one region, the work is cut into tasks, and a task has a small cost of its own: putting it on a pile, taking it off, stealing it. Cut too fine and those small costs add up; cut too coarse and some threads sit idle at the end with nothing left to steal. The best size is in the middle.

There are two costs on two scales: the fork-join is paid once per region, the task cost once per task inside a running region. The study sweeps the task size, reports the best one per workload and environment, and compares it with Rayon's own automatic splitting in Exploratory campaigns.

In summary. In the browser a thread is a Web Worker on shared memory. Starting and joining a parallel region has a fixed price, 7 to 12 times higher in the browsers than natively at 8 threads; it is a few percent of a big job and most of a tiny one. That is why the main campaign uses a big image, and why a separate campaign measures where parallelism stops paying.
