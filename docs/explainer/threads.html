Thread pools and fork-join

A parallel program hands work to several threads and waits for them to finish. Handing out and collecting takes time, and that time is the same whether the work is large or small. This page explains what a thread is in WebAssembly (a Web Worker on shared memory), how Rayon splits work and steals it, what a fork-join costs, and what the size of a task changes.

Threads and Web Workers

A thread is one line of work inside a program. The threads of a program share its memory, so they can all read the same image and write their own rows of the output without copying anything. Natively, the program asks the operating system for threads.

A web page cannot ask for threads. It has the Web Worker: a second script that runs at the same time as the page, in its own memory, and talks to the page through messages, which copy the data. That works for small messages and not for sharing an image of 67 million bytes.

Native threads are eight cooks in one kitchen who reach into the same fridge. Plain Web Workers are eight cooks in eight kitchens who pass notes under the door. A WASM thread is a cook in a separate kitchen who shares one fridge with the others.

The shared fridge is a SharedArrayBuffer: one block of memory that several workers see at once. The memory of the WebAssembly module is one of those, so N workers that run the same module on it behave like N threads of one program. The three kinds side by side:

Rayon and work stealing

Rayon is the Rust library that runs loops in parallel. You write almost the same loop as before, and Rayon splits the work across its threads. In the filter, the loop runs over the rows of the output: Rayon hands groups of rows to the threads, and the loop ends when every row is done. That final wait is the join, like await Promise.all(...) over a set of workers.

In depth: the filter's parallel region

Rayon does not cut the work into N equal pieces. It keeps splitting the work in halves, every thread keeps a queue of pieces, and a thread whose queue runs out steals half of another thread's queue (work stealing).

Why

Why steal instead of dividing evenly? The threads do not run at the same speed: the browser's own threads take time from some cores, and some rows may be cheaper than others. With fixed shares, every thread would wait for the slowest. With stealing, a fast thread finishes its queue and takes part of a slow one's, and the load balances itself. It is also why the study never pins a thread to a core: a browser cannot, and Rayon does not need it.

Fork-join. The shape of every parallel call here: fork (wake N threads and give them work), compute, join (wait for the last one). The caller continues only after the join.

Fork-join and its cost

Waking eight threads, giving them work and waiting for the last one takes time, and that time does not shrink when the work is small. A parallel region that does almost nothing still pays it in full.

The study measures this cost in every run, with a parallel region that does nothing, and reports it per environment and thread count. The run protocol says how it is measured, RQ1: scaling has the values, and Exploratory campaigns shows it next to the work of a region, for a large and a small image.

Grain size

Inside one region, the work is cut into tasks, and a task has a small cost of its own: queueing it, taking it, stealing it. Cut too fine and those costs add up; cut too coarse and some threads sit idle at the end with nothing left to steal. The best size is in between.

There are two costs on two scales: the fork-join is paid once per region, the task cost once per task inside a running region. The study sweeps the task size, reports the best one per workload and environment, and compares it with Rayon's own automatic splitting in Exploratory campaigns.

In summary. In the browser a thread is a Web Worker on shared memory. Starting and joining a parallel region has a fixed cost, which is small next to a large region and most of a small one. That is why the main campaign uses a large image, and why a separate campaign measures where parallelism stops paying.
