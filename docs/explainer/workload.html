Add a workload

A workload is one Rust struct that implements a small trait. This guide takes you from the struct to a measured campaign: write the kernel, name it in the bench and in the harness, check it in the browsers, give it a campaign spec, and add its analysis.

The trait

Every workload implements Workload: prepare runs outside the timed region, run inside it, and checksum hashes the result.

Write and register the workload

  1. Write it in bench/src/workloads/, one struct per file. Keep allocation in prepare or in the constructor.
  2. Name it in WorkloadKind (bench/src/experiment/workload_kind.rs): the enum variant, its string name, its capabilities (whether it repeats identically for passes, whether it takes a grain) and its line in build_with.
  3. Mirror the name in the harness: the Workload enum of harness/campaign/workload.py and its capabilities in harness/campaign/capabilities.py, so that a spec can name it and the harness can refuse what it cannot do.
  4. Give it a checksum of its final result. Two environments or two thread counts that give different checksums are wrong, and analysis.datacheck blocks the analysis.
  5. Add it to the CI cases in harness/browser_check/cases.py. CI runs every listed workload small in headless Chrome and Firefox and compares the checksums with native. A workload that is not listed is not checked in a browser.
  6. Add a quick spec (harness/campaigns/quick-*.json and a make quick-* target), so that anyone can watch it run on a laptop in a minute.
  7. Run the checks.
make test
bash scripts/codegen_diff.sh measured/v3

Warning

Keep allocation out of run. The default WASM allocator takes a global lock, and a lock inside the timed region is a synchronization cost that is not the one under study. A WASM run whose memory grows during the measured phase fails.

Warning

A new workload can change the machine code of an existing one, for example by adding a second caller to a function that was inlined (ADR 0086). Run the codegen diff; if a hot function of a measured workload changed, you have a new build (Change the measured code).

Give it a campaign

  1. Copy the closest spec in harness/campaigns/. Give it a new name (the results folder) and a new orderSeed (any integer; it is recorded, so the order can be rebuilt). Campaign spec format lists every key.
  2. Keep the protocol unless the question needs otherwise: 30 repetitions, the P-core mask, the warm-up per workload, "strict": true on the PC. A changed protocol value is a design decision: write the ADR first (When a decision needs an ADR).
  3. Add a row to harness/campaigns/README.md with its ADR. For a sequence of specs, add a target in make/campaign.mk like cutoff-campaigns.
  4. Try it small first: a quick- copy with 3 repetitions and a 4096 x 4096 image, on any machine.
  5. Measure on the PC, with nothing else running on it (Run a campaign).
  6. Add the results target in make/results.mk: the data check first, then the tables into data/tables/<name>/. Add it to all-results.
make env-setup
make campaign SPEC=harness/campaigns/<name>.json
make status SPEC=harness/campaigns/<name>.json

Why

Why a file and not command-line flags? The file is committed. Months later the spec says exactly what ran, the harness stores it in campaign.json next to the runs, and a restart checks that nothing in it changed (Sessions, status and resume). A flag typed in a terminal is gone when the terminal closes.

Add its analysis

  1. A command is a top-level module in analysis/, run as python3 -m analysis.<name> data/raw/<campaign> --output .... The statistics it uses live in the subpackages (stats/, scaling/, inference/). Reuse them: the bootstrap, Holm and the run summaries are there, with the seed and settings the analysis plan fixed.
  2. Read the raw folder through analysis.loading.load_campaign, never the CSVs by hand: it applies the same exclusions as every other table (ADR 0081).
  3. Write a CSV table and, for a statistic with settings, a .json sidecar with the settings and the commit (Reproduce the tables and figures).
  4. Add a unit test in analysis/tests/ on a small made-up campaign, a row in analysis/README.md, and the command in a make *-results target.
  5. To show the table in this documentation, run make explainer: it picks up every CSV in data/tables/*-v3/ (The numbers of this documentation).

Note

A new analysis is exploratory. The analysis plan (ADR 0037) fixed the tests, the ten primary contrasts and the exclusions before the campaign; with 162 configurations and many statistics to choose from, something always looks significant by chance (Ten decisions, a stricter bar).

In summary. Add a workload through the trait and the two name lists (bench and harness), check it in the browsers through the CI cases, measure it through a committed spec, and analyse it with a command that reuses the plan's statistics.
