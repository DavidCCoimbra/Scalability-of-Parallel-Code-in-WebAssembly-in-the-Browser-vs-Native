Problems found and fixed

A benchmark can be wrong without anything looking wrong: every run finishes, every checksum matches, and the numbers look plausible. Each problem on this page is of that kind. They are part of the results because anyone who benchmarks a browser will meet them.

In one sentence: telling a browser which cores to use, giving it a fresh profile and installing a fixed version are not enough to confine it, quiet it and freeze it; and a review of our own measured code found two asymmetries, fixed in the build measured/v3.
Pilot numbers on this page. The numbers that found these problems come from pilots run before the campaigns. They justify the fixes; they are not results of the study.

Each problem is told the same way: what happened, why it would have fooled us, the fix, and the check that now catches it.

Chrome escapes the CPU mask

Every run is told to use only the 8 fast cores (a taskset mask), inside its own systemd scope, a box the operating system keeps the run's processes in. During the pilot, a sampler that checked where every thread was allowed to run found that Chrome's main process had moved itself out of the box: through the session bus it asked the system for a box of its own, in the user's area, and ran on the slow cores, outside the mask. Firefox's processes stayed in (ADR 0045).

Why this would have fooled us. Chrome would have had the 8 fast cores for its workers plus extra cores for its own housekeeping, and Firefox would not. A difference between the two browsers would then have been partly a difference in how many cores each really had, and we would have read it as a difference between the engines.
  • Fix: the harness launches the browsers without the session bus address. Without it, every Chrome process stays in the run's box.
  • Check: every run records escapedProcesses, the browser processes found outside the box, and strict validation rejects any run where it is not 0.

Firefox's start-up

A browser keeps working for seconds after the page has loaded: it compiles code, loads components, starts services. The warm-up pilot ran with no delay, so its short measurements ended less than a second after the page loaded. The delay pilot (ADR 0048) then showed Firefox's local histogram at N = 8 up to 32% slower and erratic without a delay: Firefox's own start-up work was competing with the 8 workers for the 8 cores.

Why this would have fooled us. Firefox would have looked worse at scaling than it is, and the loss would have been blamed on WASM threads. The cause had nothing to do with threads: it was the browser still starting up during the measurement.
  • Fix: every browser run waits 3 s before it creates the coordinating worker (the start delay), recorded with the run.
  • Left: native has no delay, a known asymmetry that does not change a speedup within one runtime; 3 s against 6 s differs by about 1% (Threats).

A pinned Firefox updates itself

The study pins Firefox 158.0, downloaded from Mozilla's archive, and the fresh profile turns automatic updates off. On 2026-11-10, between two exploratory campaigns, the installed Firefox updated itself in place to 160.0 anyway. Only the enterprise policy DisableAppUpdate stops it (ADR 0071).

Why this would have fooled us. Two campaigns meant to compare the same Firefox would have compared two different ones, with whatever changed in the engine between them mixed into the result.
  • Caught: strict validation checks the browser version of every run, and rejected all 2640 affected exploratory runs.
  • Fix: the installer writes the policy and reinstalls a moved install, and a campaign refuses to start when a browser is not the pinned version.
  • Repeated: the 2640 runs were repeated on 158.0, in one block after native and Chrome rather than interleaved. Four cells shared with the main campaign control the block: their time ratios to it average 1.000 to 1.001 in every environment, with the same spread as the interleaved ones.

Our own asymmetries: the v2 build

After the first campaigns, a review of the measured code against the textbook, the cited papers and the lectures found two asymmetries the study had caused itself (ADR 0069):

  • A safety check only on one side of RQ2. The shared-counter histograms indexed a table whose length the compiler did not know, so every pixel paid a bounds check (compare and branch) that the local control did not. The atomic/local ratio therefore included code that only the atomic side ran, and that the engines might compile differently from LLVM.
  • Final work timed in some variants only. The local histogram's merge was inside the timed region; the private merge and the read-back of the shared counters were outside it.
Why this would have fooled us. RQ2 is a ratio of ratios, and it only cancels what is the same on both sides. A check that ran on one side only, or a merge timed on one side only, would have been read as a cost of synchronization in every engine.

The fix: fixed-size counter tables (no per-pixel check; LLVM then unrolls the loop by 8 itself), and every histogram's timed run now ends with its final histogram. The checksums did not change.

Then every reported campaign was re-run on the corrected build, tagged measured/v3. Every number in this guide comes from it; the earlier build's campaigns are not reported as results.

If you already know this: why builds are never mixed

Builds are never mixed in one comparison because a change in code layout alone, with the same instructions, can change timing by a few percent (Mytkowicz et al. 2009). A refactor of the measured path is accepted only when a codegen diff shows the hot functions unchanged; otherwise it is a new build with a new tag, and earlier campaigns stay valid only for their own build (ADR 0062, Touching the measured code).

What to remember. Confining, quieting and freezing a browser each needs its own check, not just its own setting; and a ratio only cancels what is truly the same on both sides. Every one of these is now checked on every run.
