What explains the results

A measurement tells you what happened: the filter gets 7 times faster with 8 threads, Chrome pays twice for a shared counter. It does not tell you why. This page is about the why. The study listed nine things it had seen and could not yet explain, wrote down a guess for each, wrote down what a test would show (a prediction) if the guess were right and if it were wrong, and only then ran the tests. The predictions were written after the main campaign, which is what raised the questions, and before each test.

In short: of nine open questions, the tests answered three, supported four, explained one through another, and left one open; no answer changes a result, each one says how far the explanation of a result can be trusted.

How an explanation is tested

It is easy to explain a number after you have seen it. Any story fits. The discipline that makes a story worth something is to say before the test what the test should show, so that the story can lose.

The three words mean different things, and the difference is the whole point:

  • Answered: the test changed one thing and the effect followed it. That shows a cause.
  • Supported: several independent measurements agree with the guess, but none of them changed only the thing in question. The guess is the best reading; it is not proven.
  • Not supported: the test showed what the "if wrong" column said. The guess is dropped and the question stays open.

Why

Why not just say "we think it is the memory"? Because a reader cannot tell a tested explanation from a plausible one unless the text says which is which. If every explanation were written in the same confident voice, the one that was only a guess would be believed as much as the one that was proven, and the first person to check it would stop trusting all of them.

Note

None of this is a result of the study. The results are the ten contrasts on RQ2: synchronization, decided by a plan fixed before the data. Everything on this page is exploratory: it explains those results, it does not add to them.

Question 3: why the browser is slower with one thread

Start with the simplest question. One thread, no sharing, the same Rust source: why does the filter take longer in a browser? There are only two ways for the same work to take longer on the same core. Either the machine code has more instructions, or it has the same number and the CPU gets through them more slowly.

The CPU can count both. Hardware counters give the number of instructions executed and the number of clock cycles spent (a cycle is one tick of the CPU's clock, 3.2 billion per second here). Divide each by the number of pixels and you have the cost of one pixel:

Workload:

Both engines run about a third more instructions per pixel than native code on the filter. Chrome gets through them at a higher rate (more instructions per cycle) and ends about 1.16 times the native cycles. Firefox runs them at the native rate or below, and ends about 1.36 times. Those two ratios are the time ratios of the main campaign: the counters and the clock tell the same story.

An analogy. Three cooks follow the same recipe. One was given it in 65 steps, the other two in about 86 steps each, because their translators were wordier. Of the two with the long version, one works faster with his hands and nearly catches up; the other does not.

In depth: the listings, and how the loop alone was counted

The listings agree with the counters. The filter loops in data/probes/engine-code handle 16 pixels in 65 instructions natively, 87 in Chrome and 85 in Firefox: 4.06, 5.44 and 5.31 per pixel, against the counted 4.10, 5.52 and 5.41. Firefox's loop is as long as Chrome's and runs slower; it mixes VEX-encoded and legacy-encoded vector instructions and uses palignr where V8 does not. Whether that is why it gets fewer instructions per cycle was not tested, so the answer stops at the counters.

A browser run also starts a browser, generates the input and computes checksums, and all of that is counted too. So the loop was isolated by a difference: two campaigns identical except that one does 1 pass per timed sample and the other 8 (perf-loop1-v3, perf-loop8-v3, 180 runs each). The second does seven more passes of the loop and nothing else, so (count of the second - count of the first) / (7 × samples × pixels) is the loop alone (ADR 0090). The check that the method works: the native local histogram gives 2.77 instructions per pixel against the 2.75 of its code. One caveat: the rules for calling two counter values "the same" or "smaller" (overlapping 95% intervals) were fixed after a first look at the differences, so the counter comparisons on this page are not predictions in the strict sense (ADR 0090).

Question 1: why 8 threads give 7, not 8

The filter has no part that only one thread can do, and no thread ever waits for another. So why is its speedup about 7 and not 8? The guess: the eight cores are fine, but they all read and write the same memory, and memory has a limit on how much it can deliver per second.

If the guess is right, the counters should show something specific when going from 1 thread to 8: the same instructions per pixel (the work did not change), more cycles per pixel (each instruction waits longer for its data), and more cache misses. That is what they show. Each number below is the 8-thread value divided by the 1-thread value, so 1.00 means "unchanged":

But look at the size. Natively the cycles rise by 8.5%, and an efficiency of 0.87 means 15% is lost. So the cores' own slower work explains about half of the loss. The other half is time in which a core is not running the loop at all, which a cycle counter does not see: it fits the cost of handing out and collecting the tasks, and was not measured here. That is why the outcome says "supported, for about half".

Two other measurements point the same way. First, three builds of the same filter that differ only in how fast one thread goes through memory (SIMD builds): among the native builds and Firefox, the faster one thread reads, the less eight threads gain. Chrome is the exception: it reads more slowly than native and ends at the native efficiency.

Second, the image size. Natively, a 4096 x 4096 image (32 MB for input and output together) keeps more of its efficiency at 8 threads than the 8192 x 8192 one (128 MB):

Natively this agrees. In the browsers it does not show: their efficiency is lower on the smaller image, not higher (on small images the fixed cost of a parallel region also weighs in, see When parallelism pays). So the cutoff supports the reading natively and is not clear for the browsers.

Question 2: why Firefox scales better

This is the one RQ1 contrast that came out different from native: Firefox's filter speedup at 8 threads is 5.5% higher. It would be tempting to write "Firefox runs threads better". The data says something less flattering and more interesting.

Why

What is the trap here? Speedup is T1 / T8. You can raise it by making T8 smaller, or by making T1 bigger. A runtime with a slow single thread gets a better speedup for free. If we reported "Firefox scales best" without looking at the seconds, we would be praising the slowest runtime for being slow.

Firefox's loop is the slowest of the three per thread (question 3). A slower loop asks for less memory per second, so eight of them run into the shared memory less (question 1). The counters agree: from 1 to 8 threads Firefox's cycles per pixel rise less than native's, and so do its cache misses (the table above). In the SIMD chart Firefox sits where its one-thread speed puts it, on the same curve as the native builds; Chrome sits below that curve.

And there is one test that changes the speed inside a single engine. With the slower baseline compiler, the filter is slower per thread and scales slightly better, in both browsers:

So Firefox does not scale better because of how it runs threads. In seconds it stays the slowest at every thread count. Chrome is the case this does not close: its cycles rise less than native's and yet its efficiency is the native one, so by the same accounting Chrome loses more outside the loop, which fits the larger cost of its parallel region (Fork-join in the results) and was not measured here.

Question 5: a speedup above 8

Eight threads cannot do more than eight times the work of one. Yet Firefox's local histogram reaches a speedup above 8 at k = 16 and k = 256. When a number is impossible, the baseline is the suspect: the one-thread run must be paying for something the eight-thread run does not.

In Firefox a pixel costs fewer cycles with eight threads than with one (5% fewer at k = 256, which is the size of the excess over 8), and its cache misses per pixel fall by a quarter, where native's and Chrome's fall by a twentieth. The prediction held: the one-thread run pays for cache misses that the eight-thread run does not. What SpiderMonkey's one-thread loop does to miss more is not known.

It is not a slow pool of one thread either: the speedup is above 8 against plain sequential code too (below).

Question 4: the dip at 6 and 7 threads

The local histogram's efficiency dips at 6 and 7 threads and recovers at 8, in every runtime. The guess was about how Rayon cuts the work: it halves it again and again, which gives pieces in powers of two, and six or seven threads cannot share eight pieces evenly. The test: cut the work into pieces of a fixed size instead, and see whether the dip goes away.

Runtime:

Look at the times, not the efficiencies. With a fixed grain, 6 or 7 threads are not faster: 256 KB gives the times of Rayon's own split, and 1024 KB is worse. The efficiencies with a fixed grain look better only because the one-thread run with a fixed grain is slower, which raises every speedup computed from it. The guess is not supported. The dip stays unexplained; where the kernel places six or seven threads on eight cores was not tested.

In summary. The study now knows one thing the dip is not, and says so. It also shows, a second time on this page, how a relative number can improve because its baseline got worse.

Questions 6 and 7: Chrome's atomic add

These two are the heart of RQ2 and have a page of their own: Why Chrome: code and counters. In short: V8's optimizing compiler adds to a shared counter with a read and a compare-and-swap that retries; a native program changed to add the same way comes within 3% of Chrome's one-thread times, slower on one counter (question 6, answered). On 256 counters with eight threads it is faster than the native add, as Chrome is, but 14% from Chrome's time (question 7, answered for the direction). Why the same sequence wins on 256 counters is a proposed mechanism, not a tested one.

Question 8: Firefox below 1

Firefox's RQ2 number is 0.83 at k = 16 and 0.80 at k = 256: it seems to pay less than native for sharing. But the number is a ratio of two times, and it can fall because the top got smaller or because the bottom got bigger. Firefox's atomic times are the native ones, within a few percent. What moves is the other factor: its local histogram is slower than native's with one thread and scales past 8 (question 5), which is the denominator of the comparison. The table with both factors is on The answer to RQ2. So this one needs no test of its own: it follows from question 5.

Question 9: the noisy cells

Almost every cell of the study repeats within a percent. The atomic histogram at k = 1 with eight threads does not: its runs spread over 25 to 32% between the fastest and the slowest, and they fall on a few distinct time levels instead of a smooth cloud. The guess: eight cores fighting for one cache line can settle into different patterns of who gets the line when, and a run keeps the pattern it starts with.

If so, a run's time should follow its own count of line transfers. It does: across the 30 runs of the counters campaign, the rank correlation (Spearman's ρ) between a run's time and its lines taken for writing from another core is +0.94 in Chrome, +0.63 natively and +0.56 in Firefox. At k = 256 the runs are within 1% and there is nothing to follow. The levels are states of contention; what sets the state of a run is not known.

Is the one-thread baseline fair?

Twice on this page a speedup looked better because its baseline was worse. So the study checked its own baseline. Every speedup in the results is relative to the same parallel code run with a pool of one thread. If that pool were slow, every speedup would be inflated. The main campaign therefore also ran plain sequential versions with no thread pool at all (filter-seq, hist-seq, the sequential references):

A value of 1.00 means the pool of one thread is exactly as fast as plain sequential code. Every value is between 0.96 and 1.07: the pool of one thread costs between -7% and +5% in time. The relative speedup is not inflated by its baseline.

In depth: which core did the work at one thread

Every v3 run records the busy time of each measured CPU, so the one-thread runs can be split by the core that did most of the work. For the native filter that is CPU 12 (the degraded core, see The per-core check) or CPU 14:

The runs on CPU 12 are not slower. The busiest core has 70 to 80% of a native run's busy time and 47 to 64% of a browser run's, the rest being the main thread and the browser's other threads: the split says where most of the work was, not that one core did it all.

What stays open

A study is also judged by what it admits it does not know. These are declared with the results:

  • Why SpiderMonkey's filter loop, which can now be read, gets fewer instructions per cycle than V8's.
  • Why SpiderMonkey's local histogram misses the cache more with one thread.
  • What Chrome loses outside the loop at eight threads.
  • The mechanism by which a read before the locked write contends less over 256 lines.
  • The dip at six and seven threads.
  • What sets a run's state of contention at k = 1.

In summary. An explanation is only as good as the test it survived. Here, Chrome's atomic penalty at k = 1 has a cause shown by changing one thing; its advantage at k = 256 is reproduced in direction only; the filter's scaling has a reading supported by three measurements that agree; one guess failed its test and was dropped. And twice a ratio looked better because its bottom got worse: always look at the seconds.
