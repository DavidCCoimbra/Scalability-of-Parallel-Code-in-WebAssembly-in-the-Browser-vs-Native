From source to machine code

The study says "the same code" runs natively and in two browsers. That is true of the source the author wrote. It is not true of the instructions the chip finally runs: those are made three times, by three different translators. This page explains what a translator does and why that matters.

In short: a compiler turns readable source into the numbers a chip executes; natively that happens once, before the run, while in the browser the engine does the last step itself, so each browser ends up with its own machine code for the same program.

Source code and machine code

Source code is text written for people: count = count + 1. A chip cannot read text. It runs machine code: a stream of numbers where each number means one small step, such as "load this", "add these", "store that". Every chip family understands its own set of steps; the study's PC understands the x86-64 set.

An analogy. Source code is a recipe in your language. Machine code is the same recipe translated into the one language the cook on duty speaks, broken into single motions: take the egg, crack it, drop it.

Compiling ahead of time

A compiler is the translator. It reads the source once and writes the machine code into a file, the binary. Running the program later means running that file; the compiler is not involved any more. This is what "native" means in the study: Rust source, compiled on the PC into x86-64 machine code, run directly.

A compiler does more than translate word for word. It optimizes: reorders steps, removes useless ones, uses the chip's special instructions. Two compilers, or one compiler with two settings, can make quite different machine code from the same source, and one version can be twice as fast as the other. That is why the project fixes one compiler, one version and one set of settings for everything (Same source, same flags).

WebAssembly: a second step inside the browser

A browser cannot run an x86-64 binary: it would not be safe, and a phone's chip speaks a different language anyway. So for the browser the same compiler produces WebAssembly (WASM) instead: a portable half-way form, already compiled and optimized, but written for an imaginary simple machine that no chip actually is. The browser then has to translate WASM into the real chip's machine code before it can run it.

An analogy. The recipe is first translated into a careful, simplified international version. Each restaurant's head cook then translates that into instructions for their own staff. Two restaurants, two head cooks, two versions of the final instructions.

Engines and JIT

The part of the browser that does this second translation is its engine: V8 in Chrome, SpiderMonkey in Firefox. They translate just in time (JIT): when the page loads the WASM, or even while it is already running. Most engines do it in two passes: a quick, rough translation so the code can start at once, then a slower, better one swapped in a moment later. Until the better one is ready, the program runs slower than it will.

Why

Why does the study warm up before timing? Because the first seconds in a browser may be running the rough translation. Timing those would measure the engine's start-up, not the code. So every run does a few untimed rounds first (Warm-up inside the run).

Why

Why can the same program behave differently in Chrome and Firefox? Because the last translation is theirs, not the author's. For one small operation, adding to a shared counter, the two engines chose different machine instructions, and that single choice is behind the biggest difference in the study (Why Chrome: code and counters). The browser's translator is part of what is measured, on purpose.

What to remember

In summary. Source is for people, machine code is for the chip, and a compiler bridges them. Natively that bridge is crossed once, in advance. In a browser the engine crosses it again, at run time, in its own way, so "the same code" is the same source but not the same instructions.
