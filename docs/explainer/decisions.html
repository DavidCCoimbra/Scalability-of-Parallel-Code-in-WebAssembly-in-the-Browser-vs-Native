ADR index

Every setting of this study is a choice someone made: measure on 8 cores and not 16, 30 runs and not 10, wait 3 seconds before a browser run, pad each counter to 128 bytes. Each choice is written down in a short file called an ADR, with what forced it, what was decided and what it costs. There are 74 of them in docs/adr/, and they are the study's memory.

In short: a decision is never edited away; a later ADR amends or supersedes it, so the reason behind every setting can be read in the order it happened, including the times the data proved an earlier reason wrong.

How decisions are kept

An ADR (Architecture Decision Record) is a short Markdown file named NNNN-short-title.md, with a date and four sections. A check in CI (scripts/check_adrs.py, run by make lint) refuses a file whose title, number or sections do not match.

Context

What forced a choice: a pilot number, a bug, a course rule, a review finding.

Decision

What was chosen, and who decided it (David decides design questions; Claude only helped list options).

Consequences

What it costs, what it rules out, what has to be reported as a threat.

Status

Accepted, amended by a later ADR, or superseded by one.

An analogy. A ship's log. You do not go back and change Tuesday's entry when Thursday turns out differently; you write Thursday's entry and say "Tuesday's course was wrong, because of this". Anyone reading the log later sees both the mistake and how it was found.

Why

Why write decisions down at all? Six months later, "why is the delay 3 seconds?" has only two possible answers: a file that says so, or a guess. A guess might lead someone to remove the delay, and the Firefox start-up effect it hides (below) would quietly come back into the numbers. The ADR also lets a reviewer check that a setting was chosen for a reason, not tuned until the result looked good.

Three rules keep the record honest:

  • Never rewritten. When new data changes a decision, a new ADR says what changed and why, and the old one's status points to it ("amended by 0048"). The old reasoning stays readable.
  • Fixed before the data it governs. The analysis plan (ADR 0037) was fixed before the main campaign ran, so the statistics could not be chosen to fit the results (Ten decisions, a stricter bar).
  • Pilot data only justifies design. Pilot numbers appear in ADRs to explain a parameter (W, 30 runs, 8192², the 3 s delay); results come from the campaigns on measured/v3.

Decisions that changed

Most amendments are small (a field added to the run record, a name fixed to match the code). These five changed what the study measures or how it is read, and each is a lesson about how a benchmark can fool its own author.

The start delay explained three earlier findings (ADR 0048)

Pilots had shown a Firefox "knee" at N = 7 and 8 (ADR 0044), Firefox faster with E-cores (ADR 0045), and slow early iterations (ADR 0043). With a 3 s wait before each browser run starts, the knee disappeared: the cause was Firefox's own start-up work running during the measurement, not its threads. Every browser run now waits 3000 ms, and ADRs 0029, 0043, 0044, 0045 and 0047 were amended.

The lesson: three separate "findings" had one cause that was not the thing being measured. Without the ADR trail, the knee might have gone into the paper as a property of Firefox.

From a hypothesis to machine code and counters (ADR 0049, 0068, 0072)

ADR 0049 kept the 128-byte padding and recorded Chrome's odd counter pattern as a hypothesis: "the code was not inspected". The v2 audit then read the JIT code from each browser's memory: V8 compiles the atomic add as a load plus a lock cmpxchg loop. ADR 0068 made the hardware counters readable, and ADR 0072 counted with 30 runs per cell: the loop retries once every four adds at k = 1, N = 8, and Chrome reads the line before it writes it. That was still an observation. ADR 0088 wrote down what a test would show, and ADR 0089 ran it on measured/v3: a native program in which only the instructions of the add change comes within 3% of Chrome's one-thread times, and reproduces the direction of the effect at k = 256.

The lesson: a hypothesis is allowed in an ADR as long as it is labelled one; it took four more ADRs to turn it first into a measurement and then into a tested cause. Why Chrome: code and counters.

The v2 build: asymmetries of our own (ADR 0069)

A review against the textbook and the cited papers found that the shared-counter histograms paid a per-pixel bounds check the local control did not, and that some variants timed their final merge and others did not. Both were fixed in one tagged build, measured/v2, and every campaign was run again on it. Earlier campaigns stay valid for their own build but are never mixed with v2 in one comparison (ADR 0062).

The lesson: the control and the thing it controls for must differ in exactly one way; two hidden differences meant every earlier RQ2 number had to be remeasured. Our own asymmetries: the v2 build.

A pinned browser that updated itself (ADR 0071)

The pinned Firefox 158.0 updated itself to 160.0 during a campaign, although the profile disabled updates. The affected runs of that build were repeated on 158.0, Firefox now gets an enterprise policy that turns updates off, and a campaign refuses to start with an unpinned browser.

The lesson: "pinned" is a claim until something checks it on every start. A pinned Firefox updates itself.

Notion out, Markdown in (ADR 0063)

ADR 0010 mirrored every ADR to Notion. Keeping two copies in sync by hand was dropped: the files in docs/adr/ are the only copy.

The lesson: a record that lives in two places is soon two records.

Measured again, with the rules written first (ADR 0084, 0095)

The v2 results were valid, and what they could not establish was declared (ADR 0080). Some of those items a new build could answer instead of declare, so measured/v3 was built and every campaign run again. Because the v2 numbers were known, ADR 0084 fixed in advance when v3 would be the reported build, in terms that read counts of runs and never a result. ADR 0095 records that the criteria were met and that all ten primary decisions came out as before.

The lesson: a second measurement is worth the most when nothing about it could have been chosen after seeing the first. The session of a build.

A gate that failed, and was not turned into a pass (ADR 0087)

The rehearsal before the v3 campaigns failed one criterion on one cell, twice. The cell was looked at, the behaviour turned out to exist in v2 as well, its effect on the analysed value was measured at 0.1%, and the campaign went ahead with the parameters unchanged and the failure recorded as a failure.

The lesson: a check that fails is information; changing the measurement to make it pass would have been choosing the method by the data. The gate.

An explanation that lost its support (ADR 0077, 0085)

Five slow runs of v2 fitted a degraded core running below its clock, and ADR 0077 said so as a likely reading. The per-core check then timed every core alone: the degraded one was as fast as the others. The explanation was withdrawn, and in v3 the slow runs did not come back.

The lesson: "it fits" is not "it was tested"; the record keeps both the guess and the test that undid it. The per-core check.

In summary. Before changing any setting, find its ADR: it says why the setting is what it is, and often what went wrong the last time it was different. If you change it, you write the next ADR; you never edit the old one.
