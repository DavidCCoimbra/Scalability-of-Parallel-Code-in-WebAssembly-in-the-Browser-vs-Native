The machine and environment control

Every number of the study comes from one PC, prepared the same way for every run: eight identical cores at a fixed clock for the measured program, everything else on the other cores. This page lists each control, why it exists, how the harness checks it on every run, and two problems of the machine that the checks now catch.

One PC, slowed down on purpose

A modern computer is built to be fast on average, not to be the same every second. It speeds up when it is cool and slows down when it is hot. It gives a program more or less of a core depending on what else is running. It wakes up background jobs at random moments. None of that is a problem for a user. All of it is a problem for a measurement, because the same program can take a different time each time you run it, for reasons that have nothing to do with the program.

An analogy. You want to know whether two runners are equally fast. You would not time one on a windy day and the other on a calm day, or let one run on an empty track and the other through a crowd. You pick one track, close it to the public, and wait for the wind to drop. The track is slower than a race with a tailwind, and that is the point: the same conditions for both.

This study does that to one machine (the page Programs, processes, threads and cores explains the words core, thread and clock, if they are new). The PC is an Intel i9-14900KF with 64 GB of RAM, running Ubuntu 26.04 LTS (kernel 7.0.0-43 for every campaign of the study). Its chip is hybrid: it has 8 big, fast cores (the P-cores) and 16 small, slower cores (the E-cores). The measured program gets the 8 fast cores and nothing else. Everything else on the machine gets the 16 slow ones.

Why

Why one machine, and not several? Because the study compares runtimes, not machines. If native ran on one PC and Chrome on another, a difference between them could be the PCs. With one machine, the machine is the same in both halves of every comparison and cancels out. The price is that the results describe this PC; the page External threats says so.

Why

Why not develop on it too? Development happens on a Mac. The Mac has a different CPU, turbo on, and no way to shield cores, so its numbers would not be comparable with anything. Numbers from the Mac are never results (Two machines, two jobs).

P-cores only

The measured program is told which cores it may use: the 8 P-cores, numbered 0,2,4,6,8,10,12,14. This list is a CPU mask, and the tool that applies it is taskset. The mask is set on the whole process, not on each of its threads: a web page cannot choose which core each of its workers runs on, so to keep the comparison fair native is given exactly the same treatment (ADR 0001).

Why

Why not use all 24 cores? Because the slow cores would make the fast ones wait. Rayon splits the work into pieces and lets idle threads take pieces from busy ones. With E-cores in the mix, some threads land on cores that are about half as fast, and share them with the rest of the system. In a pilot, adding the E-cores made runs at N = 8 up to 19 % slower and several times more variable (ADR 0045). The P+E case is still interesting, so it is measured on its own as an exploratory campaign (P-cores plus E-cores); it just is not the baseline.

Why

Why is a mask on the process not enough for a browser? Because a browser is not one process: Chrome starts helper processes, and one of them once moved itself out of the mask by asking the desktop for a new process (Chrome escapes the CPU mask). So every run starts inside its own systemd scope: a group the operating system keeps track of, whose AllowedCPUs bounds every process the browser creates, however it creates them. The run's own CPU time is later read from that same group.

In depth: the mask and the scope in the code

The scope is created with systemd-run, which needs a sudoers rule on the PC (make sudoers). The mask inside the scope is a cgroup cpuset, so it holds for every child process, not only the one taskset started.

Turbo, governor, SMT

Three features of the CPU make the same run take different times. All three are fixed before a session by make env-setup, and stay fixed until the next reboot. Each one has a short story of what would go wrong if it were left alone.

Why

Turbo: off. Turbo lets the chip run faster than its normal speed while it is cool, and faster still when only a few cores are busy. Imagine it on: a run with 1 thread uses one core, which stays cool and turbos high; a run with 8 threads heats the chip and turbos less. Then "8 threads are only 6 times faster than 1" would be partly true and partly an artefact: the 1-thread run had a faster clock. Speedup would mix how well the code parallelizes with how the chip manages heat. With turbo off, every core runs at the same base clock, 3.2 GHz, whatever the load (ADR 0002).

Why

Governor: performance. The governor is the rule the operating system uses to pick the clock speed. The default saves power: it lowers the clock when the machine looks idle, and raises it again when work arrives. Between two iterations the machine does look idle for a moment, so the next iteration would start slow and speed up. With the governor set to performance, the clock never drops.

Why

SMT: off. SMT (hyper-threading) makes one physical core look like two. Two threads can then run "at once" on it, but they share its arithmetic units and its cache, so each gets roughly half. If SMT were on, a run with 8 threads could have two of them on the same core, and "8 cores" would really be 7 and a half. With SMT off, the odd CPU numbers 1 to 15 disappear, and each CPU in the mask is one whole core (ADR 0025).

Degraded core. One core of this particular CPU is faulty at high frequencies. With turbo off it never reaches them: a check of every core before the build found it as fast as the others and computing correctly (The per-core check). It is the same core for every environment, so it does not favour one; it is listed as a threat (Internal threats).

In depth: how env-setup does it, and what is not logged

The frequency is not sampled during a run: reading it sends an interrupt to the measured cores, which is exactly the kind of disturbance the setup removes. The governor, turbo and SMT settings are recorded before and after each run. Since measured/v3 each run also records, per measured CPU, its busy time and a frequency reading before and after; the busy time says which cores worked, but the frequency reading turned out to be taken while a core is already going idle and is not used (ADR 0085). With turbo off, the degraded core never reaches the frequencies at which it fails, which is also why turbo stays off for every experiment on this PC, not only the reported ones.

The degraded core

One of the PC's eight fast cores is degraded. With the desktop's usual settings (turbo on), a test pinned to it crashed in 17 of 18 tries. With turbo off, the setting of every measurement, it passed 30 of 30 and timed the filter as fast as the other cores.

Why

Why this would have fooled us. A core that crashes is easy: you see it. A core that sometimes computes a wrong value and carries on is the dangerous one, and not only for the runs. The compiler that builds the measured program is a program too, and so is the analysis. That happened once: with the PC restored after the last campaign, an analysis command stopped with an error raised from inside Python's own statistics code, on data it reads without trouble elsewhere.

  • Fix: the measured build is made on the prepared PC, twice from scratch, and tagged only if both builds are byte for byte equal. Outside a prepared session, analysis on that PC runs pinned away from that core.
  • Check: every run has a checksum that must match across runtimes and thread counts, and CI regenerates every table on another machine and compares it with the committed one.

The whole story is on The per-core check.

Shield and quiet mode

The mask keeps the measured program on the 8 P-cores. It does not keep anything else off them: the desktop, the terminal, a file indexer, an update check, all of them may still be scheduled on a P-core. Two more steps handle that.

  • The shield moves every other process on the machine to the E-cores, 16 to 31. The harness, the results server and your terminal all run there. A run's own scope is the only thing allowed on the P-cores (ADR 0028).
  • Quiet mode closes desktop apps and stops the background services that wake up at random times: the file indexer, update timers, snap, docker. Every campaign turns it on before the first run and off again at the end, also when it fails (ADR 0042, ADR 0070).

Why

Why both, if the shield already moves everything away? Because the E-cores and the P-cores are not fully separate. They share the chip's last cache and its memory. A background job on an E-core that reads a lot of data pushes the measured program's data out of that cache, and the measured program slows down without anything touching its cores. Quiet mode keeps those jobs from starting in the first place. The page Memory and caches explains why a shared cache matters.

The machine also does not go to sleep in the middle of a campaign: make campaign runs under systemd-inhibit.

In depth: the shield and quiet mode in the code

The shield is a cpuset on system.slice, user.slice and init.scope. Kernel threads such as kworkers and interrupt handlers cannot be moved and are the reason "foreign CPU time" below is measured rather than assumed to be zero.

A browser that left the mask

Pilot numbers. The numbers that found the problems on this page come from pilots and from the earlier build, measured/v2. They justify the fixes; they are not results of the study. Every fix was in place before the first run of measured/v3.

Every run is told to use only the 8 fast cores (a taskset mask), inside its own systemd scope, a box the operating system keeps the run's processes in. During the pilot, a sampler that checked where every thread was allowed to run found that Chrome's main process had moved itself out of the box: through the session bus it asked the system for a box of its own, in the user's area, and ran on the slow cores, outside the mask. Firefox's processes stayed in (ADR 0045).

Why

Why this would have fooled us. Chrome would have had the 8 fast cores for its workers plus extra cores for its own housekeeping, and Firefox would not. A difference between the two browsers would then have been partly a difference in how many cores each really had, and we would have read it as a difference between the engines.

  • Fix: the harness launches the browsers without the session bus address. Without it, every Chrome process stays in the run's box.
  • Check: every run records escapedProcesses, the browser processes found outside the box, and strict validation rejects any run where it is not 0.

Checked on every run

Setting all of this once is not enough. A reboot undoes it. A step can be forgotten. A background job can slip through. So the study does not trust the setup: it checks it, at two moments, and records what it found with every run.

Why

Why check, if we just set it? Because a measurement taken with turbo back on would look exactly like a normal one, only faster, and nobody would notice. The only protection is a check that refuses to run, and a record that lets the analysis throw the run out later.

Before a session

Every start and every resume of a campaign checks turbo, the governor, SMT, that the mask is every P-core, that the shield is up and that the browsers are the pinned versions. On any problem it refuses to run. It saves the state in sysinfo/ (ADR 0040, ADR 0071).

With every run

Each run's record (its JSON file) notes the commit, the CPU model, governor, turbo, SMT, the mask, the shield's cores, the browser version, the build hashes and the run's position in the order (ADR 0023).

Foreign CPU time

How busy were the 8 measured cores during the run, minus how busy the run itself made them? Whatever is left was something else, running where it should not. Above 0.25 s the run is excluded (ADR 0051).

Strict validation

The analysis re-reads every record and excludes any run with an unclean build, turbo on, the wrong governor, SMT on, the wrong mask, an unpinned browser or a browser process outside the scope.

In the main campaign, no run failed strict validation and no run went over the foreign CPU threshold (data/tables/campaign-v3/campaign-v3-quality.md; see The data check).

In depth: how foreign CPU time is read, and the validation code

The busy time of the 8 CPUs comes from /proc/stat, read before and after the run, in clock ticks. The run's own CPU time comes from its scope's cpu.stat. Foreign CPU time is the difference. The 0.25 s threshold was fixed before any campaign result was read, as twice the largest value seen over 1638 pilot runs (0.125 s, in Chrome; the 99th percentile was 0.062 s). Small negative values are normal: /proc/stat counts in 10 ms ticks.

In summary. One PC, prepared the same way for every run: eight P-cores at a fixed clock for the measured program, the rest of the system on the E-cores, and every setting checked before a run and recorded with it. A CPU mask does not confine a browser by itself, and one core of this PC computes wrongly when it runs fast; both are now checked.
