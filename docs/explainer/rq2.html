RQ2: synchronization

RQ2 asks whether threads that share data cost a browser more than they cost native code. This page gives the metric, the ten decisions fixed before the campaign, and then what the study found about where Chrome's difference comes from: the machine code of one atomic add, a native probe that changes only that code, and the hardware counters.

The metric, with the real numbers

Two runtimes cannot be compared by the atomic histogram's time alone: the browser is already slower at everything (Browser over native). So the study asks a sharper question in three steps, here with the measured times at N = 8 and k = 1 (every pixel adds to one counter):

  1. Inside native: how many times slower is sharing than not sharing? Atomic time divided by local time, times.
  2. Inside Chrome: the same division, times.
  3. Chrome's price over native's price: . That number is the answer for this cell: 1 would mean Chrome pays for sharing exactly what native pays; 2 means twice as much.

Why

Why a ratio of a ratio, and not just "Chrome's atomic histogram is slower"? Because it is slower at the local histogram too. If we compared atomic times directly, we would count the browser's general slowness as a cost of sharing, and conclude that sharing hurts the browser even when it does not. Dividing by each runtime's own no-sharing time first cancels that out: what remains is the price of sharing alone. See A ratio of ratios, and ADR 0026.

Now the same three steps at every N and every k. k is how many different counters the pixels are spread over: k = 1 is everyone on one counter, k = 256 is spread out (Contention).

Shared atomics do not scale anywhere. At k = 1 to 16 the atomic histogram is slower with 8 threads than with one, in every runtime (speedups below 1). Contention is the same hardware problem natively and in the browser; RQ2 asks only whether the browser makes it worse.

In depth: the metric as the paper writes it

For each environment, k and N: r = log Tatomic - log Tlocal, the price of sharing on a log scale. Then Δr = rbrowser - rnative, and the guide shows exp(Δr), the ratio of ratios above. The log form makes the two ratios subtract, keeps 2x and 0.5x symmetric, and matches the geometric means the times are summarized with (The RQ2 metric, ADR 0026). The left chart above is on a log scale for the same reason.

A difference with one thread

Here is a clue to where Chrome's extra cost comes from. With one thread there is nobody to share with, so the price of "sharing" should be the same everywhere. It is not:

At k = 1 the atomic histogram costs Chrome times its local histogram, against times natively, with a single thread. So part of Chrome's extra cost is not about threads fighting at all: it is the atomic operation itself, which Chrome's engine turns into slower machine code. The exploratory private atomics are consistent with it with no sharing at all, and Why Chrome shows the code and the two tests that pin the cause down.

The machine code of one add

The same line of Rust, "add one to this shared counter", reaches both browsers as the same WebAssembly instruction. Each engine then turns it into machine code, and the two engines choose differently. If machine code is new to you, read From source to machine code first; the two ways of adding are explained step by step in Two ways to add.

The Rust source is shared by all three runtimes. Every pixel adds 1 to the counter of its grey level:

To see what each engine made of it, the study captured the machine code each engine runs for this loop on the measured build: V8 can write its compiled code to a file, and Firefox's was read out of the memory of a running Firefox at the addresses where the CPU spent its time. The listings are in data/probes/engine-code/. Per pixel, with the operands simplified:

Native (LLVM) Firefox (SpiderMonkey)

lock add  %rcx, (counter)    # Firefox, %rcx = 1
lock incq (counter)          # native, one locked op

lock means: nobody else may touch this counter while I add. One instruction, never fails. Firefox does 8 pixels per loop turn with a cheap alignment test and one interrupt check per 8 pixels.

Chrome (V8)

retry:
mov  (counter), %rax         # plain read
add  $1                      # the new value
lock cmpxchg new, (counter)  # write if unchanged
jne  retry                   # another core won

cmpxchg is "compare and exchange": write the new value only if the counter still holds what I read. If it does not, jump back and start again.

An analogy. Eight people keep a shared tally on a whiteboard. Firefox's way: grab the marker, add one, let go. Chrome's way: read the number, work out the next one in your head, then go to write it, but only if the board still shows the number you read. If someone wrote in between, read again.

Why

Why does Chrome do this? V8's optimizing compiler turns this atomic add into a compare-and-swap loop rather than a lock add. V8 has a second, simpler compiler (the baseline compiler, used while the code is still warming up), and that one emits a single locked instruction, lock xadd. So this is a choice inside one compiler of one engine, not something the study's code asks for, and not something a WASM program can change. It is part of what "running in Chrome" costs, so it is a result of RQ2, not a flaw of the study.

Without any sharing, the extra read already costs something. From the main campaign, with one thread, Chrome's atomic histogram takes 1.085 times native's time at k = 256 and 1.84 times at k = 1, where each add has to wait for the previous one to the same counter:

V8's code comes from one diagnostic Chrome run per kernel and compiler with V8 writing its compiled code (scripts/capture_chrome.py, scripts/chrome_code.py). Firefox 158 release ships no such dump, so one long Firefox run per kernel was sampled with perf and the sampled pages were read from the process memory (scripts/capture_firefox.py, scripts/firefox_code.py). V8's optimizing compiler lowers the i64.atomic.rmw.add, whose result is unused, to a load, an add and a lock cmpxchg back to the load; its baseline compiler to lock xadd behind an alignment and a bounds check. The exploratory private atomics (one table per thread, no sharing at all) cost Chrome 1.83 to 1.85 times native at k = 1 (Private and packed atomics): the instruction cost without the sharing cost.

A probe that changes only the add

Reading two listings shows a difference. It does not show that the difference is what makes Chrome slow: the two engines differ in many other things. To test a cause you change that one thing and nothing else, and see whether the effect follows.

So the study wrote a probe: a small native program that counts the same image into the same table of padded counters, and built it several times. Each build adds one to a counter with different instructions: the native way (lock inc), V8's optimizing way (read, add, lock cmpxchg, retry), and V8's baseline way (lock xadd). Nothing else changes: no browser, no WebAssembly, the same compiler for everything around the add.

Why

Why write the prediction down first? Before the probe ran, the study wrote what it should show if the explanation is right: with the compare-and-swap the native program is slower at k = 1 and faster at k = 256 with eight threads (ADR 0088). A prediction written afterwards can always be made to fit. One written before can fail, and that is what makes passing mean something.

Threads:

The probe rows are the median of 10 passes, from data/probes/atomic-increment/passes.csv; a probe, not a result. The Chrome and native rows are the main campaign.

The prediction held. With one thread, the native program with Chrome's way of adding takes Chrome's times: slow at k = 1, close to native at k = 256. With the native way it takes the native times at every k. With eight threads at k = 256 it turns faster than the native way, as Chrome does. The way of adding is enough to produce Chrome's whole RQ2 pattern, in both directions, with no browser involved.

An analogy. Two bakeries make different bread and you suspect the flour. Comparing the bakeries proves nothing: the ovens, the water and the bakers differ too. So you bake at home twice, changing only the flour. If your two loaves differ the way the bakeries' do, it was the flour.

In depth: what the probe cannot show

Each probe thread has a fixed slice of the image and a fixed core, where the bench splits the image into Rayon tasks and leaves placement to the kernel, so its eight-thread times at k = 1 are not the bench's. One session, ten passes per cell. The probe shows that the sequence is enough to produce the effect on this CPU, which is less than showing that nothing else contributes to Chrome's times (data/probes/atomic-increment/README.md, ADR 0089).

The other compiler of each engine

A second test stays inside the browser. Both browsers have two compilers: a quick baseline one and a slower optimizing one. The tier campaign (2100 runs) ran each browser in three arms: as shipped, with the baseline compiler only, and with the optimizing compiler only.

Three things to read here. First, "as shipped" and "optimizing only" give the same times: the study's campaigns measure the optimizing compiler, as intended. Second, Chrome's baseline compiler, which adds in one locked instruction, does not have the k = 1 penalty: its time barely depends on k, and the RQ2 number at k = 1 falls from 2.17 to 1.04. Third, Firefox does not change with k under either compiler.

This test changes the whole compiler, so every instruction of the loop changes with the add; alone it shows that the effect follows the compiler. The probe above isolates the add. Together they say: the cost of Chrome's atomic histogram at k = 1 is the compare-and-swap sequence of V8's optimizing compiler.

Retries, counted

The loop is one thing; how often it actually goes round again is another. A retry only happens when another core changed the counter between the read and the write, so with one thread it never happens, and with eight threads on one counter it could happen a lot. The study counted it.

The CPU has built-in counters for events like "a locked instruction ran" or "a cache line had to be fetched from another core" (hardware counters). A separate campaign on the same build (perf-v3) read them with perf stat on the eight P-cores, 30 runs per cell, at k = 1 and 256 and N = 1 and 8, and divided each run's counts by its number of atomic adds.

So the counter to watch is locked loads per add. With one thread it is about 1 (one attempt per add). Whatever it rises to with eight threads is the retries:

At k = 1 with 8 threads, Chrome does 0.24 more locked loads per add than with 1 thread: about one add in four retries. Firefox and native add 0.001 to 0.002, which is nothing. At k = 256, where the adds are spread over 256 counters and two cores rarely race for the same one, Chrome's extra is only 0.015.

Why

Why compare with N = 1 and with Firefox, and not just read Chrome's number? Two things could inflate the count. The thread pool itself does a few locked operations (handing out work, waking threads), and those grow with N. And the browser does some locked operations while it starts up, which fall inside the counting window. Subtracting Chrome's own N = 1 value removes the second; Firefox, which runs the same WASM module with the same thread pool and adds only 0.002, bounds the first. What is left is the loop going round again.

In depth: the N = 1 baselines and what the window holds

The N = 1 baselines are 0.999 natively, 1.016 in Chrome and 1.037 in Firefox: the counting window of a browser run also holds the browser's start-up and the calibration, which do their own locked operations (0.016 and 0.037 per add above native). Retries are read as the excess over N = 1, so this cancels. The pool's own locked operations (work stealing, latches, wake-ups) are bounded by Firefox's excess of 0.002, with the same module and the same Rayon. ADR 0072 describes the method on the earlier build; the table above is the same campaign on measured/v3.

Line transfers, counted

The retry is not the whole story. Chrome's loop begins with a plain read, and that read has a cost of its own when the counter was last written by another core.

Cores do not exchange single numbers; they exchange cache lines of 64 bytes (Data moves in lines of 64 bytes). When a core needs a line that another core has just written, the line has to travel over. The CPU counts those events: a HITM is "I asked for a line and found it modified in another core's cache". There are two kinds. A read HITM: a plain read wanted a copy. An RFO, read for ownership: a locked instruction wanted the line in order to write it.

Why

Why a line move matters. Fetching a line from another core's cache takes on the order of a hundred nanoseconds on a chip like this one (the exact figure depends on the CPU and was not measured here), against about one nanosecond for a value already in the core's own cache. A loop that moves a line for every add is bounded by those moves, not by the arithmetic.

Natively and in Firefox the line is only ever taken for writing: read HITMs are at most 0.006 per add. Chrome's plain read first fetches it from the other core: 0.30 read HITMs per add at k = 1 and 0.71 at k = 256. At k = 1 that doubles the number of line moves per add, 0.49 in Chrome against 0.24 natively and 0.26 in Firefox, and Chrome takes about twice as long.

The counters also explain why the k = 1 cells are the noisiest of the study. Their runs fall on several time levels, 25 to 32% apart, and a run's time follows its own count of line moves (in Chrome, Spearman's ρ = +0.94 between a run's time and its lines taken for writing). The levels are states of contention that differ from run to run; what sets the state of a run is not known (question 9).

Note

A check that the counting is right. The cycles counted per add should match the run times from the main campaign. Chrome at k = 1, N = 8: about 1889 ms per iteration in the main campaign × 8 cores × 3.2 GHz, divided by the 67 million pixels, predicts about 720 cycles per add; the counters, on their own 30 runs, say 681. This cell varies by more than that from run to run (see above), so the two agree. The counting windows hold the right intervals. (Cycles here measure time on the eight cores, waiting included, not useful work.)

k = 256: reproduced in direction, mechanism open

At k = 256 the picture flips: Chrome's atomic histogram gets faster with threads (speedup 1.96) while native's does not (0.92), and Chrome pays only 0.42 of native's price for sharing. The counters show that Chrome moves more lines than native there, not fewer, and yet finishes in about half the time:

So the gain is not fewer transfers. What is known: the sequence is enough to produce it. In the probe, the native program with the compare-and-swap takes 240 ms at k = 256 with eight threads, where the locked add takes 415 ms; Chrome takes 210 ms and native 415 ms. Pick 8 threads in the probe table to see it.

Look at the order: it is not the order of how fast one add is. The sequences that do more around the locked write finish sooner. One prediction failed here, and it is kept as a failure: Chrome's baseline compiler was expected to lose the advantage over native, and it keeps most of it; Firefox's baseline compiler even gains one that its optimizing compiler does not have.

Why

What is the explanation, then? A proposed one, not tested: eight cores hitting 256 lines at random spend their time moving lines between caches, and a sequence that reads the line first, or does other work between two locked writes, asks for exclusive ownership of a line less often. The study shows that the sequence causes the effect; it does not show the mechanism inside the CPU. It also depends on the padding: with eight counters packed into one line, Chrome's atomic histogram becomes 3.45 times slower (packed counters).

The padding holds

Each shared counter is padded to 128 bytes, so that no two counters ever share a cache line and the only sharing measured is the sharing the study intends (False sharing and padding). In the browser the counters live in the WASM module's memory, laid out by the Rust allocator inside it, so the padding had to be checked there too, not only natively.

perf c2c, a tool that lists the cache lines several cores fought over, ran during one k = 16, N = 8 run per browser on the earlier build, measured/v2; the counter table and its padding are the same code in measured/v3. It found 16 contended lines, 0x800 bytes apart (16 counters × 128 bytes = 2048 = 0x800), every access at offset 0 of its line, in Chrome and in Firefox. Each padded counter is alone on its line in WASM memory: what the study measures is true sharing, not false sharing.

The perf c2c reports are with the data of that build, at the tag data/v2 (data/raw/perf-v2/c2c/).

The answer to RQ2

Synchronization changes the gap, and how depends on the engine. Relative to the no-sharing control, shared atomics cost Chrome 1.4 to 2.3 times what they cost natively when the sharing is concentrated on a few counters (k = 1 to 16), and 0.42 times when it is spread over 256 counters, where Chrome's atomic histogram even scales (speedup 1.96, against native's 0.92 and Firefox's 0.97). Firefox is never worse than native: no detectable difference at k = 1, cheaper from k = 4 on.

Two things the number hides, both shown by its two factors below. Firefox's values under 1 at k = 16 and 256 do not come from cheaper atomics: its atomic times are the native ones, and its local histogram scales more than native's, which makes the denominator smaller (question 8). And Chrome's effect in both directions follows one thing, the instructions its optimizing compiler emits for the add (the probe).

In depth: why memory order is not the explanation

WASM atomics are always sequentially consistent, which a reader may suspect as the cause. It is not: on x86 a locked read-modify-write costs about the same whatever its ordering, so Relaxed and SeqCst compile to the same instruction on these targets (Memory order, for the record). The reason is the code each engine generates around the operation.

In summary. Sharing between threads is expensive in every environment. Measured as the atomic over local time ratio against the same ratio natively, Chrome pays 1.4 to 2.3 times the native cost on 1 to 16 counters and 0.42 times on 256; Firefox's ratio is never above native's. At k = 1 the penalty follows the compare-and-swap loop of V8's optimizing compiler: it is gone with V8's baseline compiler, and a native program with that loop comes within 3% of Chrome's one-thread times. At k = 256 the same probe reproduces the direction of Chrome's advantage, 14% away from Chrome's time, and the mechanism is proposed, not shown.
