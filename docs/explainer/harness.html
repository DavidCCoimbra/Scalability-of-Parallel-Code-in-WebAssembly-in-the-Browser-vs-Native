From make to a CSV row

The whole study is thousands of small, identical experiments called runs. This page follows one of them: from the moment the harness decides to start it, through the program that does the measuring, to the two files it leaves on disk. Once you can read those two files, every number in the study is within reach.

In one sentence: a run is one freshly started program that warms up, times the workload ten times and writes the times to a file; the same Rust function does the timing in all three environments, and only how it is started and how its file reaches the disk differ.

The run pipeline

Start with the word. A run is one start of one program. For native, it is the compiled program starting, measuring and exiting. For a browser, it is Chrome or Firefox starting with a brand-new, empty profile, loading one page that does the measuring, and being closed. Nothing survives from one run to the next: no process, no cache, no window.

Picture it. A run is one lap on the stopwatch, but with the runner sent home and called back for every lap. It sounds wasteful. It is the only way to be sure that lap 7 is not faster because the runner was already warm from lap 6. The page The run is the unit says why this matters for the statistics.

Why is nothing automated inside the browser? Tools such as Puppeteer, Playwright or the DevTools protocol can drive a browser from a script, which would make the harness simpler. But they do it by living inside the browser process: extra threads, extra messages, extra timers, all in the thing being measured. We would be timing the browser plus the puppet strings. So the harness only launches the browser with a URL and waits for the result file to appear (ADR 0006).

A native run

For a native run the harness starts the compiled program, bench/target/release/native, with the configuration as command-line flags (which workload, how big an image, how many threads). The program prints its results as CSV text to its standard output, the harness catches that text and writes it to disk next to a record of the run's context.

Inside, the program does four things in order, and they are the same four things the browser page does, because it is the same Rust code: it builds the pool of N worker threads; it generates the input image from a fixed seed; it times a few empty parallel regions (the calibration); then it runs the warm-up and the measured iterations, timing each one.

Why is only the parallel work timed? Each iteration also prepares its buffers and checks its result. Those happen outside the clock. If they were inside, the time would include work that has nothing to do with scaling, and native and the browsers do that work at different speeds for reasons unrelated to threads. The clock starts right before the parallel region and stops right after.
Checksum. Every iteration ends by boiling its whole output down to one number (a hash). The first iteration's number is the reference; a later one that differs means the program computed something different, and the run fails. The numbers must also match across environments and thread counts, which harness.collect checks before any analysis. It is how we know all three runtimes really did the same work.

A browser run

A browser run starts Chrome or Firefox the way the harness wants it: with a temporary, empty profile; without a window (headless); with its own updates, telemetry and background features switched off; and with a URL that carries the configuration, the same values the native program got as flags (ADR 0022, ADR 0029).

Why a fresh profile every time? A browser profile is its memory: caches, compiled code it saved, settings, history. If run 2 reused run 1's profile, it could start with code already compiled or files already cached, and be faster for a reason that is not the runtime. A fresh profile makes every browser run start from zero, like every native run does (fresh profile).
Why headless? A window means drawing, compositing and a desktop talking to the browser, all of it work on the measured cores that has nothing to do with the workload. A pilot measured the difference between headless and headful at under 0.3 %, so headless costs nothing and removes a source of noise (ADR 0046).

What the harness does

  1. Creates a fresh profile (Firefox also gets a user.js that turns off updates, telemetry and safe browsing).
  2. Starts the browser in the run's scope and CPU mask, with index.html?run=<id>&threads=8&....
  3. Waits for <id>.csv to appear (or for a timeout).
  4. Stops the whole scope, so no browser process survives into the next run, and deletes the profile.
  5. Adds the machine's context (mask, governor, foreign CPU time) to <id>.json.

What the page does

  1. Refuses to run unless the page is cross-origin isolated (explained below).
  2. Waits the start delay (3 s), so the browser finishes its own start-up first.
  3. Starts a coordinating Web Worker, which loads the WASM module and starts N pool workers.
  4. The worker calls the same Rust run function and gets the CSV back as a string.
  5. The page sends {csv, meta} to the local server.
Why does a worker run it, and not the page itself? While the pool works, the thread that started the parallel region waits for the others to finish, and in the browser that wait is a call that blocks the thread (Atomics.wait). A page's main thread is not allowed to block, because it also draws the page and handles input. So the page hands the job to a Web Worker, which may block, and waits for its message. Chrome is Chrome for Testing 155.0.8059.84 and Firefox is 158.0, both pinned and checked before every session (ADR 0021, ADR 0071). The start delay came from a pilot in which Firefox was still starting up during short iterations (ADR 0048).

The results server

A web page cannot write a file to your disk. So the harness runs a tiny web server on the machine, harness/server.py, on the E-cores, reachable only from the machine itself (127.0.0.1). It has two jobs:

  • It serves the page. The browser loads bench/www/index.html from it, with two special headers attached that make the page cross-origin isolated.
  • It receives the result. When the page is done, it sends the CSV and some context to the server (POST /results?run=<id>), and the server writes <id>.csv and <id>.json, the same two files a native run gets.
Why do the headers matter? Threads in the browser share memory through a SharedArrayBuffer. Years ago that feature was used in a security attack, so browsers now refuse it unless the page promises, through those two headers, that it will not mix in content from other sites. No headers, no shared memory, no threads. The page checks the promise took effect before it starts, and fails loudly if not.
If you already know this: the headers and the write order

The server writes the JSON first and the CSV last, so an existing CSV always means a complete run. It never overwrites a run (it answers 409): a repeated id is a harness bug to notice, not to hide (ADR 0019). The headers are COOP and COEP.

One CSV row, field by field

Here is what a run leaves behind. The CSV file has one row per timed thing: every warm-up iteration, every measured iteration and every calibration sample. Native and the browsers write exactly the same columns. Below is a real file from the main campaign, its header and its first measured row, and then each field read aloud:

Two columns matter most. phase says what kind of row this is: a calibration sample, a warm-up iteration, or a measured one. Only measured rows are used for timing. And ns is the time of that one iteration, in nanoseconds (billionths of a second): the row above says 3 274 887 ns, which is about 3.3 ms, for one filter pass over the whole image with 8 threads.

The JSON file next to the CSV is the run's record: which commit was built, the hashes of the binary and the WASM module, the CPU mask, governor, turbo and SMT, the browser version, the run's position in the shuffled order, the foreign CPU time, and the exact command that started it (ADR 0023, ADR 0027). It is what lets the analysis throw out a run that was not taken under the right conditions. More in The run record.

What to remember. A run is one fresh start of one program. The same Rust code times the workload in all three environments; the harness only differs in how it starts the program (flags or a URL) and how the result reaches the disk (printed, or posted to a local server). Every run ends as one CSV of times and one JSON of context.
