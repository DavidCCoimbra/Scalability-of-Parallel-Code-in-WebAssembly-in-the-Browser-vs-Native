The workflow: tickets, PRs, ADRs

Every change to this repository, from a comment to a campaign, goes the same way: a ticket, a branch, a pull request that CI and a reviewer look at, a squash merge. The author must be able to explain every line that lands, which is why the process is written down and why some things are off limits.

In one sentence: one ticket, one branch named after it, commits prefixed with its id, a PR from the template, CI green, the bot's findings fixed or answered, squash-merge; a decision gets an ADR, and AI_USE.md is written by the author alone.

A ticket, a branch, a PR

  1. The ticket lives in Linear (team DAV). It has a "done when" criterion; read it first, and if it is vague, make it verifiable before writing code.
  2. The branch is the one Linear suggests, dcoimbra/dav-NNN-short-title. Never work on main, never push to it.
  3. Commits start with the ticket id: DAV-NNN: what changed. Linear moves the ticket to In Progress from the branch, to In Review from the PR, to Done from the merge.
  4. The PR is filled from .github/pull_request_template.md: the ticket, what changed and why, the "done when" criterion as a checklist, how it was verified (Mac numbers are never results), and the pre-merge checklist.
Why a ticket for everything, even a comment? The course rule is that the author can explain every line, and the way to make that true months later is a trail: this line came from this PR, which answered this ticket, for this reason. A change without a ticket has no trail.

What CI checks

Every push to a PR runs .github/workflows/ci.yml. A first job looks at which folders changed and runs only the jobs that matter:

JobRuns whenWhat it does
changesalwaysDecides the others from the paths that changed
rustbench/** changedcargo test with both paddings, clippy, the SIMD parity check on the final native binary and WASM module (ADR 0017), the browser package from a clean checkout
browserbench/** or harness/** changedBuilds, then runs every workload small in headless Chrome and Firefox and checks their checksums equal native (ADR 0024)
docsalwaysThe Python tests of scripts/, harness/ and analysis/; the ADR structure; no em dash; this guide's data.js up to date; mypy --strict; shellcheck
paperpaper/** changedBuilds every PDF with LaTeX, checks the page limit, uploads the PDFs as an artifact

make test runs the same checks locally, minus LaTeX. Two of them only work on Linux (The common failures).

The bot review and the merge

  1. When the PR opens, .github/workflows/claude-review.yml runs an AI reviewer (claude[bot]) with the study's checklist (.claude/agents/methodology-reviewer.md): the timed region, warm-up, the same build in every environment, checksums, the unit of analysis. It posts inline comments and one ranked summary. It never pushes.
  2. Each finding is fixed in a commit, or answered in a comment that says why not. A comment posted on the author's behalf by the local assistant starts with [claude]; the author resolves the threads.
  3. CI green and the findings handled: squash-merge. One commit lands on main with the PR's title, so main's history is one line per change.
  4. After the merge, /merged DAV-NNN adds the ticket's raw material (decisions, numbers, problems, references) to docs/paper-material/, one file per paper section.
Why squash? A branch's twenty "fix typo" commits are useful while working and noise afterwards. One commit per PR means git log main reads as the list of changes, each with its ticket, and git bisect lands on a whole change.
Why a reviewer that is not the author? The author of a benchmark is the person least able to see its blind spots: a warm-up that is too short, a timed region that includes an allocation, a comparison across builds. The checklist is the list of ways this study could fool itself, run on every change (Four ways a study fools itself).

When a decision needs an ADR

An ADR (architecture decision record) is a short file in docs/adr/: context, decision, consequences, status. It is written when any of these changes:

  • a parameter of the protocol: thread counts, image size, warm-up, repetitions, the CPU mask, the start delay, what is headless;
  • the statistics: the plan, a test, a threshold, an exclusion rule;
  • the measured code, or anything that makes a new build;
  • how the harness controls the machine, or what it records;
  • the workflow itself, or what is reported from which build.

Numbering is sequential; a decision is never edited, only superseded by a later one that names it. scripts/check_adrs.py checks the structure in CI, and Decisions: the ADRs lists all of them by topic.

Why write decisions down at all? Because the paper has five pages and the defence has questions. "Why 30 runs?", "why 128 bytes?", "why not the E-cores?" each have an answer with the pilot data that gave it, and the ADR is where that answer waited. A decision in someone's head is lost by the second week.

What to remember. Ticket, branch, prefixed commits, PR from the template, CI, bot, squash. A changed parameter or statistic is an ADR before it is code. The author owns AI_USE.md and main.
