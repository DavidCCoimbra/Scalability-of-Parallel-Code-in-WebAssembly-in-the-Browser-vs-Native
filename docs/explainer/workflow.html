Contribute: branches, PRs and ADRs

Every change to this repository goes the same way: a branch, a small pull request that CI and a reviewer check, a squash merge. Commits and PR titles are Conventional Commits, a design decision gets an ADR, and AI_USE.md is written by the author alone. This guide gives each step and what is off limits.

A branch, small commits, a PR

  1. The change is small and has one purpose. The soft ceiling is about 500 changed lines per PR, cut along module boundaries; tests go in the same PR as the code they test. Mechanical PRs (campaign specs, ADRs, data, the paper) have no ceiling.
  2. The branch starts from origin/main and is named <type>/<short-name>, for example feat/bench-input. Never work on main, never push to it. PRs go one at a time: the next is opened after the previous one is merged.
  3. Commits and the PR title follow Conventional Commits: type(scope): description, in the imperative, lower case, no full stop, no ticket prefix. The types are feat, fix, refactor, perf, test, docs, build, ci, data and chore.
  4. The PR is filled from .github/pull_request_template.md: a summary, a Mermaid diagram of where the change fits, the paper figure it produces when there is one, and how it was verified (Mac numbers are never results).

Why

Why small PRs, one at a time? The course rule is that the author can explain every line, and nobody can explain two thousand lines read in one evening. A PR of one module with its tests can be read whole, and it leaves a trail: this line came from this PR, for this reason. A commit title in a fixed form makes that trail searchable.

What CI checks

Every push to a PR runs .github/workflows/ci.yml. A first job looks at which folders changed and runs only the jobs that matter:

JobRuns whenWhat it does
changesalwaysDecides the others from the paths that changed
rustbench/** changedcargo fmt --check, clippy for native and WASM, cargo test, the SIMD parity check on the final native binary and WASM module (ADR 0017), the browser package from a clean checkout
browserbench/** or harness/** changedBuilds, then runs every workload small in headless Chrome and Firefox and checks their checksums equal native (ADR 0024)
tablesanalysis/**, harness/**, data/** or the make targets changedmake tables-check: regenerates every table from the raw runs and fails if one differs from the committed one
pythonalwaysThe Python tests of scripts/, harness/ and analysis/; the ADR structure; this documentation's data.js up to date; mypy --strict; shellcheck

make test runs the same checks locally, minus the browser and the tables jobs. Two of them only work on Linux (The common failures).

The bot review and the merge

  1. When the PR opens, .github/workflows/claude-review.yml runs an AI reviewer (claude[bot]) with the study's checklist (.claude/agents/methodology-reviewer.md): the timed region, warm-up, the same build in every environment, checksums, the unit of analysis. It posts inline comments and one ranked summary. It never pushes.
  2. The author reviews every change; the bot is a double check. Its minor findings (style, naming, wording) are ignored. A finding that looks critical (a bug, a wrong number, a threat to the measurement) is discussed by the author before any reply or change. A comment posted on the author's behalf by the local assistant starts with [claude]; the author resolves the threads.
  3. CI green and the review read: squash-merge, by the author. One commit lands on main with the PR's title, so main's history is one line per change.
  4. After the merge: git switch main, git pull, and the next PR starts.

Why

Why squash? A branch's twenty "fix typo" commits are useful while working and noise afterwards. One commit per PR means git log main reads as the list of changes, each with its type and scope, and git bisect lands on a whole change.

Why

Why a reviewer that is not the author? The author of a benchmark is the person least able to see its blind spots: a warm-up that is too short, a timed region that includes an allocation, a comparison across builds. The checklist is the list of ways this study could fool itself, run on every change (Four ways a study fools itself).

When a decision needs an ADR

An ADR (architecture decision record) is a short file in docs/adr/: context, decision, consequences, status. It is written when any of these changes:

  • a parameter of the protocol: thread counts, image size, warm-up, repetitions, the CPU mask, the start delay, what is headless;
  • the statistics: the plan, a test, a threshold, an exclusion rule;
  • the measured code, or anything that makes a new build;
  • how the harness controls the machine, or what it records;
  • the workflow itself, or what is reported from which build.

Numbering is sequential; a decision is never edited, only superseded by a later one that names it. scripts/check_adrs.py checks the structure in CI, and Decisions: the ADRs lists all of them by topic.

Why

Why write decisions down at all? Because the paper has five pages and the defence has questions. "Why 30 runs?", "why 128 bytes?", "why not the E-cores?" each have an answer with the pilot data that gave it, and the ADR is where that answer waited. A decision in someone's head is lost by the second week.

What is off limits

RuleWhy
Never push to main; never force-push a shared branchEvery change goes through a PR and a review; a force-push rewrites what the review saw
AI_USE.md is written by the author onlyIt is the declaration of AI use the course requires; it must be the author's own words
No AI attribution lines in commits or PRsAI use is declared once, in AI_USE.md, not scattered in the history
Measurements only on the PC; Mac numbers are never resultsTwo machines, two jobs
No tracked edits in the checkout while a campaign runsThe run's commit becomes -dirty and the run fails strict validation
Never mix builds in one comparison; results only from measured/v3The rules and why
Never edit data/raw/Same
No em dash, documents in EnglishThe author's rule

In summary. A small change, a branch, Conventional Commits, a PR from the template, CI, the bot as a double check, squash. A changed parameter or statistic is an ADR before it is code. The author owns AI_USE.md and main.
