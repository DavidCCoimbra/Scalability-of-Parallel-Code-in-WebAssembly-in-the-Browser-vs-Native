The session of a build

Everything the study reports was measured in one long sitting on one machine, on one exact copy of the program. This page walks through that sitting from the first check to the last campaign: what was checked before a single result was taken, what went wrong, and how each problem was handled without letting the numbers decide.

In one sentence: check every core, build the program twice and compare, try a small rehearsal, write down the rules, and only then measure; when the rehearsal failed on one cell, the reason was found and recorded before the real campaign started.

Why the study was measured twice

The study was first measured on a copy of the program called measured/v2. Its results were valid. But writing them up left a list of things that could only be declared, not answered: the speedup had no plain sequential code to compare with, the two histograms did not split their work the same way, a few slow runs had no established cause, nobody knew for sure which of a browser's two compilers was being measured.

A new copy, measured/v3, fixes those, and every campaign was run again on it. The study reports v3 only.

Why not keep the v2 numbers and add the new ones next to them? Because two copies of a program are two different programs to a CPU. Moving a function by a few bytes can change a timing by a percent or two, for reasons that have nothing to do with what is being studied. A table that mixed runs of two builds would show differences that are only the build. So the rule is: one build per comparison, never mixed (ADR 0062), and the older data is kept apart at the tag data/v2.
Picture it. You timed runners on one track, then resurfaced the track. You cannot add new lap times to the old table: you run everybody again on the new surface and publish that table.

There is one more thing to be honest about. The v2 results were already known when v3 was measured. That makes v3 a replication with corrections, not a blind experiment. To keep the known numbers from steering any choice, every rule on this page was written down before any v3 run existed (ADR 0084).

The per-core check

The measuring PC has a known flaw: one of its eight fast cores (P-cores) is degraded. That had been known for weeks as "it fails at high frequencies", which is why turbo is off. Before building anything, the session tested every core on its own.

On the PC as found (turbo on, the usual desktop settings), a test program pinned to that core crashed in 17 of 18 tries, and in 0 of 28 tries on the other cores. On the prepared PC (turbo off, the settings every measurement uses) the same test passed 30 of 30 times on that core. Then the filter itself was timed on one core at a time:

Computed by scripts/explainer_data.py from the 80 runs in data/checks/core-check/runs/: the median over a CPU's 10 runs of each run's median iteration. A check, never a result.

CPU 12 is the degraded core. On the prepared PC it is as fast as the others, and all 80 runs gave the right checksum.

Why keep a flawed core in the measurement at all? The rule was fixed before the check ran: a core leaves only if it gives a wrong answer or crashes at the measuring conditions; a slower core would be reported with its number, not removed. Removing a core changes the largest thread count from 8 to 7 and with it the ten comparisons the study committed to. And deciding to remove it after seeing times would be choosing the design by the data. The check found neither a wrong answer nor a crash, so the core stays (ADR 0085).

The check changed three other things:

  • The build is made on the prepared PC. A failing core can compute wrongly without crashing, and the compiler is a program like any other. Hence the next section.
  • An old explanation lost its support. In v2, five filter runs with one thread were 21% slower than the rest, and the degraded core was the suspect. Pinned to that core the filter is not slow. In v3 the slow runs did not come back at all: no native filter run with one thread is more than 5% above the median.
  • A planned filter was dropped. The plan was to keep only runs whose core read near 3.2 GHz after the run. The check showed that the reading is taken while the core is already going idle and says anything between 1.2 and 3.2 GHz on a core that had just run at full speed. A filter built on it would have thrown away good runs at random, so it was dropped before it was ever used.

Built twice

The program that is measured is built once and then frozen: every one of the 27,150 runs of v3 uses the same files. So those files had better be right. The build stage compiles everything from scratch twice and compares the two results byte for byte, through their digests. Only if they agree is the commit given the tag measured/v3.

Every campaign then records the digests of the files it actually ran, in its campaign.json, so a table can be traced to these exact bytes.

Picture it. Before printing ten thousand copies of an exam, two people type it out independently and compare. If the two versions match letter for letter, a slip of the finger in one is very unlikely to have gone unnoticed.
If you already know this: what changed in the measured code between v2 and v3

Four changes, none an optimization (ADR 0086). (1) Every shared-counter histogram builds its tasks through the same grain control as the local one; the counting loops were compared by hand in the machine code and are identical to v2's (natively movzbl; shl $7; lock incq eight times per turn). (2) Two sequential workloads, filter-seq and hist-seq, with no Rayon call. (3) The memory size before the measured phase is written to the CSV, which showed that the 64 MiB of the output image are first touched in the warm-up. (4) Two unused options were removed.

One lesson is worth keeping: the first draft of the sequential filter called a helper of the parallel filter, and that changed the machine code of the parallel filter, because a function with two callers is no longer inlined. Adding a workload can change another one. The sequential filter got its own copy, and scripts/codegen_diff.sh confirmed the parallel one was back to the bytes of v2 (Change something safely).

The gate, and the cell that failed it

A campaign takes 14 hours. Finding out afterwards that a warm-up was too short would waste a night. So before the main campaign comes a gate: a small rehearsal of 135 runs at the real image size, on the cells whose code changed, checked on four criteria.

CriterionFirst gateSecond gate
Runs done, failed, excluded135, 0, 0135, 0, 0
Same output in all three runtimes and both thread countsyesyes
Every timed sample at least 100 times the clock's resolutionyesyes
First three measured iterations within 5% of the last three44 of 45 cells44 of 45 cells

One cell failed, and the plan had said in advance what to do: run the whole gate once more with another order. The same cell failed again. This is the check's own output, and the line that matters in its table:

So the session stopped, as designed, and the cell was looked at. In every one of its runs, one or two of the first three measured iterations take 21 to 22 ms and the others 19.7 ms. The 71 warm-up iterations before them show nothing of the kind. And it is not new: the v2 campaign has the same behaviour in the same cell, which nobody had seen because 30 runs dilute it under the limit.

Why go on with a failed gate, and why is that not cheating? Three options were on the table. Hunt for the cause first: hours of work that would not change the effect. Change the measurement (drop the first iterations, measure longer): that would alter the analysis after seeing data, which is exactly what the plan forbids. Or measure with the parameters as they are and declare the cell. The effect on the number that is actually analysed decides it: a run's value is the median of its ten iterations, and one or two slow ones out of ten do not move a median. Measured: 0.1%. So the campaign went ahead, and the gate is recorded as failed on one criterion in one cell, twice. It was not turned into a pass (ADR 0087).

The cell is Firefox, local histogram, k = 1, 8 threads: the control of one of the ten primary contrasts. The tier campaign later showed these slow early iterations come with Firefox's optimizing compiler (27 of 30 runs) and are almost absent with its baseline compiler (1 of 30). What they are is still not known.

Rules fixed before the data

The dangerous moment in any study is the one where you can see the numbers and still have a choice to make. The session removed those moments by writing the choices down first:

And the answer came out the same. All ten primary contrasts are rejected or not rejected on v3 exactly as on v2, with effects of the same sign.

Then the campaigns

With the gate recorded, the main campaign ran through the night, and the exploratory ones after it, ordered so that whatever had to be dropped for lack of time would be dropped from the end. Nothing had to be.

Across all of them: no failed run, no missing run, no run excluded, no checksum conflict.

The assistant stayed on, under a rule. In v2, the AI coding assistant on the PC was stopped during a campaign, so that nothing else used the machine. That also froze every terminal for 14 hours. For v3 it was kept running under one rule: while a campaign runs, no command is started on the PC, by the assistant or by hand. A rule cannot be checked, but what each run records can: the machine's load before it and the CPU time other processes took on the measured cores. Those are the same in the v3 campaign as in the v2 one (a 95th percentile of 0.036 s of foreign CPU time against 0.037 s). That is evidence of the same quiet, not proof that nothing ran, and the record says so (ADR 0087).
If you already know this: analysis on a restored PC

After the last campaign the PC was restored (turbo on). The first attempt to write the hybrid tables then stopped with a TypeError raised inside Python's own statistics module, on data the same command reads without error: a wrong computation, not a crash, on the degraded core. Since then, analysis on that PC outside a prepared session runs pinned away from CPUs 12 and 13, and CI regenerates every v3 table on another machine and compares it with the committed one (ADR 0094, From raw runs to the paper).

What to remember. Most of a trustworthy measurement happens before the measurement: check the machine, freeze the program, rehearse, and write down what you will do in each case. Then, when something does go wrong, you follow the rule instead of the numbers, and you write down what happened.
