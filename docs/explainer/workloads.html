Workloads

The study measures two kernels on a large grey image. A 3x3 Gaussian filter, where each thread works on its own rows and never waits: it answers RQ1. A histogram counted two ways, with shared atomic counters and with per-task local counters: the pair answers RQ2. The input parameter k sets how many counters the pixels are spread over, and so how much the threads contend.

Why

Why these two kernels and not something larger? Each is a few dozen lines, so you can read the whole measured loop and see that nothing is hidden in it. One has no coordination; the other has exactly one kind. Both produce a result that can be hashed and compared, so every environment is checked to compute the same thing. A real application would mix many effects that could not be separated.

Every workload implements one small interface. Only run is timed: prepare resets state before the timed region, and checksum hashes the result after it.

In depth: the interface in Rust

The Gaussian filter

A blur softens an image. Each output pixel is the weighted average of itself and its eight neighbours, with the centre weighing most:

The image is 8192 x 8192 pixels, 67 million of them. Row 100 of the output needs only rows 99 to 101 of the input, and no thread writes the input. So each thread takes a group of rows, filters them into its own part of the output, and never waits for another thread. No workload is more parallel than this, which is why it answers RQ1: whatever slows it down in the browser is the environment, not coordination.

In depth: the timed loop, the kernel and SIMD

Rayon splits the output into one-row chunks and groups them into tasks; one thread filters the rows of a task in place.

The kernel is the integer binomial 1-2-1, with weights that sum to 16, so the division is a shift. The weights are checked at compile time, and the largest sum fits in 16 bits, which lets SIMD process eight pixels per 128-bit register on both sides (SSE2 natively, simd128 in WASM).

The histogram, two ways

A histogram counts how many pixels have each grey level. There are 256 grey levels, so the result is 256 numbers:

With eight threads, each thread reads its own share of the pixels. The two variants differ in where they count:

hist-atomic: shared

One table of 256 counters that all threads share. For every pixel, a thread adds 1 to the counter of that grey level with an atomic add, so that two threads that add at the same moment never lose a count. This is the synchronization the study measures.

hist-local: the control

Each task counts into its own plain table, and the tables are merged in pairs at the end. Nothing is shared while counting, so there is no atomic add.

Why

Why does the shared version need atomic adds? A plain add is three steps: read the count, add one, write it back. If two threads do them at the same moment on the same counter, both read the same old value and one count is lost. An atomic add does the three steps as one indivisible step. Atomic operations explains what that costs.

Both variants give the same 256 counts, and a test checks it. They differ only in where the counting happens. The 256 shared counters are padded so that no two sit on the same cache line (False sharing and padding).

In depth: the two loops, the add, and the two extra variants

Two more variants appear only in the extras campaign (Private and packed atomics):

  • hist-atomic-private: one padded atomic table per thread, merged at the end. It runs the same atomic instruction as hist-atomic, but no core touches another's counters: the cost of the instruction with nothing shared.
  • hist-atomic-packed: counters of 8 bytes, eight per cache line, without padding: what false sharing adds.

Both timed loops end with their result stored: the merged histogram, or the counters read back. Allocation and the reset of the counters happen in prepare, outside the timed region, because the default WASM allocator takes a global lock, which would add a second kind of synchronization to the measurement (ADR 0014).

k: the contention dial

If the image had one grey level, all eight threads would add to the same counter all the time: the most contention possible. With 256 grey levels evenly spread, the adds spread over 256 counters, and two threads rarely want the same one at the same moment. The study generates images with exactly k distinct grey levels, k = 1, 4, 16 or 256, and times the histograms on each. k = 1 concentrates the contention on one counter; k = 256 spreads it thin.

Why

Why more than one input? "How much synchronization costs" has no single answer: it depends on how many threads want the same thing at once. With one input the study could only say "in this case". With four values of k you see the shape, and Chrome behaves differently at its two ends.

A speedup below 1 means that eight threads are slower than one. At k = 1, every add waits for the counter's line to come back from the core that wrote it last (Contention). The local histogram scales almost ideally at every k. RQ2: synchronization compares the environments.

In depth: how the k shades are chosen

Grey level i of k is i x 256 / k, so the levels are spread over the range and, with the padding, over k different cache lines. The same random draws choose the level of each pixel for every k, so only the contention changes between inputs, not the pattern of accesses.

Inputs and checksums

The images are not read from files. A generator produces them from a fixed seed, so every environment gets the same bytes. The filter reads an image of uniform random pixels (noise); the histograms read an image with k grey levels (few).

Why

Why generate the image instead of loading a photo? A file could differ between machines, or a browser could read it slightly differently. A generator with a seed gives the same 67 million bytes everywhere, and every run records a fingerprint of them to prove it.

Two hashes protect the comparison:

  • the input fingerprint, a hash of the generated image: the same input everywhere;
  • the checksum, a hash of the result (the filtered image, or the 256 counts): computed after every iteration and required to be equal across iterations, thread counts and environments. If any two differ, the analysis refuses to run.

Why

Why hash the result? A compiler that sees that a result is never used may skip the work; hashing the result forces it to be computed. And a timing that comes with a wrong result is not a timing of the same work: a bug in one environment would make it look faster.

In the main campaign of 5310 runs no checksum differed (The data check).

In depth: the generator and the hash

A SplitMix64 generator seeded with 0x5EED; both hashes are FNV-1a.

In summary. The filter has no coordination and measures the environment alone. The histogram is counted twice, with shared atomic counters and with local counters, and the gap between the two is the cost of sharing. k sets how much the threads contend for the shared counters. Every result is hashed, so a wrong answer cannot pass as a fast one.
