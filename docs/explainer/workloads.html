The workloads

Two small jobs on a big grey image. A blur, where every thread works on its own rows and never waits for anyone. A histogram, counted two ways: with one shared tally that every thread adds to, and with private tallies added up at the end. The difference between the two ways is the cost of sharing.

In one sentence: the blur answers RQ1 (no coordination at all), the pair shared / private histogram answers RQ2, and a number called k turns the fighting over the shared tally up or down.
Why these two jobs and not something bigger? Each is a few dozen lines, so anyone can read the whole measured loop and see there is nothing hidden in it. One has no coordination; the other has exactly one kind. Both produce a result that can be hashed and compared, so every environment is checked to compute the same thing. A real application would mix many effects we could not pull apart.

Every workload implements one small interface. Only run is timed; prepare resets state before the clock starts, and checksum hashes the result after it stops.

The Gaussian filter

A blur makes an image softer. Each output pixel becomes the average of itself and its eight neighbours, with the centre weighing most:

The image is 8192 x 8192 pixels, 67 million of them. Row 100 of the output only needs rows 99 to 101 of the input, and nobody writes the input. So each thread takes a group of rows, blurs them into its own part of the output, and never needs to wait for another thread. This is as parallel as a job can get, which is why it answers RQ1: whatever slows it down in the browser is the runtime, not coordination.

Picture it. Eight people each colouring their own rows of a paint-by-numbers. They look at the lines next to theirs, but nobody paints on anyone else's rows, so nobody waits.
If you already know this: the timed loop, the kernel and SIMD

Rayon splits the output into one-row chunks and groups them into tasks; the rows of a task are blurred in place by one thread.

The kernel is the integer binomial 1-2-1, summing to 16, so dividing is a shift. The weights are checked at compile time, and the largest sum fits 16 bits, which lets SIMD work on eight pixels per 128-bit register on both sides (SSE2 natively, simd128 in WASM).

The histogram, two ways

A histogram counts how many pixels have each shade of grey. There are 256 shades, so the result is 256 numbers:

With eight threads, each thread looks at its own share of the pixels. The question is where it counts:

Picture it: a vote in a classroom of 256 options. Shared tally: one sheet on the board, and every student walks up and adds a mark. Two students who want the same line at the same time have to wait for each other. Private tallies: every student keeps a sheet at their desk, and at the end the sheets are added up. Nobody waits during the vote; the only extra work is adding the sheets.

hist-atomic: shared

One table of 256 counters shared by all threads. For every pixel, the thread adds 1 to the counter of that shade with an atomic add, so that two threads adding at the same moment never lose a count. This is the coordination being measured.

hist-local: the control

Each task counts into its own plain table. At the end the tables are merged in pairs. Nothing is shared while counting, so no atomic adds at all.

Why does the shared version need "atomic" adds? A plain add is three steps: read the count, add one, write it back. If two threads do those three steps at the same moment on the same counter, both read the same old value and one count is lost; the histogram would be wrong. An atomic add does the three steps as one indivisible step. What that costs, and why it costs more in Chrome, is Atomics in machine code.

Both versions give exactly the same 256 counts, and a test checks it. They differ only in where the counting happens. The 256 shared counters are kept apart in memory so that two of them never sit on the same cache line; why that matters is padding.

If you already know this: the two loops, the add, and the two extra variants

Two more variants appear only in the exploratory campaign (Private and packed atomics):

  • hist-atomic-private: one padded atomic table per thread, merged at the end. The same atomic instruction as hist-atomic, but no core ever touches another's counters: the cost of the instruction alone, with no sharing.
  • hist-atomic-packed: counters of 8 bytes, eight to a cache line, with no padding: what false sharing adds.

Both timed loops end with their result stored: the merged histogram, or the counters read back. Allocation and the reset of the counters happen in prepare, outside the clock, because WASM's default allocator takes a global lock, which would add a second kind of synchronization to the measurement (ADR 0014).

k: the contention dial

If the image only had one shade, all eight threads would add to the same counter, all the time: the worst possible fight. If it had 256 shades evenly spread, the adds would spread over 256 counters and two threads would rarely want the same one at the same moment. The study makes images with exactly k distinct shades, with k = 1, 4, 16 or 256, and times the shared histogram on each. k is a dial: 1 is all the fighting concentrated on one counter, 256 is the fighting spread thin.

Why not just one input? Because "how much synchronization costs" has no single answer: it depends on how many threads want the same thing at once. With one input we could only say "in this case". With four settings of the dial we can see the shape, and, as it turned out, Chrome behaves differently at the two ends of it.

Read the table like this: a speedup below 1 means eight threads are slower than one. Natively, at k = 1, eight threads on one shared counter take more than twice as long as one thread, because every add has to wait for the counter to come back from whichever core wrote it last (Contention). The private control scales almost perfectly at every k. How the browsers differ is RQ2: synchronization.

If you already know this: how the k shades are chosen

Shade i of k is i x 256 / k, so the shades are spread over the range and, with padding, over k different cache lines. The same random draws pick the shade of each pixel for every k, so only the contention changes between inputs, not the pattern of accesses.

Inputs and checksums

The images are not read from files; they are generated by a fixed recipe from a fixed starting number (a seed), so every environment gets exactly the same bytes. The blur reads an image where every pixel is random (noise); the histogram reads an image with k shades (few).

Why generate instead of loading a photo? A file could differ between machines, or be read slightly differently by a browser. A recipe with a seed gives the same 67 million bytes everywhere, and a fingerprint of them is recorded with every run to prove it.

Two hashes protect the comparison:

  • the input fingerprint, a hash of the generated image: the same input everywhere;
  • the checksum, a hash of the result (the blurred image, or the 256 counts): computed after every iteration and required to be equal across iterations, thread counts and environments. If any two differ, the analysis refuses to run.
Why hash the result at all? Two reasons. A compiler that notices a result is never used may skip the work; hashing the result forces it to be computed. And a timing that comes with a wrong result is not a timing of the same job: a bug in one environment would make it look faster.

In the main campaign of 4860 runs no checksum differed (The data check).

If you already know this: the generator and the hash

A SplitMix64 generator seeded with 0x5EED; both hashes are FNV-1a.

What to remember. The blur has no coordination and measures the runtime alone. The histogram is counted twice, with a shared tally and with private tallies, and the gap between them is the cost of sharing. k says how hard the threads fight over the shared tally. Every result is hashed, so a wrong answer can never pass as a fast one.
