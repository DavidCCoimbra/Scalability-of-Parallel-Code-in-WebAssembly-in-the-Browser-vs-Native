Debug a run

A campaign of thousands of runs will sometimes have one that fails: a browser that did not post its result in time, a checksum that disagrees, a machine that was not prepared. The harness records the failure next to the good runs and keeps going. This guide shows you how to find what failed (make status), when (campaign.jsonl), why (the run's .error.json), and how to replay one run while you watch.

Start from make status

make status SPEC=harness/campaigns/<name>.json

make status reads only the two journal files of the campaign, never the machine, so you can run it while a campaign runs. Read these lines:

  • progress: done, failed and remaining, then the same per environment. If one environment fails more than the others, the cause is in that environment (a browser that is not the pinned version, a profile problem), not in the machine.
  • problems: what the strict checks found in the runs so far (an escaped process, foreign CPU time, a context key that could not be read). none is the normal line.
  • sessions: how many times the campaign was started. More than one is normal: the campaign was stopped and resumed.
  • last run: its id and age. A last run that is minutes old, with remaining > 0 and no progress, is a hung run; the orchestrator kills it at timeoutSeconds.

Why

Why does the harness not stop at the first failure? One failed browser run in 5310 is not unusual, and a campaign that stops at 3 in the morning wastes the night. The harness records the failure and goes on. The data check then refuses to analyse a campaign with a failed run until the run is repeated or excluded with a reason (The data check).

The run's records

Everything that a run leaves is in data/raw/<name>/, named by its id:

FileWhen it existsWhat to read in it
campaign.jsonlAlways; one line per run as it finishedstatus (done or failed), seconds, problems. grep failed campaign.jsonl lists the failed ids in order.
<run>.error.jsonThe run failedThe same context as a good run's JSON plus the error: a timeout, a non-zero exit, a missing result, a validation problem. The run counts as failed until it is run again.
<run>.browser.logA browser run did not finishThe browser's own output: a crashed tab, a page that could not load the WASM module, a policy error. Deleted when the run succeeds.
<run>.json and .csvThe run succeededThe context and the times. A succeeded run can still be wrong: a checksum that differs from the others, or a context that fails strict validation. Those are found by the data check, not by status.
failed/After --retry-failedThe previous attempt's files, moved aside so the retry starts clean; a second retry adds .attempt2.
sysinfo/Strict campaigns, one file per sessionThe machine state at each start: governor, turbo, SMT, mask, shield, browser versions, with any problem found. The first thing to compare when a later session behaves differently.

Re-run one id by hand

The launchFlags key of the JSON of a run is the exact command the orchestrator used. To replay one run outside a campaign, with its output in your terminal:

# a native run, no scope and no mask (fine on the Mac)
python3 -m harness.native --run debug-filter-n8 --results data/raw/debug \
  --query "workload=filter&input=noise&threads=8&width=4096&height=4096&warmup=5&iters=10&calibration=20"

# a browser run: the launcher starts the results server itself
python3 -m harness.launcher --browser chrome \
  --executable harness/browsers/chrome-155.0.8059.84/chrome-linux64/chrome \
  --run debug-chrome-filter-n8 --results data/raw/debug --headless \
  --query "workload=filter&input=noise&threads=8&width=4096&height=4096&warmup=5&iters=10&calibration=20"

Drop --headless to see the browser window and its console. On the PC, add --cpus 0,2,4,6,8,10,12,14 and --scope-user $USER to reproduce the conditions of the campaign.

To run the failed runs of a campaign again, at their position in the order:

make campaign SPEC=harness/campaigns/<name>.json   # resumes; skips what is done, skips failed
python3 -m harness.campaign harness/campaigns/<name>.json --retry-failed   # runs the failed ones again

Why

Why does a plain resume skip failed runs? So that a failure you have not read is not repeated and overwritten without notice. You decide, after reading the error, whether to retry. --retry-failed moves the old files to failed/ and keeps the attempt count.

Something broke: where to look has a longer list, by symptom.

In summary. Read the status, then the journal, then the error file, then replay the one run by hand with its own launchFlags. Retry only after you know why it failed. The data check, not the status, says whether the campaign can be analysed.
