RQ1: scaling

RQ1 asks whether the same parallel code gains from threads in the browser as it does natively. The filter and the local histogram answer it: their threads never wait for each other. With enough work per parallel region they scale in the browsers as they do natively, and the browser is slower by a factor that does not grow with the thread count.

If you have not yet read Ratios, speedup and intervals, read it first: this page is written in those terms.

Speedup curves

Speedup answers "how many times faster is it with N threads than with 1?", inside one runtime. 2 threads giving speedup 2 is perfect; 8 threads giving 7 is very good. The dashed line in the chart is perfect. Pick a workload and compare the three environments:

Workload:

The three lines sit on top of each other. That is the result: adding threads helps the browser as much as it helps native code. Each dot is the middle of 30 separate runs, and the shaded band around it says how much that middle could move with another 30 runs (How sure: the interval). The bands are so narrow you can barely see them.

Why

What would it look like if WASM scaled worse? The browser lines would start near native's at N = 1 and bend away below it as N grew: 8 threads giving, say, 4 instead of 7. Then the gap between browser and native would be a cost of parallelism, growing with every thread. The lines do not bend away, so it is not.

A yardstick for efficiency. Efficiency is speedup divided by N: the share of each thread's time that turned into useful work. 1.0 is perfect; above 0.8 is considered good for memory-heavy code like an image filter, because the 8 threads share one memory bus. The filter's 0.87 natively, 0.87 in Chrome and 0.92 in Firefox at N = 8 are all in that range.

In depth: the superlinear Firefox value, and why the ratio must come with the speedup

The filter reaches about 7 at N = 8 everywhere. The local histogram reaches 7.8 to 8.5; Firefox's value above 8 at k = 256 (8.48) starts from a slower T1 (1.27 times native), not from faster threads: its one-thread run pays for cache misses that its eight-thread run does not (question 5). A relative speedup compares each environment with itself, so an environment with a slow single thread can show a high speedup and still be slower in seconds. That is why every speedup in this documentation is read next to the time ratio browser / native (ADR 0039), the next section. The paper reports this reading in paper/final/paper.tex, section RQ1.

Browser over native

Speedup hides one thing: it never says who is faster in seconds. So here is the same question in seconds: how many times longer does the browser take than native, for the same workload and the same N? A value of 1.2 means "20% slower than native".

Workload:

This is the headline of RQ1: the line is flat. The browser is about 1.17 (Chrome) to 1.36 (Firefox) times slower than native on the filter with one thread, and about the same with eight (1.18 and 1.29). The cost of running in the browser is a factor per thread that does not grow as threads are added: Chrome's stays about the same and Firefox's falls from 1.36 to 1.29. It gets divided by N like everything else.

Why

Why the flat line is the test, and not the speedup alone. Two environments can both have a speedup of 7 and still be far apart in seconds; the speedup alone would hide that. And a browser could have the same speedup at N = 2 but fall behind at N = 8; the speedup at one N would hide that too. A ratio that stays flat across every N rules both out at once.

In depth: the primary RQ1 contrast and the k = 1 instruction aside

The primary RQ1 contrast is the filter's speedup at N = 8, browser over native, tested with Holm over the 10 primary contrasts fixed before the campaign (Ten decisions, a stricter bar):

Chrome's filter speedup is within a few percent of native's and the interval contains 1. Firefox's is 5.5% higher and Holm-significant, but from a slower baseline. In seconds the filter on one thread is 1.17 times native in Chrome and 1.36 in Firefox, and the ratio does not grow with N: WASM threads cost a factor per thread, not scalability. Why Firefox scales a little better is not that it runs threads better: its loop is slower, and eight slower loops ask less of the shared memory (What explains the results).

Note

Chrome faster than native at k = 1. On the local histogram at k = 1, every pixel increments the same counter, a chain bound by store forwarding. V8 compiles it as a load, an add and a store; LLVM as one memory-operand inc. Chrome ends up about 2.7% faster than native there, a likely part of the reason being the instruction choice (ADR 0060, and Store forwarding at k = 1). The local histogram at k = 1: one counter, one chain

At k = 1 every pixel adds to the same counter, so each add waits for the one before it (Store forwarding at k = 1 explains the mechanism). That is why the local histogram is several times slower at k = 1 than at k = 256 with one thread, in every environment, and it is where Chrome ends slightly faster than native:

At k = 1 the loop is a dependency chain through memory: the new value goes from the store buffer straight to the next load (store-to-load forwarding), and no pixel can start before the previous one finished. Here Chrome is even slightly faster than native. LLVM emits one memory-operand inc per pixel; V8 emits a separate load, add and store:

On this core the memory-operand inc chain is about 1.5 to 2 % slower. A C probe of the two sequences alone on one P-core (bench/probes/rmw_chain.c, ADR 0060) took 155.2 ms against 152.7 ms, about 60 % of the gap; it explains a design result, it is not a campaign number. The lesson the paper draws: one source and one set of flags do not give one instruction stream; the engine's code generator is part of what is measured.

Fork-join in the results

One cost does not get divided by N: starting the threads on a piece of work and waiting for them all to finish, the fork-join (Fork-join and its cost). Every run measures it before its workload, by timing an empty parallel region: all the threads are woken up, do nothing, and are collected again.

Probe:

Computed by scripts/explainer_data.py from the calibration-warm rows of every run in data/raw/campaign-v3/: the median over runs of each run's median of 20 calls, and the mean of all calls.

At N = 8 one empty fork-join costs about 110 µs in Chrome and 60 µs in Firefox against 7.9 µs natively: eight to fourteen times more. That sounds bad, until you compare it with the work: one filter pass over the 8192 x 8192 image takes several milliseconds, so the fork-join is about 3% of it in Chrome and 0.2% natively. With big pieces of work it is noise; with pieces of a few hundred microseconds it is the main cost. Exploratory campaigns measures exactly where that line is.

In depth: the step at N = 8 and the clock ticks

All three runtimes step up at N = 8, likely because the coordinating thread then shares the 8 cores with N workers; below N = 8 the browser values are one or two clock ticks (performance.now() is 5 µs in Chrome and 20 µs in Firefox), so the browser medians there are coarse. The N = 8 medians are 110, 60 and 7.9 µs and the means 164, 91 and 46 µs; Fork-join calibration explains the warm and cold probes.

The answer to RQ1

With enough work per parallel region, the same Rust/Rayon code scales in the browser as it does natively. The filter's efficiency at N = 8 is 0.87 natively, 0.87 in Chrome and 0.92 in Firefox; the speedups agree within a few percent; and the browser / native time ratio does not grow with N, in strong and in weak scaling (Weak scaling). WASM costs a factor per thread that does not grow with N, and it divides with the work. What does not divide is the fork-join of each region, several times slower in the browsers.

In summary. Threads help the browser as much as they help native code. The browser is 17 to 36% slower per thread on the filter, and that does not get worse with more threads. The one thing that stays expensive is starting and stopping the threads, so keep each parallel piece of work big.

In depth: where the constant factor and the lost efficiency come from

The literature points to the engines' code generation and bounds-checked linear-memory accesses as the source of the per-thread factor (Jangda et al. 2019, Szewczyk et al. 2022). The counters of the loop measured it for the filter: both engines run about a third more instructions per pixel than native code (question 3). The lost efficiency (0.87, not 1) is not a serial part: the timed region has none. The filter's Karp-Flatt serial fraction at N = 8 is small in all three (Karp-Flatt) and reads as a cost of running in parallel. With eight threads a pixel costs the same instructions and more cycles (8.5% more natively), with more cache misses: the eight threads run into the memory they share. That explains about half of the lost efficiency natively; the rest is time in which a core is not running the loop at all (question 1). The SIMD builds on Exploratory campaigns point the same way for the native builds and for Firefox: the faster one thread goes through memory, the less eight threads gain. Chrome does not fit that line: it goes through memory more slowly than native and has the native efficiency.
