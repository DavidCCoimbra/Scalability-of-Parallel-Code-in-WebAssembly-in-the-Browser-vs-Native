Installation and first run

This guide takes about an hour. You install the toolchain, build the native runner and the WebAssembly package, run one workload, read one row of its output, and run the tests. Every command works on a Mac or on Linux. Nothing you run here is a result of the study: results come only from the measuring PC.

Two machines, two jobs

The project uses two computers, each for one job.

The Mac: where code is written

  • Build, run the tests, read and change the code
  • Run the native program to see what it prints
  • Its times are never a result

The Linux PC: where numbers are made

  • Its CPU is prepared: P-cores set aside, clock fixed, nothing else running
  • The pinned browsers are installed there
  • Every number of the paper comes from it

Why

Why can a time from the Mac never be a result? The Mac has a different chip, its clock speeds up and down by itself, and other programs share it. A number from it compares the Mac with the PC, not Chrome with native. A fair comparison explains the rule; The machine and environment control shows what the PC does about each point.

Install and build

You need three things: Rust (the compiler of the workloads), Python 3 (the harness and the analysis use only its standard library), and uv (it runs the type checker and the plotting library without making them project dependencies). Then, from the repository folder:

make toolchain wasm-bindgen   # Rust's nightly compiler of one fixed date, and the WASM packager
make build                    # the native program and the WASM package

make runs named recipes. The recipes are in Makefile and make/*.mk, and make help lists them. make build has two steps:

Why

Why a nightly compiler of one fixed date? WebAssembly with threads needs a compiler feature that only Rust's nightly builds have. A fixed date means that you and the measuring PC compile with the same compiler, so a difference between two builds is never "a different compiler".

The build gives you bench/target/release/native, the native program, and bench/www/pkg/, the WASM module with the small JavaScript file the browser loads. On the PC, make setup also downloads the two pinned browsers, and make deps sudoers chrome-apparmor prepares the system once (Commands has the full list).

Run one thing

The native program takes its whole configuration as flags and prints one line per timed iteration. A small image keeps the run to about a second:

bench/target/release/native --workload hist-atomic --input few --k 4 --threads 8 \
  --width 1024 --height 1024 --warmup 2 --iters 5

Read the flags as a sentence: the histogram with shared counters, on an image with few grey levels (4 of them), with 8 threads, 1024 by 1024 pixels, 2 warm-up iterations and then 5 measured ones. Each part has its page: Workloads, k, warm-up.

In the browser the same options go in the page's address, and the page posts the result to a small local server. That needs the pinned browsers; A browser run shows it. To try the whole pipeline on any machine without preparing it, run make quick-rq1: a small copy of the main campaign that takes about two minutes. Its numbers are never results.

Read one row

The program prints a CSV table (values separated by commas), one row per iteration. This is the header and one row of the main campaign, a native run of the filter with 8 threads:

The fields that matter today:

FieldIn this rowWhat it means
env, workload, inputnative, filter, noiseWhere it ran, which dish, which picture. A browser run says chrome or firefox here.
k(empty)How many shades of grey the histogram's picture has. The filter does not use it.
width, height8192, 8192The picture's size in pixels: 67 million of them.
threads8N, how many threads did the work.
phase, itermeasured, 0Which part of the run this row is, and which round. The first rows of a run are calibration-* (timing the cost of handing out work) and warmup (untimed rounds); only measured rows count.
ns3274887The time of this round in nanoseconds: 3.27 ms to blur the whole picture with 8 threads.
checksum0x0c94a2fe…A fingerprint of the output picture. It must be identical for every thread count and every environment; if it is not, the result was wrong and nothing else matters.

Why

Why a checksum on every row? A parallel program that gives a different answer with 8 threads than with 1 has a bug, and timing a bug is pointless. And a compiler that sees nobody reads the output may skip the work; a printed checksum forces it to be computed. Inputs and checksums has the details.

The other fields record the conditions of the run (memory used, where the buffers sat in memory, the fingerprint of the input), so that an odd number can be explained later. Data files, CSV schema and tables describes every field.

Run the tests

make test     # Rust tests, Python tests, then the lint

The tests check in code what the checksum checks in a run: every workload against a one-thread version, at every thread count from 1 to 8. One of them:

make lint checks formatting, Rust's warnings, the structure of the decision records, that the data file of this documentation is up to date, and Python's types. On a Mac two of its checks fail on Linux-only code. The same checks pass in CI, which runs on Linux, so there is nothing to fix.
