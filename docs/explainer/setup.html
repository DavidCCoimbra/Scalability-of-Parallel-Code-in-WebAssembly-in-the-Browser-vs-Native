Installation and first run

By the end of this page you will have built the project, run it once, read what it printed, and run its tests. Every command here works on the Mac. Nothing you do today produces a result for the paper; that only happens on the measuring PC, and the page says where that line is.

In short: make setup, make build, one native run, one CSV row read field by field, make test: an hour, and you can read the rest of the guide with the code in front of you.

Two machines, two jobs

The project lives on two computers on purpose.

The Mac: where code is written

  • build, run the tests, read and change the code
  • run the native program to see what it prints
  • its times are never a result

The Linux PC: where numbers are made

  • its CPU is prepared: fast cores set aside, clock fixed, nothing else running
  • the pinned browsers live there
  • every number in the paper comes from it

Why

Why can a time from the Mac never be a result? It has a different chip, its clock speeds up and down by itself, and other programs share it. A number from it would compare the Mac to the PC, not Chrome to native. A fair comparison explains the rule; The machine and its controls shows what the PC does about each of those.

Install and build

Three things need to be on the machine: Rust (the compiler for the workloads), Python 3 (the harness and the analysis use only its standard library), and uv (runs the type checker and the plotting library without making them project dependencies). Then, from the repository folder:

make toolchain wasm-bindgen   # Rust's nightly compiler of one fixed date, and the WASM packager
make build                    # the native program and the WASM package

make is a tool that runs named recipes; the recipes live in Makefile and make/*.mk, and make help lists them. make build is two steps:

Why

Why a nightly compiler of one fixed date? WebAssembly with threads needs a compiler feature that only Rust's nightly builds have. Fixing the date means everyone, and the measuring PC, compiles with exactly the same compiler, so a difference between two builds is never "a different compiler".

What you get: bench/target/release/native, the native program, and bench/www/pkg/, the WASM module with the small JavaScript file the browser loads. On the PC, make setup also downloads the two pinned browsers, and make deps sudoers chrome-apparmor prepares the system once (Every command has the full list).

Run one thing

The native program takes the whole configuration as flags and prints one line per timed round. A small image keeps it to about a second:

bench/target/release/native --workload hist-atomic --input few --k 4 --threads 8 \
  --width 1024 --height 1024 --warmup 2 --iters 5

Read the flags as a sentence: the histogram with shared counters, on a picture with few shades (4 of them), using 8 threads, 1024 by 1024 pixels, 2 untimed rounds then 5 timed ones. Every word of that sentence is a page of this guide: The workloads, k, warm-up.

In the browser the same options go in the page's address instead of on the command line, and the result is sent to a small local server rather than printed. That needs the pinned browsers and belongs to the PC; A browser run shows it. To try the whole pipeline on the Mac without preparing anything, make quick-rq1 runs a tiny copy of the main campaign in about two minutes. Its numbers are never results either.

Read one row

The program prints a table in CSV form (values separated by commas), one row per round. Here is the header and one real row from the campaign the paper uses, a native run of the filter with 8 threads:

Field by field, the ones that matter today:

FieldIn this rowWhat it means
env, workload, inputnative, filter, noiseWhere it ran, which dish, which picture. A browser run says chrome or firefox here.
k(empty)How many shades of grey the histogram's picture has. The filter does not use it.
width, height8192, 8192The picture's size in pixels: 67 million of them.
threads8N, how many threads did the work.
phase, itermeasured, 0Which part of the run this row is, and which round. The first rows of a run are calibration-* (timing the cost of handing out work) and warmup (untimed rounds); only measured rows count.
ns3274887The time of this round in nanoseconds: 3.27 ms to blur the whole picture with 8 threads.
checksum0x0c94a2fe…A fingerprint of the output picture. It must be identical for every thread count and every environment; if it is not, the result was wrong and nothing else matters.

Why

Why a checksum on every row? Two reasons. A parallel program that gives a different answer with 8 threads than with 1 has a bug, and timing a bug is pointless. And a compiler that notices nobody reads the output may skip the work entirely; a checksum that is printed forces it to be computed. Inputs and checksums has the details.

The other fields record the conditions of the run (memory used, where the buffers sat in memory, the picture's own fingerprint) so that a strange number can be explained later. Data folders and files reads every one of them aloud.

Run the tests

make test     # Rust tests, Python tests, then the lint

The tests check what the checksum checks, in code: every workload against a plain one-thread version, at every thread count from 1 to 8. One of them:

The lint part (make lint) checks formatting, Rust's own warnings, the shape of the decision records, the "no em dash" rule, that this guide's data file is up to date, and Python's types. On a Mac two of its checks complain about Linux-only code; the same checks pass in CI, which runs on Linux. That is expected, not something to fix.
