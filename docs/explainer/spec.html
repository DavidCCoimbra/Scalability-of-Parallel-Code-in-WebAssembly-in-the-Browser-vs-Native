Campaign spec format

A campaign spec is one JSON file in harness/campaigns/ that holds every parameter of a campaign. This page lists every key: its type, its default, and what it does. The harness rejects a spec with a key that is not listed here.

Example

The spec of the main campaign, as it is in the repository:

Run a spec with make campaign SPEC=harness/campaigns/<file>. Its runs land in data/raw/<name>, and the harness stores the spec in campaign.json there; a resumed campaign must find an identical spec (Sessions, status and resume).

Optional keys

KeyTypeDefaultWhat it does
cpusstring, a CPU listnoneThe CPU mask of every run (ADR 0001, ADR 0045). Required when strict is true. The main campaign uses 0,2,4,6,8,10,12,14, the eight P-cores
harnessCpusstring, a CPU listnoneWhere the harness and the results server run (ADR 0028). The main campaign uses 16-31, the E-cores
hybridbooleanfalseDeclares that the mask holds P-cores and E-cores, for the hybrid campaign (ADR 0059)
scopeUserstring or nullnoneRuns each run in its own systemd scope as this user, so that its CPU time and escaped processes are counted (ADR 0045). $USER means the current user; null runs without a scope and without sudo
headlessbooleantrueBrowsers without a window (ADR 0046)
startDelayMsinteger0Wait between the page loading and the run starting, so that the browser's start-up work is over (ADR 0048). The campaigns of the study use 3000
timeoutSecondsnumber300A run longer than this is killed and recorded as failed
discardFirstLaunchbooleanfalseOne extra launch per browser and session that is not kept: the first launch on a machine is much slower (ADR 0034)
strictbooleanfalseRefuses to start unless the machine is prepared and the browsers are the pinned versions, and validates the context of every run (ADR 0040, ADR 0071)
heightPerThreadinteger, at least 1noneWeak scaling: the image height is this value times N (ADR 0055)
buildbaseline, scalar or avx2baselineThe build variant the campaign runs (ADR 0057)
passesinteger, at least 11Calls of run per timed sample, for images too small for the browser clock (ADR 0064). Only workloads that repeat identically accept more than 1
engineArmslist of engine arm objectsnoneCrosses every browser run with these arms. It needs a browser in environments, and the arm names must differ (ADR 0084)
commentstringnoneFree text. The harness ignores it

Note

passes, comment and engineArms were added after the first campaigns. The harness leaves them out of the stored spec while they are unset, so that an older campaign still resumes against an identical spec.

Workload objects

Each entry of workloads is one workload on one input. A key that is not listed is rejected.

Engine arm objects

An engine arm is one way of starting the browsers. Arms are a dimension of the plan: they are shuffled into the run order like everything else, and every run records its arm. Only the tier campaign uses them.

KeyTypeDefaultWhat it does
namestring of lowercase letters and digitsrequiredThe arm's name, part of the run id
chromeJsFlagslist of flags like --name, without spacesemptyPassed to Chrome in --js-flags
firefoxPrefsobject of preference name to string, boolean or integeremptyWritten to the fresh Firefox profile of the run

What the harness plans from a spec

The plan is every combination of environment, workload, thread count, engine arm and repetition, shuffled once with orderSeed. For the main campaign that is 3 environments x 9 parallel workloads x 6 thread counts x 30 repetitions = 4860 runs, plus 5 sequential workloads at one thread (3 x 5 x 30 = 450): 5310 runs, plus the discarded first launches.

A run id names its place in the plan: campaign-v3-2666-chrome-filter-noise-n8-r27 is position 2666 of the order, Chrome, the filter on noise, 8 threads, repetition 27.
