Data files, CSV schema and tables

Every run leaves a pair of files in data/raw/<campaign>/: a CSV of times and a JSON of context. Every derived number is in a table in data/tables/<campaign>/. This page describes each folder, each column of the CSV, each field of the run context and each table. Nothing in data/raw/ is ever edited; everything in data/tables/ can be deleted and made again.

One row, read aloud

Start with one line of one file. This is a measured iteration of run 4646 of the main campaign: native, the filter, eight threads, repetition 11:

Read it left to right with the names of the header. env native; workload filter; input noise (k is empty, because noise has no k); width and height 8192; the seed of the input; threads 8; phase measured, so this row counts; iter 0, the first measured iteration; ns, the time of that iteration in nanoseconds, about 3.3 million, or 3.3 ms. Then come two hashes, which show that the input was the same image and the output the same filtered image as in every other environment, and addresses and memory sizes kept for the record. Installation and first run reads a row like this one field by field.

Why

Why does every row repeat the whole configuration? So that a row can be read alone. A thousand files later, you do not need to remember which folder meant what: the row says native, filter, 8 threads. The joined table of harness.collect is all the rows of all the runs with the run id added, and it needs no other key.

Why

Why two files per run and not one? The CSV holds what the measured program wrote and nothing else; the JSON holds what the harness knew about the machine around it. Kept apart, the Rust code never needs to know about governors or scopes, and the harness never parses a time (What crosses each boundary).

Other folders of data/: probes/ holds one-off measurements and disassemblies (the store-forwarding chain, the V8 and native loops of ADR 0060). data/raw/quick-* and data/mac-smoke/ are ignored by git, because they are never results. python3 -m harness.collect writes a joined table such as data/campaign-v3.csv on demand; it is not kept.

Raw is never edited. A wrong run is not fixed in place. It is excluded by a rule fixed before the analysis (D7 of the plan), or run again and moved to excluded/ with an ADR that says why. So every table traces back to the files as the runs wrote them.

data/tables

Why

Why a second folder? Raw is what happened; tables are what was computed from it, by a command that can run again. Delete data/tables/, and make all-results writes it back identical, except for the time stamp in each sidecar. If a number in the paper is doubted, that command is the answer.

One folder per campaign, or per family of campaigns, written by the *-results make targets. Every folder ends in -v3: the final build, and the only one that this documentation and the paper read. The tables of the earlier build are at the tag data/v2.

The CSV: one row per iteration

The Rust code writes the same schema natively and in the browser. Each row has the whole configuration, so one row says what it measured:

The JSON: the run's context

The harness writes it around the run. It lets the analysis refuse a run that was not taken under the conditions it claims (strict validation, ADR 0027):

In depth: every key of the run's JSON
KeyMeaning
buildrustc, wasm-bindgen and the exact RUSTFLAGS of the artifact
clockResolutionNs, clockSmallestStepNsThe browser clock's resolution, measured by the page
commitThe git commit; a -dirty one fails strict validation

environment, browserVersion, headlessEnvironment and its exact version (checked against the pin)
cpuMask, pCpus, maskSiblingsThe mask the run got and the topology behind it: one CPU per physical P-core

startDelayMs, passes, grainSettings of the run
