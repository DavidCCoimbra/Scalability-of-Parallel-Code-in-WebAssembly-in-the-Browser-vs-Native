One run, start to end

A run is one program start: the program is launched, works, prints its times, and is gone. This page follows two real runs of the main campaign through the code, line by line: the atomic histogram at k = 1 with 8 threads, once natively (campaign-v3-4610-native-hist-atomic-k1-n8-r0) and once in Chrome (campaign-v3-4221-chrome-hist-atomic-k1-n8-r0). Then the 30 runs of each configuration go into the analysis.

In one sentence: the campaign picks the run, the harness starts it on the fast cores, both the native program and the browser end up in the same Rust function, which times only the work, and the CSV it prints is stored next to a record of the conditions.

The shape before the steps

Before stepping through 27 lines of code, here is the whole shape. Each box is a separate program (a process); the dashed zones are where it runs; the arrows say what crosses from one to the next. Only the red box is inside the clock.

Why does only the red box matter for the numbers? Everything to its left happens before the clock starts and runs on other cores; everything to its right happens after the CSV exists. So a slow harness, a slow disk or a slow analysis cannot change a measured time. The only things that can are inside that box: the runtime, the code, and the machine it runs on, which is what the study compares. How the pieces talk gives every port and file.

Into the analysis

Each run left a CSV (one row per iteration) and a JSON (its context) in data/raw/campaign-v3/. The analysis joins them, reduces each run to one number, and compares configurations. Follow the atomic histogram at k = 1 from its runs to its speedup; the plain version of each statistic is on Reading the numbers.

What to remember. One run is one fresh process, started from outside the measured cores, that ends in run_in_pool whatever the environment. The clock brackets only Workload::run. What comes out is text in a file, and from there on it is arithmetic.
