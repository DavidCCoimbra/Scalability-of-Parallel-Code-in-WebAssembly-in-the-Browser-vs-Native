Atomic operations

An atomic add makes sure no count is lost when several threads add to the same counter. A CPU offers two ways to do it: one locked instruction, or a read followed by a compare-and-swap that retries. This page explains both, shows which one each compiler emits for the same line of Rust, and explains why the memory ordering argument makes no difference on these targets.

What an atomic add is

A plain count = count + 1 is three steps for the CPU: read the value from memory, add one, write the result back. With one thread that works. With two threads on the same counter, the steps can interleave:

StepThread AThread BCounter in memory
1reads 4141
2reads 4141
3writes 41 + 142
4writes 41 + 142, not 43

Two adds ran and the counter went up by one: a count is lost, and the histogram is wrong. An atomic add makes the three steps one indivisible step. No other thread can get between the read and the write, so nothing is lost, even with 8 threads on one counter.

Why

Why does the study use atomics and not a lock? A lock is a second mechanism on top of the add (take the lock, add, release), with its own costs to separate. An atomic add is the smallest unit of synchronization a CPU offers: one instruction. Whatever a browser does differently with it is as close to the hardware as a measurement gets.

Two ways to add: lock, or try and retry

A CPU has two ways to make an add atomic. The difference matters when two cores want the same counter:

  • Lock the line and add. One instruction (lock add on x86) takes the counter's cache line, adds, and releases it. It cannot fail: the core that holds the line adds, and the others wait their turn.
  • Try, check, retry. Read the counter with a plain read, compute the new value, then run a compare-and-swap: "write my new value, but only if memory still holds the value I read". If another core changed the counter in between, the swap fails and the loop starts again with a new read.

Lock-and-add is taking the one shared pen and writing your mark before you hand it on. Try-and-retry is writing your mark on a note from memory and then checking the sheet: if nobody wrote since you looked, you stick the note on; if someone did, you start over.

What each engine emits

The Rust source does not choose the strategy; the compiler that produces the machine instructions does. LLVM, natively, and Firefox's engine emit lock-and-add. The optimizing compiler of Chrome's engine emits try-and-retry. The study captured the machine code each engine runs on the measured build: V8 writes its compiled code to a file, and Firefox's was read from the browser's memory at the addresses where the CPU spent its time (data/probes/engine-code/). How to read it. Each line is one machine instruction. mov copies a value, add adds, shl multiplies by a power of two, and an instruction that starts with lock is atomic on memory. The words in brackets are memory locations; the ones that start with % are the core's registers.

Why

Why does V8 choose the retry loop? The WebAssembly instruction is "atomic add, and return the old value". When the old value is not used, as here, there are two correct ways to compile it, and V8's optimizing compiler takes the general one that works for any read-modify-write. It is a choice of the engine, not a bug, and the study's code cannot change it. That makes it a finding of RQ2, not a flaw of the setup.

Memory order, for the record

If you know atomics, you will ask about memory ordering first. It is not the reason for the Chrome result. Every Rust atomic takes an ordering (how strictly other memory accesses are kept in sequence around it), and you could suspect that the browsers pay for a stricter one. On this hardware they do not:

In depth: why ordering changes nothing on these targets

The histogram asks for Relaxed, the weakest ordering: it needs only that each counter is updated atomically, and the counters are read after the parallel call has joined (ADR 0014). SeqCst is the strongest, and the only one JavaScript and WASM offer. The choice changes nothing here:

  • WASM atomics are always sequentially consistent, whatever Rust asked for.
  • On x86, any locked read-modify-write is a full barrier natively too, and atomics cost about the same whatever their semantics, because cache-line transfers bound them (Schweizer et al. 2015).

So native code and the browsers pay for the same ordering. If Chrome's atomics cost more, the reason is in the instructions each engine emits, which the section above shows.

Store forwarding at k = 1

One more effect appears at k = 1, and it has nothing to do with atomics: the local histogram, with one thread and nothing shared, is several times slower at k = 1 than at k = 256. When every pixel adds to the same counter, each add waits for the result of the one before it, and the core cannot overlap them. At k = 256 consecutive pixels usually hit different counters, and the core runs many adds at once.

Why

Why does it matter for the study? "k = 1 is slow" is partly not about synchronization. If RQ2 compared k = 1 with k = 256, that effect would be mixed into the answer. So RQ2 never compares inputs: it compares the atomic histogram with the local one at the same k, where the effect is in both and cancels (In depth: the RQ2 metric).

The measured times, the two instruction streams and the probe that compares them are on RQ1: scaling.

In summary. An atomic add makes sure that no count is lost when threads share a counter. A CPU can do it in one locked step, or by trying and retrying. LLVM and Firefox emit the first; Chrome's optimizing compiler emits the second, which costs an extra read and, under contention, retries. Memory ordering is not the reason.
