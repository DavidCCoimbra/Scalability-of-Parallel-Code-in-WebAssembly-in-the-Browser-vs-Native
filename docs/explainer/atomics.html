Atomics in machine code

The shared histogram has one line of Rust per pixel: add one to a shared counter, atomically. That one line reaches Chrome and Firefox as the same WebAssembly instruction, and the two browsers turn it into different machine code. One of them does the add in one step; the other tries, checks, and retries. That difference is where the RQ2 results come from.

In one sentence: native code and Firefox add with one locked instruction that cannot fail; Chrome reads the counter, computes, and tries to write it back only if nobody changed it in between, going round again if someone did.

What an atomic add is

A plain count = count + 1 is three steps for the CPU: read the current value from memory, add one, write the result back. With one thread that is fine. With two threads on the same counter, the steps can interleave:

StepThread AThread BCounter in memory
1reads 4141
2reads 4141
3writes 41 + 142
4writes 41 + 142, not 43

Two adds happened, the counter went up by one: a count was lost, and the histogram is wrong. An atomic add makes the three steps one indivisible step, so no other thread can slip in between the read and the write, and nothing is ever lost, even with 8 threads on one counter.

Why does the study use atomics and not a lock? A lock would be a second mechanism on top of the add (take the lock, add, release), with its own costs to untangle. An atomic add is the smallest unit of synchronization a CPU offers: one instruction. Whatever the browser does differently with it is as close to the hardware as a measurement can get.

increment takes &self, not &mut self: an atomic may be changed through a shared reference, which is why all threads can hold &self.counters at once. The counters are reset in prepare, outside the timed region, with a plain write (get_mut proves no other thread can see them).

Two ways to add: lock, or try and retry

A CPU has two ways to make an add atomic, and the difference matters when two cores want the same counter:

  • Lock the block and add. One instruction (lock add on x86) takes the counter's cache line, adds, and lets it go. It cannot fail: whoever holds the line adds, the others wait their turn.
  • Try, check, retry. Read the counter with a plain read, compute the new value, then run a compare-and-swap: "write my new value, but only if memory still holds the value I read". If another core changed the counter in between, the swap fails and the loop starts again with a fresh read.
Picture it. Lock-and-add is taking the one shared pen and writing your tick before handing it on. Try-and-retry is writing your tick on a sticky note from memory, then checking the sheet: if nobody wrote since you looked, you stick it on; if someone did, you tear it up and start over.

What each engine emits

Which strategy a runtime uses is not chosen by the Rust source; it is chosen by whatever turns the code into machine instructions. The native compiler and Firefox's engine pick lock-and-add; Chrome's engine picks try-and-retry. The study found this by capturing the machine code each engine runs on the measured build: V8 can write its compiled code to a file, and Firefox's was read out of the browser's own memory at the addresses where the CPU spent its time (data/probes/engine-code/). How to read it. Each line is one machine instruction. mov copies a value, add adds, shl multiplies by a power of two, and anything starting with lock is done atomically on memory. The words in brackets are memory locations; the ones starting with % are the core's own scratch registers.
Why does V8 choose the retry loop? The WebAssembly instruction is "atomic add and return the old value". When the old value is not used, as here, there are two correct ways to compile it, and V8's compiler happens to take the general one that works for any read-modify-write. It is a choice of the engine, not a bug, and not something the study's code can change. That makes it a finding of RQ2 rather than a flaw of the setup.

Memory order, for the record

Anyone who knows atomics will ask about memory ordering before anything else, so it has to be said plainly: it is not the reason for the Chrome result. Every Rust atomic takes an ordering (how strictly other memory accesses are kept in sequence around it), and one could suspect the browsers pay for a stricter one. They do not, on this hardware:

If you already know this: why ordering changes nothing on these targets

The histogram asks for Relaxed, the weakest ordering: it only needs each counter updated atomically, and the counters are read only after the parallel call has joined (ADR 0014). SeqCst is the strongest, and the only one JS and WASM offer. The choice changes nothing here:

  • WASM atomics are always sequentially consistent, whatever Rust asked for.
  • On x86, any locked read-modify-write is a full barrier natively too, and atomics cost about the same whatever their semantics, being bound by cache-line transfers (Schweizer et al. 2015, cited in the paper).

So the native code and the browsers pay for the same ordering. If Chrome's atomics cost more, the reason has to be in the instructions each engine emits, which is what the section above shows.

Store forwarding at k = 1

One more effect hides at k = 1, and it has nothing to do with atomics: even the private histogram, with one thread and no sharing at all, is several times slower at k = 1 than at k = 256. When every pixel adds to the same counter, each add must wait for the previous add's result before it can start; the core cannot overlap them. At k = 256 consecutive pixels usually hit different counters and the core runs many adds at once.

Why does it matter for the study? Because it means "k = 1 is slow" is partly not about synchronization. If RQ2 compared k = 1 against k = 256, that effect would pollute the answer. So RQ2 never compares inputs; it compares shared against private at the same k, where this effect is present in both and cancels (the RQ2 metric).
If you already know this: the numbers, the dependency chain and the two instruction streams

At k = 1 the loop is a dependency chain through memory: the new value goes from the store buffer straight to the next load (store-to-load forwarding), and no pixel can start before the previous one finished. Here Chrome is even slightly faster than native. LLVM emits one memory-operand inc per pixel; V8 emits a separate load, add and store:

On this core the memory-operand inc chain is about 1.5 to 2 % slower. A C probe of the two sequences alone on one P-core (bench/probes/rmw_chain.c, ADR 0060) took 155.2 ms against 152.7 ms, about 60 % of the gap; it explains a design result, it is not a campaign number. The lesson the paper draws: one source and one set of flags do not give one instruction stream; the engine's code generator is part of what is measured.

What to remember. An atomic add exists so that no count is lost when threads share a counter. A CPU can do it in one locked step, or by trying and retrying. Native and Firefox do the first; Chrome does the second, which costs an extra read and, under contention, retries that the study counted. Memory ordering is not the reason.
