Exploratory campaigns

The main campaign answers RQ1 and RQ2 with ten comparisons fixed in advance. The exploratory campaigns ask the follow-up questions on the same build and protocol, 30 runs per configuration: where Chrome's atomic cost comes from, whether the RQ1 picture holds when the work grows, when SIMD is removed and when slow cores are added, and how much work a parallel region needs before threads pay.

Why

Why "exploratory", and why it matters for how you read the numbers. The ten main comparisons were named before any data existed, and tested with a bar raised for testing ten things at once. These were not. If you look at enough numbers, some will look surprising by chance alone, so a result here describes and explains; it does not decide. The intervals are plain 95% ones with no correction (Ten decisions, a stricter bar).

The questions

  1. Is Chrome's extra cost about threads sharing a counter, or about the atomic instruction itself? Give each thread its own counters, so nothing is shared, and see what remains.
  2. Does the padding between counters matter? Remove it, so counters share cache lines, and see what changes.
  3. Does the browser keep up when the work grows with the threads? Instead of a fixed image, give each thread the same amount of image (weak scaling).
  4. Is the browser gap caused by the SIMD instructions? Build the filter without SIMD on both sides, and natively with wider SIMD, and compare the gaps.
  5. What happens with slow cores added? Let the runtimes use the 16 efficiency cores too, up to 20 threads.
  6. How much work does a parallel region need before threads pay? Shrink the image until the fixed cost of starting the threads shows.
  7. How small may a task inside a region be? Fix the task size by hand and sweep it.

Private and packed atomics

Questions 1 and 2. The extras campaign (5400 runs, k = 1 and 256, N as before) adds two variants of the atomic histogram next to the shared and the local ones:

  • private: every thread gets its own padded table of atomic counters, merged at the end. The same atomic instruction runs for every pixel, but no two threads ever touch the same counter. If Chrome still pays extra here, the instruction itself is the cost.
  • packed: the shared table without padding, eight 8-byte counters per 64-byte cache line, so counters that are different numbers still share a line (false sharing). If Chrome's advantage at k = 256 disappears here, it depends on the padding.

Answer 1: it is partly the instruction. Private atomics, with nothing shared, scale like the local control, but still cost Chrome 1.83 to 1.85 times native at k = 1 and 1.08 to 1.09 at k = 256, at every N including N = 1. Firefox matches native. So of Chrome's 2.06 at k = 1 with real sharing in this campaign, about 1.85 is already there with nothing shared. This campaign has times only, so by itself it cannot say what that excess is; it has the shape that the native probe found for the compare-and-swap sequence (slow at k = 1, close to the locked add at k = 256), and the probe is what shows the cause (The test: change only the add).

Answer 2: yes, it depends on the padding. Packed counters at k = 256 slow the atomic histogram by 1.18 times natively, 1.25 in Firefox and 3.45 in Chrome. Chrome's advantage under spread contention needs every counter on its own line.

Weak scaling

Question 3. So far every run used the same 8192 x 8192 image however many threads it had (strong scaling). Weak scaling is the other way to add threads: grow the image with them, 8192 × 1024·N pixels, so each thread always has the same amount of work. Ideally the time then stays the same whatever N is, and the weak efficiency T1/TN stays at 1 (1080 runs).

Workload:

Answer 3: yes. The filter's weak efficiency at N = 8 is 0.86, 0.85 and 0.92 (native, Chrome, Firefox), the local histogram's 0.99 to 1.00, within 2 points of what strong scaling gave. Browser / native time stays flat in Chrome (1.16 to 1.20) and falls from 1.36 to 1.28 in Firefox: the browser gap does not grow with N here either.

Why

Why ask the question twice? Strong scaling can hide a problem: with a fixed image, each thread's share gets smaller as N grows, so a per-thread cost could be masked by the shrinking work. Weak scaling keeps the share fixed. Getting the same answer both ways is what makes RQ1's answer solid.

SIMD builds

Question 4. The filter normally processes several pixels per instruction with 128-bit SIMD on both sides (SSE2 natively, simd128 in WASM). If the browser's SIMD path were worse than native's, that alone could explain the gap. Two more builds changed only this (720 runs): scalar (no SIMD on either side) and native AVX2 (256-bit, native only, deliberately breaking the same-flags rule to see the effect of faster code).

Show:

Answer 4: no, SIMD is not the cause. Without SIMD the filter at N = 1 is 3.9 to 4.9 times slower, and the browser gap is larger, not smaller (Chrome 1.48 to 1.50, Firefox 1.59 to 1.60, flat across N). The gap comes from somewhere else: the engines run about a third more instructions per pixel (question 3).

In depth: the faster the code, the worse it scales
  • Efficiency at N = 8 rises to 0.97 to 0.98 without SIMD, and drops to 0.72 with AVX2. Across the three builds and the three runtimes, the faster one thread goes through memory, the less eight threads gain (question 1 has the chart).
  • The excess time T8 - T1/8 grows natively with the code's speed (207, 424 and 748 µs for scalar, baseline and AVX2), as when cores share memory bandwidth. In the browsers it changes little (Chrome 569 and 515, Firefox 317 and 349 µs), consistent with a fixed per-iteration overhead, of which the fork-join is about a fifth.

P-cores plus E-cores

Question 5. The i9-14900KF has, besides the 8 fast cores every other campaign uses, 16 slower E-cores. This campaign (900 runs) lets the runtimes use the 8 P-cores plus 12 E-cores, N up to 20, to see whether work stealing copes with cores of unequal speed in every runtime.

Workload:

Answer 5: it works in all three. The E-cores gain the filter 10 to 18% in every environment over the main campaign's P-only N = 8 (time at N = 8 there over time at N = 20 here), with browser / native 1.15 to 1.36. Work stealing balances unequal cores in all three runtimes.

In depth: speedups above N on the local histogram

The local histogram at k = 1 reaches speedups above N (Chrome 29.5 at N = 20). That is not super-linear parallelism: the single-thread baseline is a store-forwarding chain on one counter (Store forwarding at k = 1), and ADR 0061 traces the excess to that loop running faster per core on an E-core than on a P-core. The evidence is a single-core probe on the earlier build (data/earlier/probes/ecore-workloads.txt), not repeated on measured/v3, so it is given as the likely reason and without numbers. The cells with E-cores also vary more between the two builds than any other (up to 8%, where every P-core cell is within 1%): which threads the kernel puts on which kind of core is not controlled and not recorded per thread (ADR 0094).

How much work a region needs: the cutoff campaign

Question 6. The answer to RQ1 holds "with enough work per parallel region". This campaign measures how much is enough in each environment.

The filter and the local histogram (k = 256) ran on images from 512 x 512 to 8192 x 8192 pixels, at N = 1 to 8 (4080 runs). The smallest images take a few microseconds, less than the browser's clock can tell apart, so each timed sample repeats the work several times (passes) and divides by the count (ADR 0064). Two things to see. The speedup never drops below 1: at these sizes, threads never make the work slower. But efficiency falls fast as the work shrinks, and faster in the browsers, because their fixed cost of starting and stopping the threads (fork-join) is larger.

Why

Why "half the threads' worth" as the line? Some line is needed to turn a curve into one number, and efficiency 0.5 (8 threads doing the work of 4) is the point where the overhead has eaten as much as it left. The study reads where each curve crosses it, and reports the work per call at that point:

For the filter that is 125 µs of single-thread work natively, 396 in Chrome and 459 in Firefox: the browsers need 3 to 4 times the work native needs to keep half the threads' worth. With the local histogram's 325 and 362 µs, that is the "0.3 to 0.5 ms" of the advice. In Firefox it is about the cost of 8 fork-joins (8 × 60 µs); natively it is 1.4 times that (8 × 10.8 µs). The fork-join of the browsers here is the campaign's median; Firefox's 20 µs clock makes it coarse.

The 100:1 rule

A rule of thumb from the course: a parallel region should do at least 100 times the work its fork-join costs, so that the overhead stays under 1%. It gives a second, stricter line than efficiency 0.5. With the fork-join this campaign measured (300 runs per environment), applied to the full 8192 x 8192 image at N = 8:

Only native keeps the fork-join under 1% of the time at 8192² (0.33%; Firefox 1.4%, Chrome 2.7%). To reach the 1% line, the browsers need 6 to 10 times more work per region than native (last column), because their fork-join costs that many times more.

Two lines, two numbers. "3 to 4 times the work" and "6 to 10 times the work" measure the same thing, the browser's dearer fork-join, against two different lines. Efficiency 0.5 is a loose line (lose half); the 100:1 rule is a strict one (lose 1%). The browser's handicap looks bigger against the strict line because its fork-join is a bigger share of a smaller budget. Both say: in the browser, make the regions bigger.

How small a task may be: the grain sweep

Question 7.

Inside one region, Rayon cuts the work into tasks that idle threads pick up (Grain size). Cut too small, and the cost of handling each task dominates; cut too large, and there are too few tasks to keep all the threads busy. Somewhere in between is a flat bottom: the U-curve. The grain sweep (5400 runs, N = 8) fixes the task size by hand and measures the time; adaptive is Rayon's own split.

Workload:Image:

  • At 8192² the best task is 4 rows for the filter and 64 to 128 KB for the local histogram, in all three runtimes. The bottom of the U is in the same place.
  • Too fine: 1 KB histogram tasks cost 2.1 to 3.0 times the best. Too coarse: one task per thread, with nothing left for an idle thread to pick up, costs 1.01 times the best natively and 1.11 to 1.16 in the browsers.
  • Rayon's adaptive split is within 3% of the best at 8192² (and 3 to 18% slower at 1024², where regions are small). Hence the advice: let it choose.
  • The shared atomic histogram hardly cares: at k = 256 its time stays within 0.3% of the best natively, 0.6% in Chrome and 1.3% in Firefox over every grain from 1 KB to 8192 KB. Its time is set by the fight for the counters, not by how the image is cut.
In depth: the best grains, and the 100:1 rule applied per task

The 100:1 rule lands in or near the flat region of best grains when it is applied to the cost per task (0.46 to 1.0 µs for the histogram, last columns), not to the region's fork-join: the per-task overhead is what a too-fine grain pays for, so that is the cost the rule should be set against inside a region.

What this means for a developer

Make parallel regions coarse

With 8 threads in the browser, start a parallel region only when it holds roughly 0.3 to 0.5 ms of work as one thread would do it. Below that, more than half of what the threads could give is lost to starting and stopping them. Natively about 0.12 to 0.19 ms is enough.

Let Rayon pick the task size

Inside a region, the best size for each piece a thread picks up is the same in all three runtimes, and Rayon's own choice is within 3% of it. Tuning it by hand for the browser gains almost nothing.

Avoid or spread synchronization

Shared atomic counters that every thread hits cost Chrome up to 2.3 times what they cost natively (RQ2). Give each thread its own counters and merge at the end, or spread the sharing over many padded counters.

Measure in the browser

One source does not give one instruction stream: the engine rewrites your atomics its own way, and that is part of the cost (Why Chrome).

An analogy. Calling eight friends to help carry boxes takes a few minutes of phone calls. For a whole house move it is nothing. For one box, you would have carried it yourself before the first call ended. The browser's phone calls take ten times longer than native's, so the house has to be bigger before calling pays.

The rest of the page is where each number above comes from: the size of a whole parallel region (the cutoff campaign), a rule of thumb from the course, and the size of each task inside a region (the grain sweep).

In summary. With nothing shared, Chrome's atomic add already costs more than the native one at k = 1, and its advantage at k = 256 needs the padding. The RQ1 picture holds when the work grows with the threads, without SIMD and with slow cores added. Threads pay in the browser as they do natively, but a parallel region needs about three to four times the native work to keep half of the threads' worth; inside a region, Rayon's own split is within 3% of the best fixed task size at 8192 x 8192.
