Environments and builds

The comparison is fair only if the code is the same. One Rust crate is compiled by one compiler with one release profile into a native Linux program and a WebAssembly module, and Chrome and Firefox each compile that module with their own engine. This page describes the three environments, what WebAssembly threads need, what still differs below the shared source, and how a build is identified.

Same source, same flags

Three things are the same in every environment. Each would spoil the comparison if it were not:

  • The source. One folder, bench/. Only the entry point differs: a main for the Linux program, and a small library that the browser page calls.
  • The compiler. One version of the Rust compiler, pinned by date. Two versions can produce different machine code from the same source, and that difference would be taken for a difference between environments.
  • The options. The same release profile for both outputs, with the same width of SIMD (instructions that process several pixels at once): 128 bits on both sides.

Why

Why not let the native build use everything the CPU has? The PC's CPU has 256-bit SIMD (AVX2), which processes twice as many pixels per instruction, but WebAssembly offers only 128 bits. With 256 bits natively and 128 in the browser, part of the gap would be the width of the instructions, not the environment. The study keeps both at 128 bits and measures the wider native build only as an exploratory campaign (SIMD builds). A check in CI confirms that the filter's inner loop uses SIMD in both outputs (ADR 0017).

Native

"Native" means a normal Linux program: the compiler produced its machine code in advance, and the operating system runs it directly on the CPU. It reads its configuration from the command line (workload, threads, image size), starts its N threads, runs the warm-up and the measured iterations, and prints one line per iteration. The harness captures that output and writes the CSV.

Its clock is the operating system's high-resolution clock, which counts in nanoseconds.

In depth: the entry point and the scope it runs in

The binary is bench/target/release/native. It builds a global Rayon pool of N threads, runs the configuration and prints CSV. The harness starts it inside a systemd scope with a taskset mask of the 8 P-cores. The clock is std::time::Instant.

Chrome and Firefox

In a browser the same code arrives as a WebAssembly module inside a web page. A fresh copy of the browser opens the page, started for this run only, with no history, no extensions and no window. The engine compiles the WebAssembly to machine code, the page runs the workload, and then posts its results to a small local server that writes the CSV.

Chrome

Chrome for Testing 155.0.8059.84, a build that Google publishes for test automation, downloaded once and checked against a recorded digest. Its engine is V8. A pilot found it within about 1.3% of ordinary Chrome (ADR 0050).

Firefox

Firefox 158.0, downloaded from Mozilla's archive. Its engine is SpiderMonkey. A policy switches automatic updates off, after a pinned copy once updated itself (A pinned Firefox that updated itself).

Why

Why a fresh browser for every run, with no window and no extensions? A browser in daily use carries state: extensions, cached pages, background tabs, update checks. Any of them can take CPU time during a measurement, differently from one run to the next. A fresh temporary profile has none of that, headless mode removes the cost of drawing, and both browsers get the same quiet settings. A pilot measured headless against a visible window: within 0.3% (ADR 0046).

Why

Why no automation framework (Puppeteer, Playwright)? Those tools drive the browser through a control channel, with their own threads and timers inside the browser, which would be part of the measurement. Here the browser gets only a URL with the configuration in it, and the page reports back by itself (ADR 0006).

The page's clock is performance.now(). Browsers round it on purpose, to make timing attacks harder: to 5 µs in Chrome and 20 µs in Firefox here. Every measured iteration lasts at least 100 times that, so the rounding cannot change a result (ADR 0039, ADR 0041).

In depth: pins, flags and the version check

Both versions are pinned in harness/browsers.json, the Chrome archive with its SHA-256. The launcher gives each browser a fresh, temporary profile and runs it headless, with settings that turn off background work (updates, telemetry, safe-browsing downloads) in both. Every run records the browser's exact version, and a campaign refuses to start with a version that is not the pinned one (ADR 0071).

A pinned Firefox that updated itself

The numbers in this section come from pilots and from the earlier build, measured/v2. They justify the fix; they are not results of the study.

The study pins Firefox 158.0, and the fresh profile turns automatic updates off. On 2026-11-10, between two exploratory campaigns of the earlier build, the installed Firefox updated itself in place to 160.0 all the same. Only the enterprise policy DisableAppUpdate prevents it (ADR 0071).

Why

Why this would have gone unnoticed. Two campaigns meant to compare the same Firefox would have compared two different ones, with whatever changed in the engine between them mixed into the result.

  • Caught: strict validation checks the browser version of every run, and rejected all 2640 affected exploratory runs of that build.
  • Fix: the installer writes the policy and reinstalls a moved install, and a campaign refuses to start when a browser is not the pinned version.
  • Now: on measured/v3 the policy and the version check were in place from the first run. Every Firefox run of every campaign is 158.0 and interleaved with the others, and no run was rejected for its version.

What WASM threads need

A native program gets threads from the operating system. A web page does not: its only way to run two things at once is a Web Worker, a second script with its own memory. For Rayon's threads to work in a browser, several workers must run the same WebAssembly module on one shared memory. That takes five things:

  1. A compiler set to produce thread-capable code. By default WebAssembly code has no atomic instructions. The build turns them on.
  2. A standard library built the same way. The prebuilt Rust standard library for WebAssembly has no atomics, so it is rebuilt from source with them. Only a nightly compiler can do that, which is why the pinned compiler is a nightly.
  3. Permission for shared memory. A browser allows a SharedArrayBuffer only on a page that declares, with two HTTP headers, that it loads no content from other sites. The local results server sends both.
  4. A pool of workers. A small library, wasm-bindgen-rayon, starts N workers that share the module's memory and become Rayon's threads.
  5. A worker that coordinates. The main thread of a page may not block, but a parallel region means waiting for every thread to finish. So one extra worker calls the Rust code and waits, and the main thread waits only for its message.

Why

Why does this matter for the results? A browser run has more threads than N: the N workers of the pool, the coordinating worker, and the browser's own threads. At N = 8 they share the 8 cores. That is one of the threats in Threats to validity, and the reason every run measures the cost of starting and joining a parallel region (Fork-join calibration).

In depth: the flags, the headers and the worker

Target features +atomics,+bulk-memory,+mutable-globals,+simd128 and a shared, imported memory of at most 4 GiB; -Z build-std for the standard library; Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp from the server; startThreadPool(N) from wasm-bindgen-rayon; and a dedicated worker because Atomics.wait is forbidden on the main thread.

Builds and tags

A build is the exact compiled output: one Linux program and one WebAssembly module from one version of the source. Change one line of the measured code and the machine code may come out different, sometimes in a way that changes a timing. So runs of two builds are never compared as if they were one.

Why

Why so strict? Suppose you measure native on Monday, improve the code a little on Tuesday, and measure Chrome on Wednesday. Chrome runs better code, and the comparison is unfair without anyone noticing. So every run records the build it came from, and a campaign is always one build. A git tag names the build of every reported number: measured/v3.

The build history

After the first campaigns, a review of the measured code against the textbook, the cited papers and the lectures found two asymmetries that the study had caused itself. The second build, measured/v2, fixed them (ADR 0069):

  • A bounds check on one side of RQ2 only. The shared-counter histograms indexed a table whose length the compiler did not know, so every pixel paid a bounds check (a compare and a branch) that the local histogram did not. The atomic over local ratio therefore included code that only the atomic side ran, and that the engines could compile differently from LLVM.
  • Final work timed in some variants only. The merge of the local histogram was inside the timed region; the merge of the private tables and the read-back of the shared counters were outside it.

Why

Why this would have gone unnoticed. RQ2 is a ratio of ratios, and it cancels only what is the same on both sides. A check that ran on one side, or a merge timed on one side, would have been read as a cost of synchronization in every engine.

The fix: counter tables of a fixed size (no check per pixel; LLVM then unrolls the loop by 8), and every histogram's timed run ends with its final histogram. The checksums did not change.

Every campaign was then run again on the corrected build. The reported build is the third, measured/v3: a replication of v2 with known results, which adds the sequential references and the same task-splitting code for both histograms (Why the study was measured twice). Every number in this documentation comes from measured/v3; the campaigns of the earlier builds are not reported as results.

In depth: why builds are never mixed

Builds are never mixed in one comparison because a change in code layout alone, with the same instructions, can change timing by a few percent (Mytkowicz et al. 2009). A refactor of the measured path is accepted only when a codegen diff shows the hot functions unchanged; otherwise it is a new build with a new tag, and earlier campaigns stay valid only for their own build (ADR 0062, Change the measured code).
