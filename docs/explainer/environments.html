Environments and builds

The comparison is fair only if the code is the same. One Rust crate is compiled by one compiler with one release profile into a native Linux program and a WebAssembly module, and Chrome and Firefox each compile that module with their own engine. This page describes the three environments, what WebAssembly threads need, what still differs below the shared source, and how a build is identified.

Same source, same flags

Three things are held equal, and each would spoil the comparison if it were not:

  • The source. One folder, bench/. The only file that differs is the entry point: a main for the Linux program, and a small library the browser page calls.
  • The compiler. One exact version of the Rust compiler, pinned by date. Two versions of a compiler can produce different machine code from the same source, and that difference would be mistaken for a difference between runtimes.
  • The options. The same optimization settings for both outputs, including the same width of SIMD (instructions that work on several pixels at once): 128 bits on both sides.

Why

Why not let the native build use everything the CPU has? The PC's CPU can do 256-bit SIMD (AVX2), which processes twice as many pixels per instruction, but WebAssembly can only ask for 128 bits. If the native build used 256 and the browser 128, part of the gap would be the width of the instructions, not the runtime. The study keeps both at 128, and tries the wider native build only as an exploratory extra (SIMD builds). A check in CI confirms the filter's inner loop really uses SIMD in both outputs (ADR 0017).

Native

"Native" means a normal Linux program: the machine code was produced on the build machine, and the operating system runs it directly on the CPU, like any command-line tool. It reads its settings from the command line (which workload, how many threads, the image size), starts its N threads, does the warm-up and the timed iterations, and prints one line of results per iteration. The harness captures that output and writes the CSV.

Its stopwatch is the operating system's high-resolution clock, which counts in nanoseconds.

In depth: the entry point and the scope it runs in

The binary is bench/target/release/native. It builds a global Rayon pool of N threads, runs the configuration and prints CSV. The harness starts it inside a systemd scope with a taskset mask of the 8 P-cores. The clock is std::time::Instant.

Chrome and Firefox

In the browser the same code arrives as a WebAssembly file inside a web page. The page is opened by a fresh copy of the browser, started just for this run, with no history, no extensions and no window on screen. The browser's engine compiles the WebAssembly into machine code, the page runs the workload, and when it is done it sends its results to a small local server that writes the CSV.

Chrome

Chrome for Testing 155.0.8059.84, a build Google publishes for test automation, downloaded once and checked against a recorded hash. Its engine is V8. A pilot found it within about 1.3% of ordinary Chrome (ADR 0050).

Firefox

Firefox 158.0, downloaded from Mozilla's archive. Its engine is SpiderMonkey. Automatic updates are switched off by a policy, after a pinned copy updated itself once in the middle of the study (A pinned Firefox updates itself).

Why

Why a fresh browser for every run, with no window and no extensions? A browser you use carries state: extensions, cached pages, background tabs, update checks. Any of them can take CPU time in the middle of a measurement, and differently from one run to the next. A fresh temporary profile has none of that; headless (no window) removes the cost of drawing; and both browsers get the same quiet settings, so neither is favoured. A pilot measured headless against a visible window: within 0.3 % (ADR 0046).

Why

Why no automation framework (Puppeteer, Playwright)? Those tools drive the browser through a control channel, with their own threads and timers inside the browser. They would be part of the measurement. Here the browser gets nothing but a URL with the settings in it, and the page reports back by itself (ADR 0006).

The page's stopwatch is performance.now(). Browsers deliberately round it, to make a kind of attack harder: to 5 µs in Chrome and 20 µs in Firefox here. Every measured iteration lasts at least 100 times that, so the rounding cannot change a result (ADR 0039, ADR 0041).

In depth: pins, flags and the version check

Both versions are pinned in harness/browsers.json, the Chrome archive with its SHA-256. The launcher gives each browser a fresh, temporary profile, headless, with flags that turn off background work (updates, telemetry, safe-browsing downloads), the same in spirit for both. Every run records the browser's exact version, and a campaign refuses to start with an unpinned one (ADR 0071).

A pinned Firefox that updated itself

The numbers in this section come from pilots and from the earlier build, measured/v2. They justify the fix; they are not results of the study.

The study pins Firefox 158.0, downloaded from Mozilla's archive, and the fresh profile turns automatic updates off. On 2026-11-10, between two exploratory campaigns of the earlier build, the installed Firefox updated itself in place to 160.0 anyway. Only the enterprise policy DisableAppUpdate stops it (ADR 0071).

Why

Why this would have gone unnoticed. Two campaigns meant to compare the same Firefox would have compared two different ones, with whatever changed in the engine between them mixed into the result.

  • Caught: strict validation checks the browser version of every run, and rejected all 2640 affected exploratory runs of that build.
  • Fix: the installer writes the policy and reinstalls a moved install, and a campaign refuses to start when a browser is not the pinned version.
  • Now: on measured/v3 the policy and the version check were in place from the first run, so every Firefox run of every campaign is 158.0 and interleaved with the others. No run was rejected for its version.

What WASM threads need

A normal program gets threads from the operating system. A web page does not: its only way to run two things at once is a Web Worker, a second script with its own memory. To make Rayon's threads work in the browser, several workers have to run the same WebAssembly module on one shared memory, and that takes five pieces, each of which exists for a reason:

  1. A compiler told to produce thread-capable code. By default WebAssembly code has no atomic instructions. The build switches them on.
  2. A standard library built the same way. The ready-made Rust standard library for WebAssembly was built without atomics, so it is rebuilt from source with them. Only a nightly compiler can do that, which is why the pinned compiler is a nightly.
  3. Permission for shared memory. Browsers only allow a SharedArrayBuffer on a page that promises not to mix in content from other sites, declared with two HTTP headers. The local results server sends both.
  4. A pool of workers. A small library, wasm-bindgen-rayon, starts N workers that share the module's memory and become Rayon's threads.
  5. A worker to coordinate. A page's main thread is not allowed to stop and wait (it must keep the page responsive), but running a parallel region means waiting for every thread to finish. So one extra worker calls the Rust code and does the waiting, and the main thread only waits for its message.

Why

Why does this matter for the results? Because a browser run has more threads than N: the N workers of the pool, the coordinating worker, and the browser's own threads. At N = 8 they all share the 8 cores. That is one of the threats discussed in Threats to validity, and the reason the cost of starting and joining a parallel region is measured in every run (Fork-join and its cost).

In depth: the flags, the headers and the worker

Target features +atomics,+bulk-memory,+mutable-globals,+simd128 and a shared, imported memory of at most 4 GiB; -Z build-std for the standard library; Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp from the server; startThreadPool(N) from wasm-bindgen-rayon; and a dedicated worker because Atomics.wait is forbidden on the main thread.

Builds and tags

A build is the exact compiled output: one Linux program and one WebAssembly file from one version of the source. Change one line of the measured code, rebuild, and the machine code may come out different, sometimes in a way that changes a timing. So runs from two different builds are never compared as if they were one.

Why

Why so strict about it? Imagine measuring native on Monday, improving the code a little on Tuesday, then measuring Chrome. Chrome would be running better code, and the comparison would be unfair without anyone noticing. To make that impossible, every run records which build it came from, and a campaign is always one build. The build every reported number comes from is named with a git tag, measured/v3.

In depth: codegen-neutral refactors and the earlier build
  • Every run records the git commit and the SHA-256 of the native binary and of the .wasm file.
  • A refactor of the measured path is checked with scripts/codegen_diff.sh; if any hot function's code changes, it is a new build, with its own tag (ADR 0062).
  • Two builds came before it. A review of the first one found asymmetries in the measured path, among them a per-pixel bounds check paid only by the shared counters; measured/v2 removed them (The build history). measured/v3 adds the sequential references and gives every histogram the same task splitting, and every campaign was run again on it (The session of a build). The data of measured/v2 is at the tag data/v2.

One last point, and it is a finding rather than a flaw: the same WebAssembly instruction does not give the same machine code in both browsers. For one atomic add, SpiderMonkey emits one locked instruction and V8 emits a loop that may retry (What each engine emits). The build history

After the very first campaigns, a review of the measured code against the textbook, the cited papers and the lectures found two asymmetries the study had caused itself. They were fixed in the build measured/v2 (ADR 0069):

  • A safety check only on one side of RQ2. The shared-counter histograms indexed a table whose length the compiler did not know, so every pixel paid a bounds check (compare and branch) that the local control did not. The atomic/local ratio therefore included code that only the atomic side ran, and that the engines might compile differently from LLVM.
  • Final work timed in some variants only. The local histogram's merge was inside the timed region; the private merge and the read-back of the shared counters were outside it.

Why

Why this would have gone unnoticed. RQ2 is a ratio of ratios, and it only cancels what is the same on both sides. A check that ran on one side only, or a merge timed on one side only, would have been read as a cost of synchronization in every engine.

The fix: fixed-size counter tables (no per-pixel check; LLVM then unrolls the loop by 8 itself), and every histogram's timed run now ends with its final histogram. The checksums did not change.

Then every campaign was re-run on the corrected build. The reported build is the third, measured/v3: a replication of v2 with known results, which adds the sequential references and the same task-splitting code for both histograms (Why the study was measured twice). Every number in this documentation comes from measured/v3; the earlier builds' campaigns are not reported as results.

In depth: why builds are never mixed

Builds are never mixed in one comparison because a change in code layout alone, with the same instructions, can change timing by a few percent (Mytkowicz et al. 2009). A refactor of the measured path is accepted only when a codegen diff shows the hot functions unchanged; otherwise it is a new build with a new tag, and earlier campaigns stay valid only for their own build (ADR 0062, Change the measured code).
