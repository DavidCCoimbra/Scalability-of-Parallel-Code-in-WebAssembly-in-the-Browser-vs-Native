Eight lanes, one per P-core. A block's speed is the measured one-thread filter time of its environment: native 1.00, Chrome 1.17, Firefox 1.36.

Good morning. My project asks one thing: if I take the same parallel Rust code and run it natively and as WebAssembly with threads in Chrome and Firefox, does it scale the same way? The lanes below are the eight cores I measured on; the blocks move at the speed each environment really ran the filter with one thread.

Heavy work is moving to the browser. Does it scale there like it does natively?

  • Image and video processing, documents, visualization and machine learning now run on the web client.
  • WebAssembly with threads lets that work use every core: shared memory, Web Workers, atomics.
  • Earlier studies measured WASM with one thread, or one parallel workload at two thread counts with means only. None sweeps the threads with native as baseline in two engines, and none controls synchronization.

RQ1 - scaling

How do relative speedup and efficiency of the same parallel code evolve with the number of threads, natively and as WASM in the browser?

RQ2 - synchronization

To what extent does synchronization between threads affect the gap observed in RQ1?

Why it matters: heavy work is moving to the client, and WASM threads are how it uses all the cores. What we know from the literature is mostly single-threaded: Jangda found WASM 45 to 55 percent slower with one thread; the closest multithreaded study, Kyriakou and Tselikas, has one workload, 1 against 24 threads, and means only. So two questions. RQ1: does speedup evolve the same way with the thread count? RQ2: how much does synchronization between threads change that gap?

The design in one picture. One Rust and Rayon crate, one pinned nightly compiler, one release profile. It is compiled twice: to an x86-64 binary with baseline SSE2, and to a wasm32 module with simd128, so both sides have 128-bit SIMD. Three environments: native, Chrome with V8, Firefox with SpiderMonkey, both pinned. Two workloads. The Gaussian filter has no synchronization: it is the RQ1 reference. The histogram exists twice with identical results: shared atomic counters, each padded to its own cache line so there is no false sharing, and per-task local counters merged at the end, which is the lock-free control. The input has k distinct values, so k is a dial: with k equal to 1 all eight threads hit one counter; with 256 the contention is spread. Every run checks a checksum that is equal across environments and thread counts.

Method. The machine is an i9-14900KF: I measure only on the 8 P-cores through a process-level mask, with turbo and SMT off and the performance governor; the rest of the system lives on the E-cores. Then the thread pool, a fork-join calibration, a warm-up sized per workload from pilot data, and 10 measured iterations whose median is the run's single value. RQ1. The cores light up to eight and the three curves lie on each other. The filter reaches a speedup of 6.96 natively, 6.92 in Chrome and 7.34 in Firefox at eight threads. Look at the last column of the table: in absolute time WASM costs a constant factor, 1.17 in Chrome and 1.36 in Firefox with one thread and about the same with eight (press down to walk N back to 1). So WASM threads cost per-thread speed, not scalability. Key 2: the local histogram reaches 7.8 to 8.5 everywhere. Keys 3 and 4 are the shared atomics, for the next slides. [next] The primary contrast: Chrome's speedup over native's is 0.996, interval 0.987 to 1.004, not rejected, which bounds any difference to about one percent. Firefox is 1.055, rejected: it scales 5.5 percent better, but from a slower baseline. And the relative speedup is honest: I measured sequential versions with no Rayon call, and the pool of one thread is within minus 7 to plus 5 percent of them. Keys: up and down change N, 1 to 4 change the workload.

Why: longer code per pixel, and eight threads that run into memory, not into the runtime

2. Faster loops scale worse

3. Small regions pay for the fork-join

Image side ↑↓

Firefox scales better because its loop is slower and asks less of the shared memory. It is not evidence that a browser runs threads better: Firefox is the slowest at every N.

Why. Three pieces of evidence, all exploratory. First, hardware counters of the loop alone: both engines execute about a third more instructions per pixel than native code for the same WASM, 5.5 and 5.4 against 4.1. Second, why nobody reaches 8: from one to eight threads the instructions per pixel do not change, but cycles and cache misses rise. And across scalar, baseline and AVX2 builds, the faster one thread goes through memory, the less eight threads gain: scalar builds keep 0.97 to 0.98, the native AVX2 build drops to 0.72. Firefox's baseline filter sits exactly where its one-thread throughput puts it on that curve. So Firefox scales better because its loop is slower. [next] Third, the runtime itself. This walks down the five image sizes of the cutoff campaign. At 8192 squared a parallel region takes 3 to 4 milliseconds and one empty fork-join, about 11 microseconds natively, 105 in Chrome and 60 in Firefox, is a fraction of a percent to a few percent of it. At 1024 squared the browsers have lost half their efficiency; at 512 squared a whole region in Chrome takes less time than one calibrated fork-join, and the efficiency is 0.24 against 0.43 natively. The fork-join here is a yardstick measured separately in each run, not a component I subtracted. Keys: up and down change the image side.

RQ2: synchronization is where the engines part ways

Effect at N = 8: the atomic / local time ratio in the browser over the same ratio natively. 1 means synchronization costs what it costs natively. 99.5 % intervals; filled: rejected by Holm.

  • Shared atomics scale nowhere: with k up to 16, eight threads are slower than one in every environment (speedup 0.36 to 0.70).
  • Chrome pays 1.4 to 2.3 times the native cost when contention is concentrated, and 0.42 times when it is spread over 256 counters.
  • Firefox is never worse than native: no detectable difference at k = 1, cheaper from k = 4 on.
  • Part of Chrome's penalty exists with one thread: 698 ms against 380 ms at k = 1. It is a cost per operation, not only a scaling one.
RQ2. The metric is a ratio of ratios: how much slower the atomic histogram is than the local control, in the browser, over the same thing natively. Dividing by the control removes the effect of the input. One means synchronization costs what it costs natively. First, shared atomics do not scale anywhere: at k up to 16, eight threads are slower than one, in all three environments. Then the engines differ. Chrome pays 2.26 times the native cost at k equal to 1, 1.77 at 4, 1.43 at 16, and then flips: 0.42 at 256, where Chrome's atomic histogram is twice as fast as native. Firefox is never worse than native: 1.01 at k 1, not rejected, and below 1 after that. All ten contrasts keep their decision under Mann-Whitney and under the three sensitivity checks. And notice: Chrome's penalty is already there with one thread, so it is a cost of the operation itself.

Changing only the increment in a native program reproduces both directions of Chrome's effect, and with V8's baseline compiler the penalty at k = 1 is gone (effect 2.17 to 1.04). At k = 256 the mechanism is proposed, not shown.

Why. I read the machine code each engine produces for the same WASM instruction, i64 atomic add. LLVM natively emits one lock inc; SpiderMonkey one lock add; V8's optimizing compiler, which is what the campaign measures, a load and a lock compare-and-swap that goes back to the load if another core changed the counter in between; V8's baseline compiler a lock xadd. The picture is a model of eight cores, and the table next to it is what was measured. Now: the locked add at k equal to 1. One cache line, eight cores, it bounces; no retries. Native takes 380 milliseconds with one thread and 857 with eight: shared atomics do not scale. [next] The same with compare-and-swap: a core reads, loses the line to a neighbour, finds its value stale and retries. Chrome takes 698 and 1823 milliseconds. The native probe, where I changed only the increment, gives 677 and 2132. Counters: Chrome retries one add in four, native and Firefox practically none. [next] Now 256 counters: the lines spread over the cores, retries almost vanish, and the same sequence is the faster one: 210 milliseconds in Chrome and 240 in the probe against 414 natively. Why, I can only propose: reading the line first asks for exclusive ownership less often. [next] So the RQ2 finding is about a compiler's choice of instructions for an atomic add, not about WebAssembly threads as such: with only its baseline compiler Chrome's effect at k 1 goes from 2.17 to 1.04. Keys: 1 to 3 choose the sequence, up and down change k, R restarts the model.

Half of this project was making the measurement trustworthy, and a browser is not a benchmark-friendly process. Chrome's browser process moved itself out of my CPU mask through the D-Bus session bus, so I withhold the bus and check every run for escaped processes. Firefox was still doing start-up work during short iterations, so every browser run waits three seconds. The pinned Firefox updated itself in the middle of the exploratory campaigns despite the profile setting; strict validation caught every one of those runs, and only an enterprise policy stops it. One P-core of the machine is degraded: I checked it core by core, and with turbo off it is sound and as fast as the others. And a code review found asymmetries of our own in the histogram variants: I fixed them and re-ran everything on one tagged build. No table mixes two builds.

What these results can and cannot support

Declared limits

  • External: one machine, P-cores only, one version of each browser, headless, inputs larger than the caches (128 MiB against a 36 MB last-level cache).
  • Internal: thread placement is left to the kernel, because a browser cannot pin; at N = 8 the browsers' own threads share the eight cores.
  • Construct: "the same code" holds for the crate only. Below it, the engines' compilers differ, and that is what is measured.
  • Conclusion: a non-rejection is a bound (about 1 % for RQ1, 7 % for RQ2), not proof of equality.

Limits. External validity is the largest: one machine, P-cores only, one pinned version of each browser, and inputs that live in memory, not in cache, so the results hold for large work per parallel region. Internally, I cannot pin threads because a browser cannot, and at eight threads the browser's own helper threads share the cores. The construct: "the same code" is true for my crate; below it the engines compile differently, and that difference is exactly what I measure. And a non-rejection is a bound, not equality. What stays open: the mechanism of Chrome's advantage at k 256, the small efficiency dip at six and seven threads, where I tested and ruled out Rayon's splitting, and why SpiderMonkey's filter loop runs fewer instructions per cycle.

Answers, and what to do with them

RQ1

With enough work per parallel region, the same Rust/Rayon code scales in the browser as it does natively. WASM threads cost a factor in time that does not grow with N (1.17 to 1.36 for the filter) and a slower fork-join.

RQ2

Shared atomics widen the gap in Chrome under concentrated contention (up to 2.26) and narrow it under spread contention (0.42); Firefox is never worse than native. The penalty follows the instruction sequence V8 emits for an atomic add.

If you ship parallel WASM

  • Keep parallel regions coarse: at 8 threads, about 0.5 ms of work per region or more.
  • Prefer per-task state merged at the end to shared atomics; it scales to 8 everywhere.
  • Measure in both engines: the same module is not the same machine code.

If you benchmark browsers

  • Fresh process per run, run as the unit, plan fixed before the data.
  • Verify confinement, version and quiet in every run; do not assume them.
To answer the two questions. RQ1: with enough work per parallel region, the same code scales in the browser as it does natively; WebAssembly threads cost a constant factor and a slower fork-join. RQ2: synchronization is where the engines differ, and the cause I can point to is the instruction sequence V8's optimizing compiler emits for an atomic add: worse under concentrated contention, better under spread contention. For developers: keep regions coarse, avoid shared atomics in favour of per-task state, and measure in both engines. For benchmarkers: a CPU mask, a fresh profile and a pinned version do not by themselves confine, quiet and freeze a browser; verify it in every run.
